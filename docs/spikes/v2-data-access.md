# Spike: generic helpers cover data access in any ORM

Question: do four generic data-access helpers (SQL text, text rules, model naming, method classes), plus the five generic helpers of `v2-recipes` (`resolve-names`, `const-strings`, `mount-graph`, `call-return`, `param-flow`), let recipe rules find tables, reads and writes for 13 data-access stacks with no ORM-specific engine code?

**Verdict: go-with-changes.** The Bar is met on the six release-blocking stacks on their tuning repos, and the Drizzle recipe reproduces both fixtures exactly. The result is on tuning repos only (the helpers were designed on them), the GORM repo does not exercise GORM's call API, and the non-blocking stacks show three kinds of access no helper reaches. Details below.

## Setup

- Machine: Apple M3 Pro (arm64), 18 GiB, macOS (Darwin 27.2.0), Node v26.13.0. The machine was busy while this ran (load average 14 on `uptime`); timings were printed by the runner but are not recorded, so none are claimed here.
- Prototype: `docs/spikes/v2-data-access/` (own `package.json`, exact pins `@ast-grep/napi` 0.51.3 and `@ast-grep/lang-go` 0.0.6, `npm install --no-audit --no-fund`, outside the pnpm workspace). `engine.ts` is a copy of `docs/spikes/v2-recipes/engine.ts` extended with the `table` and `access` emits and the four helpers. It contains no ORM name; every ORM word is in `recipes/<stack>.json`.
- Corpus: 13 repos pinned in `evals/oss/repos.json`, role `tuning`, cloned by `pnpm eval:clone` at the listed SHAs. All 13 candidates use the stack named, so none was replaced (see GORM below for a caveat).
- Scoring: a scorer (since removed from the repository; keys `<file>|<table>`) applied to the recipe output converted to the `index --dump` shape. Per stack, recall and precision in the results file are the lowest of the three kinds (table, read, write).
- Commit order: the repos and all 13 label files were committed first (`Pin 13 data-access repos and hand-label ...`), before any engine or recipe code. One label fix followed (below).
- Labels were written by the agent that also wrote the recipes (one agent, not two people). Reads and writes were found by `rg` and read call site by call site; for `pg-boss` a regex listing of SQL statements was used as an aid and spot-checked, so its labels and its recipe share a blind spot for SQL built by concatenation across non-literal pieces. The maintainer spot check (1 in 10) is still pending.
- Label rules: a table is named by the name the source states (Prisma `@@map`, TypeORM `name`, a migration `CREATE TABLE`), else by the model name as written (Mongoose `model("User")`, MikroORM class name). Reads and writes are DML only; DDL (CREATE, ALTER, DROP) is neither. A call that modifies and returns the row (`findOneAndUpdate`, Prisma `update`) is a write only. Keys are per file, so the scorer does not check which function holds a call.
- Scope notes: `ent` is scored on `examples/` only (hand-written example files plus the generated `Table` constants under `examples/*/ent/*/`). `pg-boss` excludes `test/`, `docs/` and test directories. `simplebank` (sqlc) labels `db/query/*.sql`, not the generated `db/sqlc/*.sql.go`. ent views (`clean_users`, `pet_user_names`) count as tables. ent labels include join-table reads and writes from `Add<Edge>` and `Query<Edge>` calls; predicate-implied joins (`Has<Edge>()`) are not labelled.

### How the numbers moved while the recipes were written

The helpers are designed on these repos, so recipes and helpers were iterated against the missed and extra lists. First complete run, before any fix: drizzle 100/100, prisma 100/100, typeorm 100/100, kysely 100/100, sequelize recall 33.3, mikro-orm 50, mongoose 50, raw-sql recall 90.0 / precision 100, database-sql 100/100, sqlx recall 100 / precision 91.7, sqlc 100/100, gorm 100/100, ent 0. The Drizzle recipe on `fixtures/adapters` had 2 differences (of 10 edges). Changes made after that run, each from a miss, none by editing a label to fit a score except the one label fix:

1. ent: Go `const` values are an `expression_list`; the engine unwrapped none (ent 0 to 63.2 recall).
2. SQL text: a string counts as SQL when it holds a statement shape anywhere (`SELECT ... FROM`, `INSERT INTO`, `UPDATE ... SET`, `DELETE FROM`, `CREATE TABLE`, `TRUNCATE`); the first version required a leading verb and missed parenthesised subqueries and CTE fragments (pg-boss `plans.ts|job`).
3. `call-return` applied to a table name built by a call (`${plans.clockTable(schema)}`), and `resolve-names` follows `ns.member` through a namespace import (pg-boss clock table).
4. Drizzle: a constant holding `alias(users, "a")` is followed to its table; `when.viaWorkspaces` (a package that depends on a workspace package that declares `drizzle-orm`, as the adapter does). Both fixture differences came from these two.
5. Sequelize recipe: ast-grep parses `await r.m<T>(x)` as a call of an `await` expression, so the recipe needs the pattern `await $R.$M<$T>($$$A)` besides `$R.$M($$$A)`. Without it every awaited generic call was missed.
6. Label fix (separate commit): `openencoder/scripts/20_settings_options.sql` also ends with `SELECT setval(...) FROM settings_option`; the first labelling pass read only the head. The sqlx precision of 91.7 came from this; the recipe was right.

Caveats that bound these numbers: every repo is a tuning repo, so a pass shows the helpers can express the stack, not that they generalise (GH-249 and GH-250 score held-out repos). Repos are small for most TypeScript stacks (1 to 7 tables). Precision is 1 everywhere because a read or write is kept only when it resolves to a declared table; that is a design choice of the helpers (`knownTablesOnly`, resolved bindings), and the cost shows up as recall. For pg-boss, 106 SQL references to undeclared names (catalogs, CTEs that look like tables) were skipped and 66 references with a runtime-built table name were kept as low-confidence entries with a reason.

**GORM caveat.** `learning-cloud-native-go/myapp` does use GORM (`gorm.DB`, `typed.G`), but its queries are SQL strings generated by `gorm gen` and run through `Raw`. It has no `First`, `Find`, `Create` or `Where` chain, no `AutoMigrate` and no `Model()` call. The GORM row therefore shows that SQL text covers the generated-repository form; it says nothing about GORM chain methods, which would need model naming plus method classes as in the TypeORM and ent recipes (not measured). I kept the pinned repo as the issue lists it rather than substituting; a second GORM repo with chain calls should be added before the GORM verdict is relied on.

## What no helper could reach

Each of these would be a low-confidence node with a reason, not a guess.

- Runtime table names: pg-boss `${schema}.${table}` in `plans.ts` where `table` is a parameter (66 references, all in files whose literal references are already found, so no file-level miss). Reason: the name is a function parameter filled at several call sites.
- Models carried by a loop variable (Mongoose `migrate.ts` and `indexes.ts`: 6 reads and 2 writes missed). Reason: the model is a loop variable over an array literal and the table is read as `model.collection.name`.
- Relation names (MikroORM `populate: ['books']` and `populate: ['author']`: 2 reads missed; ent edge traversals and the join tables behind `Add<Edge>`: 14 reads and 8 writes missed across `traversal`, `start`, `m2m*`, `o2m*`, `o2o2types`, `privacytenant`). Reason: the target table is the declared type of the relation, found in the schema, not in the call.
- Table nodes' `columns`, `dialect`, `symbol` (Drizzle adapter fields): an output gap of the prototype, not of the helpers.

## Plan assumptions checked

- "Four generic helpers plus the five existing ones, no ORM-specific code": held for all 13 stacks; the engine holds no ORM name. Three additions to existing helpers were needed (namespace import resolution, call-return on a table name, following a constant that holds an `alias(...)` call) and one new engine option (`when.viaWorkspaces`, which the adapter's rule needs).
- "A collection counts as a table" (Mongoose, MikroORM on Mongo): held; the collection is named by the model name as written. Mongoose's pluralised collection names were not computed.
- "A table named only at runtime is a low-confidence node with a reason": held; 66 pg-boss references are kept with the reason "table name is built at runtime".
- "90% recall at 95% precision for tables, reads and writes on every release-blocking stack, 3 of 3 runs byte-identical, Drizzle reproduces both fixtures exactly": met (below).
- Not shown by this spike: held-out generalisation, GORM chain calls, scale (the biggest repo, ent, has 2,333 Go files and ran in about 190 ms per run on a busy machine, but only `examples/` is scored), and agent-written recipes (these recipes were written once each by one agent with the engine in view; three unaided runs with recorded model ids were not part of this issue and belong to GH-249 and GH-250).

## Result against the Bar

`jq '[.stacks[] | select(.blocking and (.recall < 0.9 or .precision < 0.95))] | length' docs/spikes/v2-data-access/results.json` prints **0**: all six blocking stacks pass (recall 1.0 and precision 1.0 on tables, reads and writes), 3 of 3 runs identical, and the Drizzle recipe reproduces both fixtures with no differences. Non-blocking: TypeORM, Kysely, Sequelize and sqlc pass; MikroORM (read recall 0.5), Mongoose (read 0.5, write 0.8182) and ent (read 0.6316, write 0.8367) miss for the reasons above, and are reported, not blocking.

Verdict **go-with-changes**: GH-247 builds the four helpers as specified; the changes are (a) namespace-import and `ns.member` resolution in `resolve-names`, (b) `call-return` usable inside SQL substitutions, (c) the receiver-declaration lookup for method classes, (d) workspace-dependent applicability (`viaWorkspaces`) in recipe `when`, (e) statement-shape detection for SQL strings, and (f) an open item: relation-type lookup for ORMs whose tables are reached through relations (MikroORM, ent, Sequelize `include`), plus a Drizzle output for `columns`, `dialect` and `symbol`. GH-249 and GH-250 should add a GORM repo with chain calls.
