The recipe is at `.gantry/recipe.json`, and the dry-run reports `ACCEPTED`. It lists 20 endpoints, 0 routes and 7 tables.

- **Stack:** Go with Gin for HTTP and GORM for the database. There is no frontend.
- **Endpoints (20):** `GET /api/ping` plus the endpoints under `/api/articles`, `/api/tags`, `/api/users`, `/api/user` and `/api/profiles`.
- **Tables (7):** `ArticleModel`, `ArticleUserModel`, `FavoriteModel`, `TagModel`, `CommentModel`, `UserModel` and `FollowModel`. They come from a text rule that matches `type XxxModel struct` in `models.go` files, because `UserModel` doesn't embed `gorm.Model`. The rule would also pick up any later struct whose name ends in `Model`.
- **Groups in `hello.go`:** `v1 := r.Group("/api")` and `testAuth := r.Group("/api/ping")` resolve correctly.

**What I couldn't express:** the route functions live in the `users` and `articles` packages. `hello.go` mounts them inline, for example `users.UsersRegister(v1.Group("/users"))`. The `mount-graph` and `param-flow` helpers did not carry those prefixes across packages or inline arguments, so the router-based endpoint rule dropped all 26 handlers in the `users` and `articles` route files.

As a workaround, I wrote one rule per prefix, each limited to the named registration functions. The prefixes (`/api/articles`, `/api/tags`, `/api/users`, `/api/user`, `/api/profiles`) are hardcoded from `hello.go`. If the mounts in `hello.go` change, those rules need updating by hand.
