# Gantry Engineering Spec

The single source of truth for contracts. Every issue references sections here by number. If an issue conflicts with this spec, follow the spec and flag it in the PR. To change a contract, edit this file in the same PR and say so in the PR description.

Plan doc (background and rationale): https://claude.ai/artifact/7UCZZRCs4k45gPkKBfocmY

## 1. Ground rules

- **Repo:** `jbknick/architecture-visualization-cc-plugin` (public). The product's display name is **Claude Code Architecture Visualisation Plugin**; the CLI command, package scope, MCP server name, plugin id and data directory keep the short identifier **`gantry`**. Default branch `main`. One branch and PR per issue (`gantry/<issue-number>-<short-slug>`), stacked on its dependency's branch when that one isn't merged yet.
- **Public repo:** the test bed (Devprentice) is private. Never commit its code, fact sheets, descriptions, graph dumps or screenshots showing its code. Private eval data lives only in git-ignored `evals/private/`. Commit only scripts and aggregate numbers.
- **Toolchain:** Node 26 (`.nvmrc`, `engines.node` `>=26 <27`), pnpm 10.31.0 (`packageManager`, `engines.pnpm`; `pnpm check` fails when the running Node major differs from `.nvmrc` or the pins disagree), TypeScript strict, ESM (`"module": "NodeNext"`), vitest, Biome. Build with `tsc -b`; bundle CLI/MCP entry points with `tsup` into `plugin/dist/`.
- **Local quality gate:** `pnpm check` = `biome check . && tsc -b && vitest run` (plus the version, evals and describe-mutation checks in `package.json`). `tsc -b` type-checks and writes the git-ignored `dist/` output; TypeScript 7 rejects `--noEmit` on referenced composite projects (TS6310). Biome follows git's ignore rules (`.gitignore` and `info/exclude`), so untracked local files do not fail it. The description mutation check runs on a temporary copy and never edits tracked files, so several checkouts and worktrees can run the gate at once. It must pass before a PR. This repo has no CI: never add a workflow under `.github/workflows/` or wait for GitHub Actions. The composite Action in `action/` (#282, sections 3, 10 and 14) is something Gantry ships for users' repositories, not a gate for this one; Gantry never writes a workflow file into a target repo, the user adds it. Live runs of the Action happen in a separate sandbox repository, never here.
- **Determinism:** index output is sorted and stable; no timestamps or random values inside graph content (timestamps only in `meta`, `usage_log`, `created_at`).
- **Target repo is read-only** except `.git/hooks/*` and local git config written by `gantry hooks install`. Recipes (`.gantry/recipe.json`) are written by hand and committed by the user; Gantry only reads them (section 5, recipe) and checks them with `gantry recipe check --nodes`. Never write any other file into a target repo's working tree.
- **No framework- or ORM-specific code (#203):** what a stack's routes, endpoints and tables look like lives in the repo's recipe (`.gantry/recipe.json`, section 5), applied the same way on every index run. New stack knowledge is a recipe rule or a generic helper, never a new adapter. Data access follows the same rule (#247): tables, and the functions that read and write them, come from recipe rules and four generic helpers (`sql-text`, `text-rules`, `model-naming`, `method-classes`) for any ORM or raw SQL, and no ORM or driver name appears in the engine or a helper. The built-in adapters that predate recipes (TanStack Router, TanStack Start, Hono, oRPC, Drizzle) stay registered until recipes replace them (see section 9), and are removed in the issues that replace them; `recipe/data-access.test.ts` proves, for Drizzle, that a recipe alone writes what the built-in adapter writes.
- **Process I/O:** hooks and the MCP server log to stderr only. stdout is reserved for protocol / JSON output.
- **Fail open:** git hooks and Claude Code hooks must never block a commit or a tool call because Gantry failed. Catch, log to `<dataDir>/logs/`, exit 0.
- **Worker guard:** if env `GANTRY_WORKER=1`, every hook entry point exits 0 immediately with no output.
- **Dependencies:** only those in section 2 without justification in the PR.
- **Releases (#281):** a release carries one tarball, `gantry-<version>.tgz`, with its `.sha256`, for every platform. Gantry is never published to a package registry. The tarball holds the bundled CLI and a lockfile for the native dependencies the bundle leaves external, which a runner installs with `npm ci`. The maintainer tags, pushes and uploads; no script does.

## 4. Paths and data

- Worktree root: `git rev-parse --show-toplevel`. `worktreeHash` = first 16 hex chars of sha256(realpath(root)).
- Data dir: one directory per worktree for every entry point (MCP server, hooks, skills, terminal CLI), `<base>/repos/<worktreeHash>/` (#141), or, for a repo that a workspace file lists, one directory per workspace, `<base>/workspaces/<first 16 hex chars of sha256(realpath(directory of the workspace file))>/` (#214, below). Every repo of a workspace resolves to the same data dir. `<base>` is, in order: `CLAUDE_PLUGIN_DATA` when set; else the plugin data dir derived from `CLAUDE_PLUGIN_ROOT` when that is an installed plugin path `<claude home>/plugins/cache/<marketplace>/<plugin>/<version>` (base `<claude home>/plugins/data/<plugin>-<marketplace>`, characters other than letters, digits, `_`, `-` replaced by `-`; this is the directory Claude Code assigns); else `~/.gantry/data`, which only a run with no plugin base reaches (a terminal run from a clone). With a plugin base, nothing under `~/.gantry/data` is ever read or written, even when an index exists there; a plugin data dir without an index gets a fresh one, and `init` and a full `index` write `gantry: no index for this repository in <dataDir>; building a fresh one` to stderr first. Claude Code (plugins reference, checked in #141) exports `CLAUDE_PLUGIN_ROOT`, `CLAUDE_PLUGIN_DATA` and `CLAUDE_PROJECT_DIR` to hooks and MCP stdio servers, substitutes `${CLAUDE_PLUGIN_ROOT}` and `${CLAUDE_PLUGIN_DATA}` inline in skill, agent and command content, and does not put them in the environment of commands run through the Bash tool. So skills run `CLAUDE_PLUGIN_DATA="${CLAUDE_PLUGIN_DATA}" "${CLAUDE_PLUGIN_ROOT}/bin/gantry" ...`, and `plugin/bin/gantry` exports `CLAUDE_PLUGIN_ROOT` (its own parent directory) when it is unset, which covers a terminal run of the installed copy and the `bin/` entry on the Bash tool's `PATH`. **Who creates a data dir** (#147): `init`, `index`, `embed`, `map`, `config set`, `hooks install`, lookups (`search`, `node`, which heal first) and MCP tool calls (lazy refresh). Commands that only read or keep an index current (`backlog`, `usage`, `heal`), the SessionStart hook and the git hooks create nothing for a repository that has no store; they report the missing index instead. Before #147 `backlog`, `usage` and `heal` created an empty store there, which also hid the SessionStart reminder. A run from a clone path (`--plugin-dir`, `<clone>/plugin/bin/gantry`) has no derivable plugin base and uses `~/.gantry/data` unless `CLAUDE_PLUGIN_DATA` is set (docs/INSTALL.md). Contents: `gantry.db`, `overlay.db` (what a person decided: duplicate dismissals, saved node positions, labels, hidden parts, groups and saved views; attached to every store connection as `overlay`, section 9; tables are only ever added with `CREATE TABLE IF NOT EXISTS`, never dropped or altered; it has no schema version and Gantry never deletes it, only `gantry uninstall` does, with the rest of the data dir; `GantryPaths.overlayPath`), `parse-cache.db` (disposable per-file parse results keyed by file id (section 6) and content hash; a pure accelerator that is not part of the store schema and is safe to delete), `config.json`, `catalog/`, `logs/`, `models/` (embedding model cache may live in `~/.gantry/models/` instead, shared).
- Global config: `~/.gantry/config.json`. Shim: `~/.gantry/bin/gantry`.
- Recipe (#203): `<root>/.gantry/recipe.json`, a file of the target repo, not of the data dir. The user writes and commits it; Gantry never writes it. The main layer reads it from `HEAD` (`git show HEAD:.gantry/recipe.json`), the working layer from disk, review from each side's ref (section 11).
- `core/paths`: `resolvePaths(cwd: string, env?, opts?: { workspaceFile?: string }): GantryPaths` returning `{ root, repo, workspace, worktreeHash, dataDir, dbPath, overlayPath, configPath, catalogDir, logsDir, globalConfigPath, shimPath }`. `root` and `repo` are those of the repo the command runs in; `workspace` is `{ file: string | null, repos: { name: string, root: string }[] }` (#214): `file` is the workspace file (absolute) or `null`, and `repos` lists every repo of the workspace sorted by name (a repo with no workspace file is a workspace of one: `{ file: null, repos: [{ name: repo, root }] }`).
- **Workspace file (#214; `core/src/workspace/file.ts`).** A project of several related repos lists them once in `gantry-workspace.json`, and one `gantry init` from any of them indexes all of them into one store. The file is `{ "repos": [{ "path": string, "repo"?: string }] }` (zod, strict, at least one entry). `path` is relative to the directory of the file, or absolute. A value that looks like a URL (`^[a-z][a-z0-9+.-]*://` or `^[^/]+@[^:]+:`) is rejected with `workspace file <file>: repos[<i>].path must be a local path, not a URL` (exit code 1); a path that is not the root of a git work tree is rejected with `workspace file <file>: repos[<i>].path <path> is not the root of a git repository`. `repo` overrides the repo name that `repoName` derives (it must not contain `:`). Two entries with the same name, or the same repo twice, are an error naming both entries. Remote repos are not supported.
- **Discovery (`findWorkspaceFile(repoRoot, { startAbove?, home? })`).** The walk starts at the parent of the directory the user is in (the path through which the repo was reached, so a repo reached through a symlink finds the file next to the link) and then at the parent of the real root, and goes up to the filesystem root, but not above the user's home directory when the walk passes through it. It takes the `gantry-workspace.json` that lists the repo (each `path` compared by real path with the repo's real root); a file above a repo it does not list is passed over, so the repo is a workspace of one. A repo that two files list is an error naming both (two indexes of one repo), which `--workspace` settles. A file met on the way that is invalid is an error (a file that cannot be read is not a file the repo can be sure it is not in). `--workspace <file>` on `init`, `index`, `heal` and `map` replaces discovery; the file must list the repo, else `workspace file <file>: does not list this repository (<root>)`. Hooks and the MCP server use discovery only, through `resolvePaths`. A linked worktree is its own repo with its own name rules: list it under its own `repo` name, or it stays a workspace of one.
- Rows of a repo that is no longer in the workspace file (or whose name changed) are deleted by the next full main index; the rest of the store, descriptions included, is kept. A repo that returns finds its descriptions (stored by content key) and the overlay (`overlay.db`) as they were, and a full main index copies the stored descriptions back into the search rows (`refreshDescriptionFts`), so `index` alone restores them.
- `GantryPaths.repo` is the repo name carried in every stable id (section 6), computed by `repoName(root)` (`core/src/paths`): the last two path segments of `git remote get-url origin` with any `.git` suffix and trailing slashes removed, as written (`https://github.com/a/b.git`, `git@github.com:a/b.git` and `ssh://git@host/a/b` all give `a/b`); with no `origin`, the basename of the worktree root (a linked worktree of a repo with an `origin` gives the origin name). A `:` in the name becomes `_`. Never a local path or `worktreeHash`, so two clones of one repo at different paths give byte-identical ids and `index --dump`.
- Nested worktrees under the repo (e.g. `.claude/worktrees/*`) are excluded from discovery of the parent.

## 5. Config (zod, `core/config`)

Project config (`<dataDir>/config.json`) is deep-merged over global (`~/.gantry/config.json`) over defaults.

```ts
type TaskName =
  | "describe.init"
  | "describe.sync"
  | "describe.precommit"
  | "describe.retry"
  | "overview"
  | "explain";
type GantryConfig = {
  precommit: { mode: "off" | "timeboxed" | "strict"; budgetMs: number; maxFunctions: number }; // off, 20000, 50
  routing: Record<TaskName, { model: "haiku" | "sonnet" | "opus"; effort: "low" | "medium" | "high" }>;
  exclude: string[]; // extra globs, added to built-ins
  workspaces: { overrides: Record<string, { kind?: "app" | "package" }> }; // keyed by workspace id (`ws:<repo>:<name>`), package name or directory
  duplicates: {
    mode: "warn" | "block";
    ignore: string[];
    thresholds: {
      nearJaccard: number;
      nearTokenJaccard: number;
      codeVector: number;
      codeVectorTokenJaccard: number;
      semantic: number;
    };
  }; // 0.85, 0.75, 0.98, 0.50, 0.60: fitted in M2 (#32, #131), see docs/milestones/M2.md; codeVector was 0.96 in M0; the two token gates were added in #131
  backlogReminderThreshold: number; // 100
  renameSuggestions: boolean; // false (measured in M0: Haiku flagged 0 of 23 misleading names, so precision is not measurable; stays false)
  worker?: { binary?: string }; // absent by default: absolute path of the `claude` binary for the headless worker; first in the binary resolution order (section 16)

```
Workspace file (#214, section 4): `gantry-workspace.json` is not part of `GantryConfig`; it is a file of the project, found by walking up from a repo, and `--workspace <file>` on `init`, `index`, `heal` and `map` names one explicitly. Config (`<dataDir>/config.json`, `exclude`, `workspaces.overrides`) lives in the workspace's data dir and applies to every repo of the workspace; each repo keeps its own git ignore rules and its own `.gantry/recipe.json`.

Boundaries (group `mayUse`, section 7) are warn-only: they have no `block` mode and no config switch, and nothing they print ever fails a hook, a commit or an edit (section 14).

Routing defaults: `describe.init|sync|precommit` haiku/low, `describe.retry` sonnet/low, `overview` sonnet/low, `explain` sonnet/medium.

**Recipe (`.gantry/recipe.json`, #203; `core/src/recipe/schema.ts`).** Where this repository declares routes, pages, endpoints, tables and the code that reads and writes them (#247), as data that every index applies unchanged. Nothing in it is evaluated as code, and every object is strict (an unknown key is an error).

```
{ "version": 1,
  "dependencies": [{ "name", "workspace"?, "role": "framework" | "data-access" | "neither", "note" }],
  "helpers": ["resolve-names" | "const-strings" | "mount-graph" | "call-return" | "param-flow" | "fs-routes"
              | "sql-text" | "text-rules" | "model-naming" | "method-classes"],
  "passthrough"?: ["get", "basePath", ...],
  "models"?: { "explicit"?: { "<model>": "<table>" }, "snakeCase"?: bool, "plural"?: bool },
  "methods"?: { "read"?: [method names], "write"?: [method names] },
  "tablePassthrough"?: ["alias"],
  "sql"?: { "tags"?: [...], "files"?: [globs], "exclude"?: [globs], "sqlFiles"?: [globs] },
  "rules": [{ "id", "language": "typescript", "when"?: { "dependency": [...], "viaWorkspaces"?: bool }, "files"?: [globs],
              "rule": <ast-grep rule>, "constraints"?: { "<META>": <ast-grep rule> },
              "emit": <emit>, "examples": { "match": [snippets], "noMatch": [snippets] } },
            { "id", "language": "go", "when"?: { "dependency": [Go module paths] }, "files"?: [globs], "uncalled"?: bool,
              "rule": <ast-grep rule>, "constraints"?: { "<META>": <ast-grep rule> },
              "emit": <go emit>, "examples": { "match": [snippets], "noMatch": [snippets] } },
            { "id", "language": "text", "when"?, "files": [globs], "rule": { "regex", "flags"? },
              "emit": { "kind": "table", "name": "$1" | ["$1", "$2"], "model"?: "$1", "data"? }
                    | { "kind": "query", "fn": "$1", "sql": "$2", "files"?: [globs] },
              "examples": { "match": [text], "noMatch": [text] } }] }
```

- `rule` and `constraints` are ast-grep rule objects handed to `findAll` unchanged; their shape is checked (known keys only). A rule runs on the files of the workspaces that declare one of `when.dependency` (the workspace's dependencies or frameworks) and that match `files` (picomatch, `dot: true`). Captures in an emit are `$NAME` (one node), `$$$NAME` (all nodes of a multiple metavariable) or `=text` (a literal, for a method).
- `emit` kinds: `router` (the match is a router instance; optional `base` path capture); `mount` (`parent`, `child`, optional `prefix`, optional `childIsScope` when the child is a function whose first parameter is the router, as in a Fastify plugin; `child` may be `$$$NAME` and mounts each router among its arguments); `endpoint` (`receiver`, `method`, `handler`, optional `path`, optional `pathFromChain`: when the path argument is absent or is no path, reuse the path of the previous registration in the same call chain and read every argument as a handler); `middleware` (`receiver`, `handler`, optional `path`, default `*`); `route` (a page route named by `id`, with `options` read for `component`, `loader`, `beforeLoad`, or `root`); `fileRoute` (a route whose id and URL come from the file's place in the routes folder by `convention`, now `tanstack-router`). Each emit may carry `data: { adapter }`, the label written into the node's `data.adapter` (for example `"hono"`); it is optional because TanStack Router route nodes carry none.
- Data-access emits (#247; no new node kinds, they write `table` nodes and `reads` / `writes` edges as section 9 lists): `table` (`name`: a capture, `=text`, `@class` (the class a matched decorator decorates) or a list of these, the first that reads as text; optional `model`: the name the code uses for the table (an entity, class or export name); optional `binding`: the identifier the match is assigned to stands for the table in later code; optional `data`: the node's data fields in the recipe's order, each `$X` (a capture's text, a string literal's value), `@name`, `@exportName`, `@symbol`, `@file`, `@line`, `{ "keysOf": "$X" }` (the property names of an object literal, or of the one a function returns) or a literal; `name` comes first unless the recipe places it); `read` and `write` (the table comes from `table`: an expression bound to a table, which is a string, an identifier, `ns.member` or a call named in `tablePassthrough`; from `model`: a model name, `$$$X` for several; or from `receiver`: the text of its declaration (`this.p` reads the enclosing class, `x.p` and `x` the declaration of `x`) is matched against the `receiverDecl` regexes, whose first group is the model and `{prop}` the member name; optional `method`: the match counts only when `methods` puts that method in this emit's class). A `read` or `write` with no table it can resolve emits nothing: a table is never guessed.
- **Go rules (#368).** A rule with `language: "go"` is an ast-grep rule over a `.go` file, run on the tree-sitter Go grammar the indexer already parses Go with (section 3, `lang/go/`; no Go toolchain), so it has the same `rule`, `constraints`, `files`, `examples` and captures as a TypeScript rule. `when.dependency` names Go module paths: a workspace passes it when a `require` line of its `go.mod` names one. `gantry recipe check` wraps each example: a snippet that starts with `func`, `type`, `var`, `const` or `import` is a file body, anything else is a list of statements. **A pattern with one argument must give its context**: tree-sitter reads a bare `$R.Use($H)` as a type conversion, so it matches no call; write `{ "pattern": { "context": "func _() { $R.Use($H) }", "selector": "call_expression" } }` (patterns with two or more arguments, or `$$$`, parse as calls and need none). A rule matches the expression, not its statement: match `chi.NewRouter()`, not `r := chi.NewRouter()`.
  - Go emits are the TypeScript ones without the page routes (`route` and `fileRoute`), with these differences. `mount` without `child` mounts the matched expression itself under `parent` at `prefix` (a call that returns a new router, `parent.Group("/x")`); with `child` and `childIsScope`, the child is a function literal, or a named function, whose first parameter is the router (`r.Route("/x", func(r chi.Router) { ... })`). `endpoint` has `method` (a capture, `=ALL` or `=GET`; a name like `Get`, `GET` or `MethodGet` reads as `GET`) or `methodInPath: true`, which splits a leading `METHOD ` off the path text (`"GET /users/{id}"`) and gives `ALL` when the path has none; `pathFromChain` does not exist. `table` has no `binding`, `@class` or `keysOf`; its `name` is a capture or `=text`, and a capture that is a Go type reads as the type's name (`&articles.Article{}` gives `Article`), a string literal or a constant as its value. `read` and `write` have no `receiver` and `receiverDecl`: the table comes from `table` (a string, a constant, a concatenation of them; a name known only at run time is a `{<expression>}` table with `data.reason`, `low` edges) or `model` (a string, a type written out (`&User{}`, `[]User`), or any expression whose type the Go resolver infers: `x` after `var x User`, `x := &User{}`, a parameter, a field, a call's first result), and `method` as in a TypeScript rule.
  - Helpers on Go: `mount-graph` builds a full path from the prefix chain exactly as for TypeScript (router groups and sub-routers). `resolve-names` finds what a name stands for in the syntax of its file: the nearest `x :=` or `var x` before the use in the blocks around it, a parameter, an alias of a router (`v2 := v1`), a package-level `var`; `passthrough` lists chain methods that return the same router (`r.With(mw).Get(...)`). `const-strings` reads a string constant of the same file or of another file of the same directory (the same package), and `+` concatenations of strings and constants; an identifier or a `pkg.Name` it cannot read is a `{name}` piece, with `data.reason`. `call-return` follows a call to the function or method it resolves to (the Go resolver, which infers the type of a receiver such as `a.Account.router()` through struct fields and local assignments) and takes the router that function returns. `param-flow` makes a parameter a router when something passes one into it: the call is resolved to the function, the argument becomes a mount with no prefix. A function that takes a router and that no call in the read files names registers nothing by default. A Go rule may set `"uncalled": true` (#368, off by default, one flag per rule): the routes, mounts and middleware that rule finds on such a parameter are then registered at the paths the function writes (an unreachable `loadRoutes(mux)` still declares its routes). With the option on, dead code and callers outside the read set (test files are not read) count as "called nowhere", so the rule can list endpoints that never run. A function that is called, but whose call does not resolve, registers nothing in either case. `sql-text` reads Go string literals, raw strings and `+` concatenations whose other operands are constants (a name it cannot read becomes a placeholder, and a table named by it a run-time table); `sql.files` and `sql.exclude` globs apply to `.go` files too. `model-naming` and `method-classes` apply unchanged to the model a `model` capture yields. `fs-routes` and `tablePassthrough` do not apply to Go (no file routes, no `alias(...)` call), and `receiverDecl` does not exist for Go (a declaration's text is a TypeScript idea; use `model` with an inferred type). A field of a struct is not a router: `s.router.Get(...)` registers nothing unless a variable holds the router.
  - Attribution: a `read` or `write` belongs to the innermost Go function or method that contains the call, or to the file for package-level code (`var q = "SELECT ..."`); the edge is stored with that file. A `table` rule declares its node in the file that holds the match. A text rule `table` (a `.sql` file or a migration) belongs to the first extracted file of its workspace, in path order; a `.sql` file inside a Go module belongs to the module's workspace when the TypeScript workspace at the same directory has no file. A text rule with `emit.kind: "query"` (#368) says which Go function runs the statements of a text file: `fn` (a group) is a function name, or a method name without its type, and `sql` (a group) the text holding the statements. The tables that text reads (`FROM`, `JOIN`) and writes (`INSERT INTO`, `UPDATE`, `DELETE FROM`, `TRUNCATE`) become `reads` and `writes` edges from every function or method of that name in the Go files of the module that `files` (globs, default all) selects, to the tables that are declared; a table that is not declared is skipped, and a name with no function emits nothing. This is the shape of `sqlc` output, where each `-- name: GetAccount :one` block in a query file has a generated function of the same name; the engine knows no tool.
- A rule with `language: "text"` runs over files that have no syntax tree in the index (a schema file, SQL migrations), found with `git ls-files` (tracked, and untracked files that are not ignored; at most 1 MiB each) and matched by `files`; `rule.regex` is matched against the whole text (`flags` default `gm`) and `$1`, `$2` ... are its groups. A text rule emits tables, or (#368) queries, which attribute the tables a text reads and writes to a Go function (see Go rules). Only files with a syntax tree are rows of the index, so the node of a table declared in a text file belongs to the first TypeScript or Go file, in path order, of that file's workspace; `data.file` and `data.line` name the text file. A text rule's `when` is judged against the workspace of the text file.
- `models` states how `model-naming` turns a model name into a table: the `explicit` map, then the name itself, then `snakeCase` and `plural` forms, and then the models the recipe's own emits declared. `methods` states which methods `method-classes` puts in each class; a method in both lists is a write, one in neither is no access. `sql` turns on `sql-text` (listed in `helpers`): the strings, template literals and tagged templates (`tags`, whatever they start with) of the TypeScript files in `files` minus `exclude` are read when they hold a statement shape (`SELECT ... FROM`, `INSERT INTO`, `UPDATE ... SET`, `DELETE FROM`, `CREATE TABLE`, `TRUNCATE`); `CREATE TABLE` declares a table, `FROM` and `JOIN` read, `INSERT INTO`, `UPDATE`, `DELETE FROM` and `TRUNCATE` write, names defined by `WITH` and catalogs with no declaration are skipped, and a substitution is followed to a constant or, with `call-return`, to the string a function returns. `sqlFiles` globs `.sql` files, which declare tables (a `.sql` file is not code that runs, so it has no reads or writes). `when.viaWorkspaces` widens a rule to workspaces that depend on a workspace of the repository that declares one of the `when.dependency` packages.
- **A recipe is untrusted input** (#247). The repository controls it, and it supplies JavaScript regular expressions (`rule.regex` of text rules and the `receiverDecl` templates), which backtrack: `(a+)+$` on a long line can run for hours. Limits, enforced by the schema and the engine: a pattern is at most 500 characters; a recipe has at most 50 text rules (the 51st and later are skipped with an error); one run reads at most 200 text files for text rules and 200 for `sql.sqlFiles`, each at most 1 MiB; a path that is a symbolic link, or that resolves outside the repository root (a linked directory), is never read. Over a cap is an error for that rule, which is skipped; nothing crashes. A recipe regex never runs on the calling thread: it runs in a `node:worker_threads` worker that the caller waits on for at most 100 ms per match call, 400 ms for all recipe regexes of one index run together (the worker start-up is not counted). When a budget is spent the worker is terminated, the rule is skipped for the rest of the run with one stderr line `Gantry: recipe rule <id> skipped: regex exceeded 100 ms` (an invalid regex gives `invalid regex: <reason>`), the rest of the recipe and the index complete, and `gantry recipe check` reports the rule as failed (exit 1). Hooks print that line to stderr only (their stdout stays JSON) and, with at most 400 ms of regex time, stay inside their 1,500 ms stop (section 14). Guaranteed: a recipe regex cannot hold the indexer, a hook or the MCP server longer than these budgets; a recipe cannot make Gantry read a file outside the repository through a text rule or `sqlFiles`. Not guaranteed: that a slow but finishing regex is cheap (it can use its whole budget on every run), that `gantry recipe check` finds a pattern that is slow only on a file it did not read (`receiverDecl` templates are tried on the rule's `match` examples), or anything about the `regex` keys of ast-grep rules (they run in ast-grep's Rust engine in linear time and are not limited here).
- A table whose name is known only at run time (`FROM ${table}` where `table` is a parameter, or an expression built in code) is a `table` node named `{<expression text>}` with `data.reason` (`table name is a function parameter`, `table name is built at runtime`), edges `low`: visible in the index, never a guess, and not scored (section 13).
- `passthrough` lists the chain methods that return the same router (`get`, `use`, `basePath`, `register`), so `new Hono().basePath("/v1").get("/", h).post(h2)` is one router. A registration counts only if its receiver resolves to a router a rule declared (a variable, an import that resolves to one, a router a factory function returns with `call-return`, or a function parameter that something mounts or passes a router into with `param-flow`), so `map.get(k)` is never an endpoint.
- Helpers: `resolve-names`, `const-strings` and `mount-graph` always run, and so do `text-rules` (when the recipe has a text rule), `model-naming` and `method-classes` (when the recipe states `models` or `methods`); `call-return`, `param-flow`, `fs-routes` and `sql-text` run when listed. They are generic and built on the adapter context's resolver and parse results; framework names appear only in a recipe, except the file-naming conventions of `fs-routes.ts`.
- Output is the adapter nodes of section 9 (`ep:`, `mw:`, `route:` ids; the data fields are the ones listed there), sorted, and the same recipe and tree give the same output. A route or endpoint whose path cannot be read keeps the unreadable piece as `{name}`, gains `data.reason` (`path is a function parameter`, `path is not a literal or const string`) and has `low` confidence on its edges.
- Loading (`loadRecipe(root, source)`, `source` one of `{ layer: "main" }`, `{ layer: "working" }`, `{ ref }`): a file that is not JSON or fails the top-level schema gives no recipe and one error; a rule that fails its own schema is dropped with an error naming its id and the zod message, and the rest run. With no recipe file the recipe adapter does nothing and Gantry prints nothing about it: not on `init`, `index` or a hook (the built-in adapters still map what they know). For a recipe that is present but invalid, `gantry init` and `gantry index` print one stderr line per problem: `Gantry: recipe rule <id> skipped: <reason>`, or `Gantry: recipe .gantry/recipe.json ignored: <reason>` when the file is not JSON or fails the top-level schema. Hooks print neither.
- **A text rule needs no helper entry** (#367). A recipe with a `text` rule reads its files whether or not `text-rules` is in `helpers`; the rule is the request, so listing the helper is allowed and changes nothing. Reason: recipes that listed it and recipes that did not looked the same to `gantry recipe check`, but only the first produced tables, and an error would have rejected recipes the check accepted yesterday while the removal rejects none. `method-classes` and `model-naming` were never gated by `helpers`: a `read` or `write` emit with a `method` uses the recipe's `methods` lists, and `models` is read when present. `sql-text` is different in kind: listing it is the switch that turns on scanning every TypeScript file (there is no rule to stand for it), so it stays opt-in. `call-return`, `param-flow` and `fs-routes` also stay opt-in.
- `gantry recipe check` (section 10) validates a recipe and runs every rule's examples. Zero matches in the repository is a warning, never a failure. With `--nodes` it also lists the nodes the index makes from the recipe (section 10).

**Bundler aliases (`core/resolve/bundlerAliases.ts`).** Imports that go through an alias defined only in a bundler config resolve to their source files. For each workspace, the resolver reads `vite.config.{ts,mts,js,mjs,cjs}` and `webpack.config.{js,cjs,mjs,ts}` in the workspace directory (not in parent directories). A config is parsed to a syntax tree with `oxc-parser` and never imported, required or run, so a config with side effects does nothing. The alias table is `resolve.alias` of the exported object: `export default { ... }`, `export default defineConfig({ ... })`, `module.exports = { ... }`, or the object an exported arrow or function returns (also inside `defineConfig(...)`). Both the object form (`{ key: value }`) and Vite's array form (`[{ find, replacement }]`, `find` a string) are read. A value is accepted when it is a string literal; `path.resolve` or `path.join` of a base (`__dirname`, `import.meta.dirname`, `process.cwd()`, all taken as the workspace directory) and string literals; `fileURLToPath(new URL("<literal>", import.meta.url))`; or a template literal made only of those parts. In a Vite config a string literal starting with `/` is relative to the workspace directory; elsewhere it must already be absolute. A key matches the specifier or the specifier followed by `/` and a subpath; a trailing `$` in a key (webpack) means the exact specifier only. The readable aliases go to an `oxc-resolver` of that workspace that has no tsconfig and is asked first for a specifier an alias key matches, so an alias wins over tsconfig `paths` and `node_modules` as it does in the bundler; when it finds nothing, the usual resolver (tsconfig `paths`, `node_modules`) runs. Anything else is not read: a computed value or key, a spread, a regular-expression `find`, a variable, an array of targets, or an `alias` that is not an object or an array. Such an alias is recorded as unreadable, and it changes only what the unresolved list says: a specifier that stays unresolved and starts with an unreadable key (or, when the whole `alias` value is unreadable or the key is not a string, any bare specifier that stays unresolved in that workspace) is an `UnresolvedSpecifier` with `reason: "alias_not_static"` and `alias` set to that key, or to `*`. `IndexResult.unresolved` carries both fields. Aliases of other build tools (Rollup, esbuild, Babel, Jest `moduleNameMapper`) are not read.

**Built-in excludes:** `node_modules`, `dist`, `build`, `out`, `.next`, `.output`, `.turbo`, `.vercel`, `.wrangler`, `coverage`, `**/*.d.ts`, `**/*.gen.ts`, `**/routeTree.gen.ts`, nested worktrees, plus sensitive files `.env*`, `*.pem`, `*.key`, `*.p12`, `id_rsa*`, `.npmrc`, `credentials*`, `secrets*`, `*.tfvars`. Everything git ignores is excluded. Only `.ts .tsx .mts .cts` and `.go` are parsed. Go skip rules (#221): any file below a `vendor/` or `testdata/` folder or a dot folder is not indexed (the rules the Go tool applies); `_test.go` files are indexed and count as tests (`isTestPath`); a file whose header matches `^// Code generated .* DO NOT EDIT\.$` (multiline) is indexed with the file directive `generated` and the duplicate engine skips it, like `isGeneratedPath` files. The TypeScript built-in excludes above also apply to Go paths (a `build/` or `dist/` folder is skipped).

## 6. Stable IDs

- Workspace `ws:<repo>:<package name>` (e.g. `ws:acme/shop:@acme/ui`); root package `ws:<repo>:.`. A Go module (#221) is `ws:<repo>:<module path>` (e.g. `ws:acme/shop:example.com/shop/tools`); a repository with Go modules and no TypeScript has no `ws:<repo>:.`. The repo part is #214 (the spike behind it found the one id collision of two repos in one store, `ws:.`, which every repo has): a workspace id is built and parsed in `core/src/ids.ts` (`workspaceId`, `parseWorkspaceId`, `workspaceNameOfId`, `isRootWorkspaceId`).
- Every id carries the repo name (`GantryPaths.repo`, section 4) right after its prefix, so ids are the same on every machine and in CI. They are built and parsed only in `core/src/ids.ts` (`fileId`, `symId`, `routeId`, `endpointId`, `middlewareId`, `callId`, `tableId`, `parseId`, `pathOfFileId`, `pathOfSymId`, `nameOfSymId`, ...; the web app re-exports the same module as `explorer/web/src/ids.ts`). In the forms below `<repo>` is that name (it contains no `:`, but may contain `/`, as in `acme/shop`). `gantry node`, `gantry trace` and the MCP tools still accept the short forms a person types (a path, `path:line`, `file:<path>`, `sym:<path>#<name>`, `route:<ws>:<path>`, `table:<name>`) and resolve them against the current repo. A change of the repo name (for example a remote added later) changes every id; the next full index deletes the rows under the old name (`removeReposExcept`, section 9) and writes the new ones, so the store is not rebuilt and keeps its descriptions. The view-only `mwref:<package>:<name>` nodes of the endpoints view are not stored ids and carry no repo.
- File `file:<repo>:<repo-relative posix path>`
- Symbol `sym:<repo>:<path>#<name>`; class members `sym:<repo>:<path>#<Class>.<member>`; default export without a name `#default`; a second symbol with the same id in one file gets `~2`, `~3` by source order. Go (#221): a method is `#<Recv>.<name>` with the receiver's base type (`*` and type parameters stripped); a function declared in two build-constrained files (`listen.go`, `listen_unix.go`) has two ids, one per file, because the path is part of the id; `_` and `init` repeat within a package and are numbered `~2`, `~3` in source order, and the duplicate engine never compares them.
- Route `route:<repo>:<ws>:<path>` (`<ws>` is the workspace package name, the workspace id without `ws:<repo>:`; `<path>` is the TanStack route id, the string `createFileRoute` takes, such as `/posts/$postId` or `/_app/settings/`, and `__root__` for the root route); endpoint `ep:<repo>:<ws>:<METHOD> <path>` or `ep:<repo>:<ws>:rpc <procedure.path>` or `ep:<repo>:<ws>:fn <exportName>`; middleware `mw:<repo>:<ws>:<path pattern> <name>` (#45); table `table:<repo>:<name>`; unmatched client call `call:<repo>:<ws>:<label>` (#47; `<ws>` the caller's package, `<label>` what the call names: `rpc <path>`, `<METHOD> <path or URL>`, `<METHOD> <dynamic>`, `rpc <prefix>.*` for a sub-client alias, `useServerFn(<name>)`). In endpoint and middleware ids `<ws>` is a package name as for routes; for an HTTP route it is the package of the app at the top of the mount chain (the one serving the URL), for a server function the package of its file, for an oRPC procedure the package of the file of its root router (the router no other router nests; #46). `<procedure.path>` is the dotted key path from that root router. A table id is global: `<name>` is the SQL table name, and a second definition of the same name gets `~2` in file path order (#46). Adapter ids that repeat within a workspace get `~2`, `~3` in file path order, then source order.

**Function-like kinds** (get descriptions, duplicate checks): function, method, component, hook. A component is a PascalCase function returning JSX; a hook is a function named `use[A-Z]…`.
**Go kinds (#221; `lang/go/parse.ts`).** Only top-level declarations are symbols. `func` is `function`; a `func` with a receiver is `method`, named `<Recv>.<name>` after the receiver's base type; a `type` of a `struct_type` (or generic struct) is `class`, of an `interface_type` is `interface`, any other `type` spec or alias is `type`; every name of a `const` or `var` spec is `const` (the neutral kind set has no `var`). A spec lists its names in the grammar field `name`, which also holds the commas of `const a, b = 1, 2`, so only `identifier` nodes count. `exported` is an upper-case first letter. `signature` is the parameter and result text (`(key string) (string, bool)`; a method omits its receiver). `stmtCount` counts statement nodes in the body and `complexity` is 1 plus `if`, `for`, `case` clauses and `&&`/`||`. Display labels (`LanguageModule.kindLabels`): Go `class` is `struct`; `const` stays `const` for both `const` and `var` names, because the neutral kind does not tell them apart. Methods declared in the body of an in-repo interface are symbols too (#222): kind `method`, named `<Iface>.<Method>` (`sym:<repo>:<path>#Reader.Get`), `exported` by the method's first letter, `signature` as for any method, no body (`stmtCount` 0); an alias of an interface has none. Imports are kept with their path and optional alias; type references are not extracted.

**Go call edges (#222; `lang/go/resolve.ts`, `calls.ts`; syntax and local type inference, no Go toolchain).** The resolver builds a package index over the parsed `.go` files: per package path (the module path of the `go.mod` workspace holding the file plus the folder below it; an external test package `x_test` is a package of its own that nothing imports) the functions with their result types, the types with struct fields, embedded fields and interface method sets, the methods by receiver base type and the package-level vars; when two files declare one name (build-constrained files) the first path in sorted order wins. An import path inside a workspace maps to its package; the default import name is the target's `package` clause, never the last path element; an import outside the repo makes no edge, and dot and blank imports are ignored. Per top-level function or method, names are collected with their types with scopes flattened (the nearest preceding declaration wins; a declaration is visible after its own statement; function literals count as the function around them): receiver, parameters, named results, `var x T`, `x := T{}`, `&T{}`, `new(T)`, `make(T, ...)`, `append(s, ...)`, `x := F()`, `x, err := pkg.F()`, `x := y.M()` (declared result types), `x.(T)`, `s[i]`, struct field chains through embedding, aliases, and range variables over `[]T`, `[N]T`, `map[K]T` and named types of those. Edges are in the section 7 kinds, with no new kind: `calls` from the caller's symbol to the callee's at `high` confidence for a same-package call, a package-qualified call and a call of a method on a concrete type (declared on it or promoted through struct embedding); a call on a value of an interface type goes to the interface's method symbol `#<Iface>.<Method>` at `high` (the symbol of the interface that declares the method when it comes from an embedded in-repo interface). A site whose receiver type is unknown, a method of an external type (`http.ResponseWriter.Header()`), a function-valued field or local, a builtin and a conversion emit nothing; a call of a function by itself emits no edge. `extends` runs from a struct to each in-repo type it embeds (`high`). `implements` runs from a named in-repo, non-generic type that is not an interface to an in-repo, non-generic interface when its method names (value or pointer receiver, promoted ones included) cover the interface's method set, at `low` confidence: names only, no signatures; an interface that embeds one from outside the repo, or a constraint element, is skipped, and an interface with no method gets none. `evidence` is `path:line` of the call, embedded field or type declaration. Measured (V2 spike, `docs/spikes/v2-go-calls.md`) against go/packages truth by `evals/go/score-calls.ts`; the bars are in the fixtures section. Go imports are not stored as `imports` edges, and `resolveSpecifier` has nothing to resolve for Go. A Go module's file `contains` edges and `depends_on` edges between modules (a `require` naming another module of the repo; with a root `go.work`, only modules it lists with `use`) are stored on the requiring module's `go.mod` file row.

**Go fact sheets (#224).** `FactSheet.language` is the `label` of the symbol's language module (`TypeScript`, `Go`); the worker renders it as a `language:` line after `kind:` and the describer agent receives it in each item. For Go, `doc` is the `//` comment lines directly above the declaration, `returnType` is the result part of the stored signature (`(string, bool)`, `*Store`; null when the function returns nothing), and `callees` come from `calls` edges when the index has them. `contentKey` does not depend on the prompt text, only on `PROMPT_MAJOR`, so the prompt wording change of #224 keeps `p1`.

**Go `init` fact sheets (#372).** For a Go function named `init`, `FactSheet.runsWhen` is the fixed text `Runs once at startup, when its package is loaded.`, written by the host (`GO_INIT_RUNS_WHEN` in `factsheet.ts`) and never taken from the code. The field is absent for every other function. The worker renders it as a `runs:` line before the body, the describer's claim item carries it as `runs_when` (only when set), and `groundingNames` reads its words like the words of a doc comment, so a description of an `init` function may say that it runs at startup without any word being added to the word lists. The field is not part of `contentKey` and no stored row changes (`SCHEMA_VERSION` stays 12).

**contentKey** = `<exactHash>:<PROMPT_MAJOR>`; `PROMPT_MAJOR` starts at `p1`.

## 8. Description schema and checks

JSON Schema (used for `--json-schema`, MCP submit validation and tests): `behavior` string, ≤ 25 words and ≤ 200 chars; `searchTerms` 1–6 strings, each ≤ 30 chars; `nameFits` boolean; `suggestedName` required iff `nameFits` is false, must match `^[A-Za-z_$][\w$]*$`.
Hard caps come first and are O(1), before any regex or normalisation: raw `behavior` ≤ 400 chars, each search term ≤ 60 chars, `suggestedName` ≤ 80 chars, ≤ 6 terms; over a cap fails with reason `length` and is never repaired. So no scanner ever sees more than 400 characters of `behavior`, and every regex is linear (no nested quantifiers).
The validator accepts the **shape of a description** instead of banning phrases (a phrase list cannot be both tight and precise; the independent review of #22 failed the first list on injection bypasses and 18–23% false rejects). Failure reasons: `schema`, `length`, `shape`, `identifier`, `injection`, `secret`. Checks run per function, in order:

1. **Hard caps** (above), then **schema** (types, `suggestedName` rule).
2. **Secret filter** (`secret`) on `behavior`, each term, the fields joined, and `suggestedName`: vendor key shapes (AWS, GitHub, GitLab, Slack, Stripe, OpenAI/Anthropic, Google, npm, Hugging Face, SendGrid, Twilio, Mailgun, Shopify, Vercel, DigitalOcean, PyPI, Linear, Notion, Telegram, Discord, Sentry, Square, Azure, `AGE-SECRET-KEY-1…`), hex runs ≥ 32, private keys, JWTs, `scheme://user:password@host` and `scheme://:password@host` with any scheme, `Authorization: Basic …`, `Bearer` tokens, `Set-Cookie`/`session=` values ≥ 16 chars, string literals assigned to a **credential name** (below), unquoted `NAME=value` and `name: value`, high-entropy tokens and base64-wrapped keys. A second pass removes hyphens between alphanumerics and joins adjacent tokens, so keys split by hyphens, spaces or across fields are found. Details name rules, never matched text.
   Credential name = an identifier or quoted key whose word parts (camelCase, snake_case, kebab-case, dots) include `password`, `passwd`, `pwd`, `pass`, `secret`, `token`, `credential(s)`, `apikey`, `passphrase`, or `key` **only** next to `api`, `secret`, `access`, `private`, `signing`, `sign`, `auth`, `encryption`, `master` or `license` (so `key`, `sortKey`, `cacheKey`, `STYLE_KEY`, `hotkey`, `monkey` are not credential names); a name whose last word describes the value (`tokenType`, `passwordLabel`) is not one either. Assignment forms are `=`, `:`, the Go short declaration `:=` and a Go declaration with a type between the name and `=` (#224). The value assigned to a credential name is redacted and flagged when it is a plain string literal of ≥ 4 chars in any letter case, or two or more literals joined with `+` (every half); it is left alone when it is empty or shorter, a template literal with `${…}`, an identifier or member expression (`env.KEY`, `process.env.X`), a regular expression, an option keyword (`same-origin`) or a dotted message key. Unquoted: `UPPER_SNAKE=value` (≥ 4 chars), and `name=value` or `name: value` when the value holds a digit and a letter. Description side: any token copied from a string-literal value assigned to a credential name in the fact sheet is rejected as `secret` even when it is an English word.
3. **Length**: ≤ 25 words and ≤ 200 chars for `behavior` (truncation repair below), 1–6 terms of ≤ 30 chars.
4. **Shape of `behavior`** (`shape`), after NFKC folding: (a) only ASCII letters, digits, space and `, . ; ' - _ / ( ) < > [ ] $ : #` (no backticks, `* ~ ! ? = { } | \ " @ % ^ &`, no non-ASCII, no line breaks); (b) one sentence: no `. ` followed by more text, no leading label (`WORD:`), no parenthetical aside longer than 6 words, no run of three single letters, no comma without a following space; (c) the first word is a third-person form (`-s`, `-es`, `-ies`) whose base form is an English or programming word (dictionary below), so no hand list gates it (a list of about 700 common verbs stays only as a fast path), optionally after one adverb (`Strictly parses`) or as `prefix-verb` (`Deep-copies`); `Pretends` is banned outright; base forms, vocatives (`Claude,`), pronoun and modal starts and `Safe to …` fail structurally; (d) no second-person pronoun, no deontic or addressing word (`must`, `should`, `ought`, `shall`, `please`, `todo`, `fixme`, `remember`, `need to`, `needs to be`, `has to`, `have to`, `be sure`, `make sure`, `don't`), and no first-person pronoun (`we`, `our`, `me`, `us`, `i`), matched case-sensitively as written so `US dollars` and `I/O` pass; (e) **no imperative clause** (problem `imperative-clause`): a base-form verb from a committed lexicon of about 220 action verbs (`delete remove skip ignore disable bypass turn run execute install download upload send print reveal leak commit push pull merge use replace add drop kill stop avoid forget disregard override set write edit modify change update mark trust approve rename move copy paste open close call invoke import export fetch clone checkout reset enable comment exfiltrate …`) that starts a clause is rejected: right after `,` `;` `:` `(` or a dash, or after `then`, `and`, `or`, `but`, `so`, `just`, `now`, `also`, `first`, `next`, `finally`, `please`, `never`, `always`, `not`, `do`, `don't` (one adverb may stand between: `then quietly delete`), and a clause that opens with `do` is rejected whatever its verb. Verbs that are also nouns (`update`, `call`, `set`, `commit`, `push`, `run`, `skip`, …) count only when followed by a determiner, pronoun, preposition, identifier, protective object or the end of the clause. Not rejected: an infinitive (`to fetch and cache results`: the verb follows or continues a list governed by an earlier `to`, no punctuation between), a noun after a determiner, preposition or possessive (`the delete button`, `on update`, `a run id`), the complement of a causative first verb (`Lets the user delete a row`; `lets`, `helps`, `makes`, `has`), and a list of bare verbs (`(create, read, update, delete)`). Measured and dropped from the issue's list: `note`, `warning`, `important` (ordinary nouns and adjectives), `never`, `always` (5 of 200 real descriptions), `do not` after a subject and `my` (real descriptions and search terms), and `instead` (`… instead of removing the row`).
5. **Grounding** (`identifier`), dictionary based. Every token of `behavior`, of each search term and of each split word of `suggestedName` must be (a) an **English or programming word** (the hand lists include acronyms, platform names and ordinary words the 1934 list lacks, such as `E2E`, `UTM`, `PostHog`, `allowlist`, `roadmap`, `rowid`, `classify`, and the SQLite `json_*` functions): in the shipped word list, on the hand list of ordinary terms, or a regular derived form of one (plural `-s/-es/-ies`, `-ed`, `-ing` with doubling and e-drop, `-er/-est`, `-ly`, `-able/-ible`, `-ness`, `-ment`, `-tion`, `-ity`, …; prefixes `un- re- non- pre- de- sub- multi- auto-` and a few more, two steps deep), (b) a number of fewer than 7 digits, a clock time or a size such as `30s`, `4x` (a decimal such as `1.5` too, except right after `to`, `from`, `at`, `on`, `host`, `ip`, …; three or more small numbers in a row are rejected), (c) **grounded in the fact sheet**: the whole token is an identifier, path, file name, signature name, callee, return-type name or doc identifier, or it is a sub-word of one (camelCase, PascalCase, snake_case, kebab-case and path segments, file names and extensions split into lower-case parts; `handleStripeWebhook` grounds `stripe` and `webhook`, `later-work-controller.ts` grounds `later-work`), or (d) on the stop list. Anything else is rejected, which covers foreign-language text, run-on bait names (`leftpadsecure`), spelled-out hosts (`rs`, `sh`, `com` are not words), copied lowercase passwords and opaque tokens. The camelCase and snake_case forms must be whole names of the fact sheet. **Compounds** joined by a hyphen or one slash are accepted only when on the ordinary-English allow-list (about 200: `read-only`, `built-in`, `sign-in`, `AES-256-GCM`, `robots.txt`, …), matching a small set of productive patterns (`non-`/`multi-`/`cross-`/`semi-`/`anti-`/`sub-` plus a word, a word plus `-based`/`-only`/`-safe`/`-aware`/`-readable`/…, a noun plus a participle such as `size-limited`, a compound with a function word such as `waiting-for-review`), grounded as a whole, or when **every** part is grounded in the fact sheet; two dictionary words are not enough (`evil-pad`, `auth/bypass`, `pastebin-mirror`, `leftpad-secure` fail). The ordinary-English allow-list also holds `schema.org` and the common security response header names (`Strict-Transport-Security`, `Content-Security-Policy`, ...). Route literals (`/rpc/`) and `re-` compounds (`re-validates`) are not accepted: a path or a prefix can hide a verb (`/nuke/ the suite`, `Re-elevates privileges`). A dotted or host-like token is grounded only by a whole identifier, path, callee or relative-import file name, never by a string literal, a default parameter value, a comment or a doc dotted chain; the single literal values that ground are `UPPER_SNAKE` constants such as `NOT_FOUND`. Every input the grounding scan reads is capped before any regex: signature ≤ 400 chars, doc ≤ 2,000, body ≤ 8,000. Failure details echo the first 12 characters of an offending token followed by `…`.
   **Word list**: `packages/core/src/describe/wordlist.data.ts`, generated by `scripts/build-wordlist.ts` from `/usr/share/dict/words` (Webster's Second International, 234,936 entries, 1934; its README says "The 1934 copyright has lapsed", so the list is public domain): lower-cased alphabetic words of 4–20 letters, 232,843 words, stored as a Bloom filter (15 bits per word, 10 hashes, 0.07% measured false positives, 582 KB of base64 in a TS module bundled by tsup, no file I/O, decoded lazily on first use). Two- and three-letter words and about 1,700 programming and web terms the 1934 list lacks (`async`, `callback`, `middleware`, `webhook`, `oauth`, `regex`, `json`, `email`, `database`, `timeout`, …) are hand lists in `wordlist.ts`. Adding a word means adding it to that list, with a test row that needs it.
   Search terms: 1–4 words each (more is a benign case: the term is stripped and the repair `search-terms-stripped` reported), all words grounded as above, no addressing words, no speech act or agent subject (check 6), no secret value, none starting with `prefer`, `avoid`, `please` or a shell or package-manager command (`npm`, `pnpm`, `yarn`, `npx`, `pip`, `curl`, `wget`, `sudo`, `chmod`; `curl snippet` style two-word names pass), no single-word `disregard`/`forget`. The imperative rule applies to a term only when it has ≥ 3 words and an always-flagged verb is followed (through fillers `the all any previous …`) by a protective object (`tests test auth authentication authorization check(s) validation security secret(s) credential(s) key(s) token(s) env instruction(s) rule(s) hook(s) ci lint guard(s) permission(s) …`), when a 2-word term is a destructive verb (`delete remove disable bypass ignore disregard override wipe erase drop kill`) plus `tests/auth/checks/validation/security/rules/…`, or when the terms joined together form such a phrase across term boundaries (`delete` + `tests`; a lone destructive-verb term next to a term naming protective code); `skip weekends` and `run tests` pass. If **any** term is rejected for an instruction-like reason (imperative, addressee, modal, ungrounded token, secret) the whole description is rejected with that term's reason; nothing instruction-like is stripped, because the remainder could mislead. `suggestedName`: every split word grounded, no `you/your/we/our/must/ought/shall/please/remember`, no name that starts with an always-flagged verb plus a protective object (`skipTests`, `deleteAuthMiddleware`, `removeTheAuthCheck`, `ignorePreviousInstructions`), no speech act or agent subject (`agentsDeleteTests`).
6. **Injection filter**, a small high-precision set kept for defence in depth, plus two rule families. Patterns: `ignore/disregard/forget/override/bypass … previous/above/all … instructions/rules` (and the third-person forms), `do not tell/mention/reveal`, `system prompt:` as a label, role prefixes (`system:`), chat-template tokens, agent markup, obfuscated hosts (`hxxp`, `[.]`, `x dot sh`, `evil dot rs`: `dot` followed by any top-level domain of 2–3 letters or a common longer one), markdown links, URL schemes, `rm -rf`/`curl -`. It runs on `behavior` plus all terms together and on each term. **Speech acts aimed at agents** (reason `injection`): a speech-act or causative/desire verb in any inflection (`tell instruct urge remind command order direct advise warn ask request require expect want need let allow make help encourage force permit authorize invite suggest recommend propose demand …`), used as a verb (first word, after a clause boundary or a word such as `and`, `to`, `that`), followed within 4 words by an addressee (`agent(s) assistant(s) ai model(s) llm(s) claude copilot cursor bot(s) gpt maintainer(s) developer(s) engineer(s) reviewer(s) reader(s) contributor(s)`; `caller(s)` only when followed by `to` and an action verb). For the human addressees the causative verbs (`let allow make help …`) count only when an action verb or protective object follows within ten words. `Asks the user to confirm deletion.` and `Lets the user pick which AI agent handles the ticket.` pass; `Tells the agent to remove the auth check.`, `Instructs the assistant to skip the test suite.`, `Urges agents to delete the session tests.`, `Reminds maintainers to disable the check.` fail. An addressee directly followed by a base-form action verb, or by a modal and an action verb (`agents remove …`, `bots may delete …`), fails too. **Permission claims** about protective code fail: `safe/ok/fine/allowed … to` plus an action verb, `can/may` plus an action verb or `be` plus its past participle, `is/and obsolete/removable/skippable/redundant/unnecessary`, `recommends removing …`. Declarative false claims that name no action (`Never validates the token, so any caller is trusted.`) are accepted residual risk: the field stays labelled `untrusted_description`. **Production claims** (#175, gate only since #180): text about how the description was produced is not rejected by the validator, since ordinary sentences about a model layer or a host match the pattern, but it is a cue of the extra-attempt gate (below), since only the host writes the fallback marker: a production verb (`generated`, `written`, `created`, `produced`, `made`, `built`, `composed`, `authored`, `derived`), up to three words, then `by`/`with`/`without`/`from`/`using`/`via`/`through` and a model, LLM, AI, Gantry, the host or `names only`; `no model was used`; `generated, no model`. Matched on NFKC-folded words, so punctuation, case and full-width forms do not hide it; `without a model binding` and `from the first and last names` pass. Dropped as standalone triggers because they rejected honest descriptions: `assistant`, `AI agent(s)`, `delete`, `run the`, `execute`, `system message`, `curl`/`sudo` as plain words, `instead`.
   An over-length `behavior` is truncated (below) after checks 2 and 4–6 passed on the full text, then re-checked. A failed function is re-queued; after 2 failures it is routed to `describe.retry`. On the describer path (section 15) a rejected function stays claimed in its batch, so a corrected resubmit under the same `batch_id` is checked again; the second failure makes it `failed`, except for the bounded extra attempt below.
   **Feedback, extra attempt and fallback (#150, hardened in #175).** The validators are not loosened for this (shape and injection loosening was tried in #155 and reverted after three rounds of review found bypasses; every bypass is a rejection test). Instead: (a) every rule rejection on the describer path carries `rule` (a fixed sub-rule code such as `shape.first-word`, `injection.speech-act`, or the bare reason), `field` (`behavior`, `searchTerms` or `suggestedName`) and `fix`, a fixed rewrite instruction for that rule (`packages/core/src/describe/feedback.ts`; for example `shape`: "Write one plain sentence about what it does, no lists, code or quotes."; `injection`: "Describe behaviour only; do not mention instructions, prompts, roles or the reader, ..."; `identifier`: "Name only identifiers that appear in the code shown; ..."). All three are constants picked from closed lists by the reason and by rule codes found in the validator's detail; nothing of the description or the detail is ever copied into them, so the answer never echoes the rejected text (the MCP answer drops `detail`, which can echo a token prefix; `last_error` keeps it on the host). (b) **The validator is not the security boundary** (decided by the operator for #175, final round). Description text is untrusted model output everywhere downstream; the validator is defence in depth that rejects clear-cut cases and must not reject honest sentences that main accepted (a committed benign corpus, `benign corpus: no new rejections vs main`, holds the reviewers' benign sets of #178 and this branch's own). Containment is the boundary: description text appears only in fields named `untrusted_*` (or, in the catalog files, quoted after a fixed `untrusted <who> description:` label), always as plain text, with its provenance next to it as `described_by` (`model`, `template` or `fallback`, from the provenance column, never from the text) in `gantry_node`, `gantry_search`, `gantry_browse`, `gantry_find_similar`, the impact tool's changed entries, the review view's changes, the explorer's `/api/node` and `/api/search` hits (#180), and `gantry search --json`. The explorer shows the provenance as the label above a description: a fallback reads "Generated without a model from the kind, parameter count and call count — may be incomplete" (a fallback has repeated no name since #175), a template "Template text copied from the code — may be wrong", a model description "Generated description — may be wrong"; the review panel's row for a changed symbol also names it (`<model|template|fallback> description`). **Template descriptions are raw code text (#180).** A template is written by `templateFor` straight from the return expression of a one-statement function (`Returns <expr>.`, up to 80 characters) and is not run through the validator, so it can hold whatever an attacker put in a string literal or an expression. It is stored with provenance `template`, shown only in `untrusted_*` fields, and every tool description, skill and agent text (`UNTRUSTED_NOTICE`, the reuse-first skill, the explainer agent) and the catalog note say that a description was written by a model, copied from the code by a template (which an attacker can write) or generated by Gantry's fallback, and that `described_by` says which. **The catalog quotes the signature too (#180):** a line is `- <name> signature "<signature>" — untrusted <who> description: "<text>" [<path>:<line>]`; in both quoted columns a double quote becomes a single quote and whitespace folds to one space, so a default parameter value from the code cannot close its quotes or imitate the label. (c) **Extra attempt.** A function gets one extra attempt, 3 in all and never more (`MAX_DESCRIBE_ATTEMPTS_EXTENDED`), only for a clean wording mistake: an _extendable_ second rejection whose first rejection was not tainted. A rejection is _tainted_ (`rejectionTainted`) when its reason is anything but `shape` or `identifier` (`schema` and `length` too), when it is a `shape` rejection for `addressing`, `imperative-clause`, `multiple-sentences`, `label` or `spaced-letters`, or when `instructionSignal` finds anything in the rejected submission; _extendable_ (`extendableRejection`) means `shape` or `identifier` and not tainted. The gate is deliberately broad, because a false positive costs only the extra try, never a rejection, and it taints whenever it is unsure. `instructionSignal` reads every submitted value whatever its type or position (strings under `behavior` at any depth as behavior text; every other string, array item, seventh or later term and unknown key as a term and a name, also split into its identifier words; bounded at 64 strings, 4,000 characters, depth 6) and taints on: the credential scanner and credential values copied from the code (whole or a piece of 6+ characters); the injection filter, speech acts, addressing words and the production-claim rule on all fields together; every term and name rule other than grounding and length; terms that instruct together; and the gate cues of `clauses.ts`, which live only in the gate: a clause of `behavior` (split at every punctuation mark and dash, commas and quotes included, after NFKC folding; one leading adverb skipped; the first clause too) that opens with anything but a closed-class word, an -s form or a real participle (so a base-form or unknown verb, and a number, count as orders); a participle is a word in -ed or -ing whose stem is itself a word (`sorted`, `creating`, `running`), so base forms that only end that way (`shred`, `embed`, `speed`, `string`, `feed`) are orders (#180); a part that follows a conjunction (`and`, `or`, `nor`, `but`, `yet`, `so`, `then`, `else`) is read the same way when it opens with an always-flagged action verb, or with a bare word followed by an object marker or an ambiguous action verb followed by something other than `of`, `and`, `for`, `in` and the like (`or else delete tests`, `and shred all tests`; a plain coordination such as "the name and email" is not a cue); a modal or `please`; an approval, status or provenance word anywhere (`approv*`, `merg*`, `ship*`, `review*`, `LGTM`, `safe*`, `trust*`, `verified`, `vetted`, `ready`, `cleared`, `pass*`, `looks good`, `sanction*`, `accept*`, `audit*`, `permit*`, `allow*`, `authori[sz]*`, `certif*`, `checked`, `green`, `model`, `fallback`, `generated`, …); angle brackets or any character outside printable ASCII; an addressee, AI or indefinite person; status and permission claims, including `no further|more|other|additional|extra <word>`; a secret-like value (a run of 16 or more hex digits, or a token of 16 or more letters, digits and `_+/=-` that holds a digit, #180); and the fallback marker (below). The marker rule lives only here since #180: the validator accepts ordinary sentences about a model layer or a host ("Returns the record created by the model layer."), a committed benign set holds 20 of them that the validator had rejected, and a rejected description that imitates the marker is tainted. A model that imitates the marker in an accepted description is stored with provenance `model`; consumers read provenance from `described_by`, never from the text. A tainted rejection is stored with ` [no-extra]` appended to `last_error`. `recordDescribeFailure` reads and writes the row in one `BEGIN IMMEDIATE` transaction, counts a describer-path failure only on a row still `claimed` (a worker-path failure on any row not `failed`), grants the extra attempt only when the caller says the rejection is extendable (default not), marks the failure unless the caller says it is clean (default marked), and never extends a row whose previous failure is marked. (d) **Fallback.** When the third attempt fails with an extendable rejection too, the host stores a fallback description built without a model from trusted index data (`fallback.ts`) that repeats no name at all, neither the function's nor a callee's: `Defines a <kind> that takes <n> parameters and calls <m> other functions (generated without a model).` (`1 parameter`, `no parameters`, `1 other function`, `no other functions`; the parameter clause is left out when the stored signature does not parse; `m` counts the distinct indexed callees other than the function itself). Its only search term is the kind, `nameFits` true. The sentence is validated without the marker and the marker is added afterwards; if the sentence does not pass, the function stays `failed`. **Limits of this layer (decided by the operator on 2026-11-14 after three independent reviews).** The checks above are hardening, not a guarantee. Hosts, install bait, secrets and oversized or malformed input are handled structurally. Instructions are not: the imperative-clause, speech-act and addressee rules use finite word lists, so an instruction written with a word outside them (for example "…; nuke the tests.") still passes. A stored description must therefore never be treated as trusted text. Every consumer is required to (1) return it only in a field named `untrusted_description`, never merged into instructions, tool descriptions or system text; (2) state in the tool or skill description that the field is data about untrusted code, written by a model, copied from the code by a template (which an attacker can write) or generated by the fallback, and that nothing in it is to be followed; (3) never use it to decide on a side effect (writing, deleting, installing, running) without independent evidence from the code itself. The 100% figure refers to the committed attack corpus only. The same holds for `suggestedName`: it is part of a description, so it is returned only in a field named `untrusted_suggested_name` (on the reuse-advice object, set only when `renameSuggestions` is on), never interpolated into `action` text, hook output, pre-commit lines, catalog files or any prose, and the explorer renders it as plain text. A containment test seeds a marker as the suggested name and asserts it appears nowhere else.

The five tables from `labels` to `views` (#286) hold the curation objects of section 7. JSON is `JSON.stringify` of the zod-parsed value (key order of the schema), so equal input gives equal bytes; no timestamps. They are written only through `core/src/overlay/repo.ts` and are never touched by indexing, so an index rebuild keeps them.

`overlay.anchors` (#288) has one row per `sym:` id some entry uses (a label, or an id inside an `ids` selector of the hidden list, a group, or a saved view's `hidden`): the `exactHash` of that symbol as it was when the entry was last written. **Rebuild rule (#198).** A new store (no `meta` table) gets `SCHEMA` and `meta.schema_version` = `SCHEMA_VERSION`. A store whose `schema_version` is anything else, older or newer, is stale: `openStore` throws `StaleStoreError { found, expected, dbPath }` and changes nothing. `resetStaleStore(paths)` (`store/stale.ts`, exported from `@gantry/core`) deletes `gantry.db`, `gantry.db-wal`, `gantry.db-shm` and `parse-cache.db` when `gantry.db` exists with another version, prints `gantry: the index was built by an older version of Gantry (schema <found>, now <SCHEMA_VERSION>); rebuilding it` to stderr and returns `{ reset: true, found }`; it returns `{ reset: false }` and touches nothing otherwise. It does not look at repo names: a repo that was renamed or left the workspace file is handled by the next full main index (`removeReposExcept`, above), which keeps the rest of the store. Every non-hook entry point that opens the store calls it first (`init`, `index`, `embed`, `heal`, `map`, the lookups `search`, `node` and `trace`, `review`, `backlog`, `usage`, `describe --staged`, `hooks install` and `uninstall`, `uninstall`, the MCP server and the explorer server) and then goes on as on a repository with no index: `init` and `index` build it, the MCP lazy refresh and the lookups run a full main index through `heal`, `map` runs `rebuildIndex` (a heal, or a plain full main index where there is no `HEAD`; fails open with a note on stderr), and `backlog` and `usage` report that nothing is indexed. Hooks never reset or rebuild (section 14). Descriptions, embeddings and overviews go with the old store; dismissals and layouts live in `overlay.db` and stay; `/gantry:sync` re-describes.

Any change that makes a full re-index necessary bumps `SCHEMA_VERSION` in the same PR: a schema change, or a change to what the extractor, an adapter or the resolver write for unchanged files (incremental indexing only rewrites changed files, so an older store would keep the old output for every file nobody touched).

Effective view = working rows override main rows for the same file id; a working `files` row with `deleted=1` hides the main file. `adapter_nodes` follow the rule of `symbols`: a node belongs to its `file_id`, `replaceFile` replaces a file's symbols, edges and adapter nodes together, and the effective view takes a node from the layer chosen for its file. WAL mode; writers take an exclusive lock via `BEGIN IMMEDIATE` with a 5 s busy timeout.
Backlog priority: exported functions and route/entry files 0, other exported 1, local 2.

**Adapter framework (#45, `core/src/adapters/`).** `framework.ts` defines `Adapter<F> { id, languages?, appliesTo(ws), mayMatch?(file), includeTests?, extract?(ctx), link?(ctx) }` (`languages` is the files an adapter reads, `["typescript"]` by default; the recipe adapter lists `["typescript", "go"]` (#368), and `resolver.targetAt` and `resolver.typeNameAt` give a Go adapter the function a call or a name refers to and the type of an expression), `AdapterNode` (an `AdapterNodeRecord` with `kind: route | endpoint | middleware | table | procedure` and `ws` a workspace id) and `runAdapterList(ctx, adapters)`; `adapters/index.ts` registers `ADAPTERS` (in run order: the recipe adapter (#203), TanStack Router routes, TanStack Start server functions, Hono, oRPC, Drizzle, client calls (#47), which is last so its `link` sees every endpoint) and `runAdapters(ctx)`. `extract` runs once per file of a workspace the adapter applies to (test files skipped unless `includeTests`) and returns nodes, edges and adapter-private `facts`; `extract` gets `{ fileId, path, ws, source, parsed, resolver, program() }` (`program()` is the file's oxc statements, parsed once per run and shared). `link` runs once per run with every extracted file's facts, the nodes all adapters returned so far, the resolver and `file(id)` for any read file; it is where cross-file work happens (Hono mounts, loader to server function, and later oRPC nesting, Drizzle reads and writes, client-call matching). The indexer calls `runAdapters` over the whole read set on every run (main and working, full or targeted) and stores each node and edge with the file it names, replaced per file like symbols; a file whose adapter output changed because of another file is rewritten like an importer whose edges changed. Output is sorted (nodes by id; edges by file, src, dst, kind); a repeated node id or (src, dst, kind) edge keeps the first. **The recipe adapter (#203, `adapters/recipe.ts`)** is registered first. It does nothing without a recipe (section 5). With one, `extract` runs the rules that apply to each file (the rule's `when.dependency` and `files`) and `link` runs the helpers across files (mounts and base paths composed into full paths, file-system routes, factory returns, router arguments), then writes the endpoint, middleware and route nodes described below, with their `handles`, `serves` and `contains` edges. **Data access (#247, `recipe/data-access.ts`).** The same `link` also writes the `table` nodes and the `reads` / `writes` edges a recipe describes (section 5): `table` emits, text rules and `CREATE TABLE` in SQL text declare tables (`table:<repo>:<name>`; two bindings with the same name get `~2` as before, any other declaration of a name already declared is the same table); `read` and `write` emits and SQL text give an edge from the code holding the access (its symbol, or the file for module-level code) to the table. As for Drizzle below, `count` is the number of accesses, `evidence` one `path:line` per access line (the line of the method name), confidence `high` when the table was resolved through a binding, a model or a declared name and `low` when only an import's name matched or several tables fit the model. SQL text only reaches tables that are declared somewhere (a `CREATE TABLE` in a string or a `.sql` file, a `table` emit or a text rule): undeclared names such as catalogs are skipped. A name known only at run time is a `low` edge to a table node `{<expression>}` with `data.reason`, never a guess. For a recipe with no data-access rule, `sql` or text rule, nothing changes; no ORM is built in beyond the Drizzle adapter below. Their `data.adapter` is the label the rule's emit names, so a Hono recipe writes `"hono"` and the scorer, the client matcher and oRPC read the nodes as before; route nodes carry no `adapter`. A node with an unreadable path piece also has `data.reason`. On `fixtures/pnpm-turbo` and `fixtures/adapters` the committed recipes give byte-identical nodes, data and edges to the TanStack Router and Hono adapters (`recipe/parity.test.ts` runs the recipe adapter alone against them) and, with their Drizzle rules (#247), to the Drizzle adapter (`recipe/data-access.test.ts`: the same table nodes, data in the same key order, and the same `reads` / `writes` edges with count, evidence and confidence). The TanStack Router and Hono adapters stay registered next to it until the recipes that replace them are measured; a node two adapters both write (same id) is stored once, the first in run order (the recipe), and `link` contexts see each node once. Which adapters run can be set for a test with `IndexOptions.adapters`.

Adapters apply by dependency: TanStack Start to workspaces depending on `@tanstack/react-start`, `@tanstack/solid-start` or `@tanstack/start`; Hono to workspaces depending on `hono`; oRPC to workspaces depending on `@orpc/server`; Drizzle tables to workspaces depending on `drizzle-orm`, and Drizzle usage to those and to workspaces that directly depend on one of them (#46). `handles` points at the code that holds the handler: a named handler's symbol (followed through imports), and for an inline handler the symbol whose body contains it (for a server function, its `const`), or the file for module-level code, because that is where the call graph attributes the handler's calls (#45 changed this from a synthesized `sym:<path>#<name>.handler` id, which would name no node). A route's `requests` edge to a server function is `high` when the call resolves to the server function's symbol (or a server function of the route file), `low` when an unresolved import matches one server function's export name in the workspace. Hono middleware `serves` every endpoint of its own app and the apps mounted below it whose path its pattern (`*`, `/p/*`, exact, `:param`) matches; registration order is not modelled. **oRPC and Drizzle (#46).** oRPC procedures are `<builder>...handler(fn)` chains, where a builder is `os` from `@orpc/server`, `implement(contract)`, or a top-level `const` chained on or aliasing a builder (followed across files); routers are object literals (nested, spread, returned by a router factory of the same file), `<builder>.router({...})` and `os.lazy(() => import(...))` / `lazy(...)` (the module's default export), followed through imports. Each procedure reachable from a root router becomes `ep:<ws>:rpc <path>` (kind `endpoint`), stored with the file that defines the procedure, with `handles` to the code holding its handler (the rule above: for an inline handler in a router object, the router's `const`). A Hono registration whose callback calls `.handle(...)` on an `RPCHandler`/`OpenAPIHandler` gives the served router's procedures `mountedAt`. Drizzle `reads` / `writes` edges go from the code holding the call (symbol, or the file for module-level code) to `table:<name>`: `reads` for `.from(T)` and `.leftJoin|rightJoin|innerJoin|fullJoin(T)` on a call chain, `$count(T)` and `.query.<t>.findMany|findFirst` (also `_query`; `<t>` matched to a table export name), `writes` for `.insert|update|delete(T)`; `T` is a table binding, a namespace member (`schema.T`) or an `alias(T, ...)`. `count` is the number of calls, `evidence` one `path:line` per call line. Confidence is `high` when the binding resolves to the table's export (or the query key names exactly one table), `low` when the import does not resolve and only the export name matches. Raw SQL is not read.

**Client calls (#47, `adapters/clients.ts`).** Applies to app workspaces and to workspaces depending on `@orpc/client`, an `@orpc/*-query` package, TanStack Start, `hono`, `ky` or `axios`. `requests` edges go from the code holding the call (symbol, or the file for module-level code) to the endpoint, stored with the caller's file, `count` the calls and `evidence` one `path:line` per call line:

**Evidence cap (#47).** The resolver keeps up to 20 distinct evidence strings per edge (`EVIDENCE_CAP`, was 3): `trace` decides by evidence line which inline handler a call of a shared router `const` belongs to, and a router often calls one helper from many handlers. A store indexed before #47 keeps 3 until each file is re-indexed.

**Trace (#47, `core/src/trace.ts`).** `trace(store, target, { direction?, maxNodes = 2000, maxDepth = 6 }) → { target, direction, chain: { id, kind, label, via, depth, from?, confidence? }[], edges, gaps, omitted, truncated } | null`. `target` is a route, endpoint, table, middleware, symbol or file id, a route id or URL path (`/posts/$postId`), an endpoint label (`GET /posts/:id`, `rpc posts.list`), a table name, a file path or `path:line` (`resolveTraceTarget`; null when nothing matches). `direction` defaults to `up` for a table and `down` otherwise. Down: route `serves` its component and its file's `Route` const (which holds the loader and an inline component; `via: "serves"`) → `renders` / `calls` / `uses_hook` → `requests` endpoint → `handles` handler → `calls` → `reads` / `writes` table; `requests` (from a route too) and `handles` start a new budget of `maxDepth` hops of `calls` / `renders` / `uses_hook`. Up: the same edges backwards (`serves` only from routes, so middleware is not walked), ending at routes. **Inline handlers:** an endpoint with `data.handlerSpan` `handles` the code enclosing its handler, which also holds its siblings' calls (an oRPC router object, a function registering several Hono routes). From such a handler only the outgoing `calls` / `requests` / `reads` / `writes` edges with an evidence line inside one of the spans of the endpoints that reached it are followed; going up, a handler reaches such an endpoint only through an edge with an evidence line inside that endpoint's span. An edge with `EVIDENCE_CAP` lines, fewer than its count, and none inside is followed and reported (the dropped lines may be inside). Node ids are unchanged. The walk is breadth-first in sorted edge order, visits each node once (cycles are common) and at most `maxNodes` nodes (`truncated`). `chain` keeps the start and the nodes on a path to an endpoint or table (down) or to an endpoint or route (up), sorted by depth then id, each with the edge kind it was reached by (`via`) and its parent (`from`); `omitted` counts the other visited nodes; `confidence: "low"` marks a step reached by a low edge; `edges` are the traversed edges between chain nodes. `gaps` (sorted: unmatched client calls of visited code, endpoints without a handler or (down) reaching no table, (up) endpoints no client call requests, incomplete span checks, the node budget, then one line counting the nodes where the hop limit stopped the walk). Read-only and deterministic.

Search, browse and node tool details (#28). `gantry_search` runs hybrid search: keyword FTS over name tokens, suggested name, path, behavior and search terms (top 50) fused with the nearest description vectors (top 50, query embedded with the `query` prefix) by reciprocal rank fusion (k = 60), where only vector hits with a cosine similarity of at least 0.5 to the query are fused (`VECTOR_MIN_COSINE`; the nearest vectors of a query that matches nothing are noise and must not outrank a keyword match), then exported ×1.2 and exact name ×2; with no cached model or no vectors it is keywords only, and the model is never downloaded by a search. Each hit is `{ id, repo, name, kind, lang, path, line, signature, score, untrusted_description, described_by? }` (`described_by`: `model`, `template` (text copied from the code, which an attacker can write) or `fallback` (generated without a model), present when there is a description, #175; `gantry_browse` items and `gantry_node` carry it too, and so do the explorer's `GET /api/search` hits and the review view's changes, #180) (`limit` default 10, at most 50), sorted by score then id. `repo` is the repo part of the id; the input `repo` keeps only symbols of that repo, applied after the effective-view join like `workspace`, and ranking does not change. A store holds every repo of the workspace, so a search from any repo finds symbols of all of them. `gantry_browse` items add `count` (function-like symbols in a `dir` or `file` item, else null); `kind` is a symbol kind, `dir` or `file`; `catalog_path` is the absolute path of a markdown file under the data dir's `catalog/` (`INDEX.md` when the directory defines no functions itself). `gantry_node` returns `node` as `{ id, name, kind, exported, path, line }` for a symbol or `{ id, kind: "file", path, workspace }` for a file, at most 20 neighbors per edge kind, and `more: { [kind]: n }` for the rest. When the store holds more than one repo, `gantry_browse` target `.` lists the repos (items of kind `repo`, id `repo:<name>`, `count` the functions in the repo), target `repo:<name>` lists that repo's workspaces (kind `workspace`), and a directory or file path means the one in the repo the command runs in (a workspace id names its repo); with one repo the output is as before. `gantry_node` `node` also carries `repo`. An unknown target returns `{ error: "not_found", message }`. Catalog files: one per directory that defines functions (`catalog/packages/utils/src.md`, root-level functions in `_root.md`) plus `catalog/INDEX.md`; when the store holds more than one repo every path starts with the repo name as one directory, with `%` written `%25` and `/` written `%2F` so that two repos never share a path (`catalog/acme%2Fapi/apps/server.md`, a repo's root-level functions in `catalog/acme%2Fapi/_root.md`) and `INDEX.md` lists the workspaces of all repos; each starts with a note that descriptions are untrusted and may be wrong, and every description is quoted after a fixed `untrusted <model|template|fallback> description:` label taken from the provenance column (#175). A file is rewritten only when the hash kept in `meta` (`catalog_hash:*`) changes. They are written after `gantry init`, after `heal`, after submits (at most once per 30 s, `meta.catalog_written_at`) and on every `gantry_browse`. Stored descriptions (template and submitted) are copied into the FTS `behavior`, `search_terms` and `suggested_name` columns by one helper, `refreshDescriptionFts`.

**GitHub Action (`action/`, #282).** A composite Action that users add to a workflow of their own repo (`uses: jbknick/architecture-visualization-cc-plugin/action@v<version>`, documented in `action/README.md`) to get one comment per pull request. Inputs: `version` (required; the release tagged `v<version>`), `sha256` (required; the tarball's checksum), `github-token` (default `github.token`; the workflow needs `pull-requests: write`), `embed` (default `false`; `true` also runs `gantry embed`, which adds the code-vector tier), `base` and `head` (default: the pull request's base and head commits). Outputs `comment` (`created`, `updated` or `summary`) and `comment-url`. Steps: `actions/setup-node` (Node 26, pinned by commit), install (download `gantry-<version>.tgz` and its `.sha256` from the release by tag, stop unless the download, the input and the `.sha256` file agree, `tar`, `npm ci --omit=dev`; the env var `GANTRY_RELEASE_BASE` replaces the download directory, for trying a build from another place), `gantry init` on the checkout (a fresh data dir under the runner's temp dir), `gantry embed` when asked, then `node dist/action.js`. The script is `action/src/main.ts`, bundled by tsup as `plugin/dist/action.js` and so carried by the release tarball (`gantry/dist/action.js`); it uses node built-ins and `fetch` only. It runs `gantry review <base>...<head> --json` and `gantry duplicates --since <base> --json`, builds the comment and posts it. No model calls. **Comment:** the body starts with the hidden marker `<!-- gantry:pr-comment -->` and is a summary, never the review JSON: risk and its reasons, the duplicates the pull request adds or changes (`duplicates --since`, section 14), a table of changed symbols with their direct and potential consumer counts, boundary crossings, the consumers per change (top 10 direct and top 10 potential, each with `path:line`, the rest counted; above them, when the reachable tier is not empty, the line `Reachable (4+ hops): <n>` (`impact.reachable.total`), and when there are hubs the line `Hubs: <name> (<consumers_total>), ...` with at most 3, then `and <n> more` (#295)), the notes of the review, and a footer naming the duplicate tiers (exact and near; also code-vector with `embed`). When the head commit has no `.gantry/recipe.json` the comment says the radius is structural only. Every list is capped, every line is at most 200 characters, text from the repo appears only inside code spans, and the whole body is at most 60,000 characters (GitHub's limit is 65,536); a body that is still too long loses, in order, consumers, notes, crossings and the changed-symbol table, and then the text is cut, always with a note saying so. **Posting:** the script lists the pull request's comments (following `Link` pages) and updates the first whose body starts with the marker, otherwise creates one, so a pull request never has more than one Gantry comment. A pull request from a fork (its head repo differs from its base repo, or is gone), a run that is not for a pull request, and any 401, 403 or 404 on the comment calls (or a server error that outlasts two retries) never fail the job: the body goes to the job summary and the run ends green. **Fail open (changed in the fix of #282):** the Action never fails the job for a Gantry error. A failed or invalid install input, download, checksum check, extraction, `npm ci`, `gantry init`, `gantry embed` or `gantry review` (non-zero exit, or output that is not JSON) is logged as a `::warning` line, the step exits 0, and the pull request still gets its one comment (found by the same marker and updated in place) headed "the analysis failed" with the reason as one line of at most 200 characters in a code span (text outside `A-Za-z0-9 ._:,;()/=@+-` is replaced by spaces in the shell steps; the script also strips backticks and line breaks). A checksum mismatch is logged as an `::error` line, the tarball is deleted and never extracted or run, and the step still exits 0. The earlier steps pass their reason to the last step through step outputs; the last step runs unless the job was cancelled. When the install failed there is no `dist/action.js`, so that step runs `action/post-failure.sh` from the Action's own checkout (bash, `curl` and `node` only) which builds the same comment text, lists the comments, updates or creates the marked one, and exits 0; when no comment can be posted (a fork, a refused token, no network) the same text goes to the job summary. A duplicate check that fails is reported inside the comment as before. The only failure left is a misconfigured workflow (no base and head to review, or no `GANTRY_BIN`). The Action is meant for the `pull_request` event and never runs the code it indexes. Tests (`pnpm vitest run action`) run the script against a fake GitHub API on `node:http` (`action/src/testkit.ts`) and make no real network call (the install step and `post-failure.sh` run too, against local files and the fake API); a snapshot test renders the comment from the committed review and duplicates pair in `action/testdata/` (made with `pnpm action:e2e --write-pair action/testdata`) and compares it byte for byte with `action/testdata/comment.md`; `pnpm action:e2e` runs the built script twice on a fixture branch and prints `created`, `updated`, `comments: 1`.

**Estimate formula (measured in M0, headless Haiku/low on 200 real functions):** `inputTokens = 950 × toDescribe`, `outputTokens = 250 × toDescribe`, `batches = ceil(toDescribe / 40)`, `rounds = ceil(batches / 4)`. Sequential headless time is about 0.96 s per function (about 62 functions per minute, derived from 60 / 0.96). The worker spike's 125–165 output tokens per function came from short synthetic functions and is not used; the 4-at-a-time wall times were not measured with parallel calls. Describer-subagent (Path B) throughput is not measured; do not print a subagent time estimate until it is (see `docs/spikes/GO-NO-GO.md`).

## 11. Index lifecycle

- **Targeted re-index (#360).** A run that names its files (the PostToolUse hook, lazy refresh, heal) writes those files and then re-resolves only the files whose edges can have changed: the importers of what it wrote or deleted (walked on through every importer whose edges did change, so a barrel passes a change on), the files that carry adapter output, and the files whose text ends an import specifier with the name of a file it wrote (an import that was waiting for that file). Its cost follows the files named, not the repository (6,033-file repo: one edited file about 0.9 s, from 2.1 s). A file that is not edited gets a changed edge only through one of those routes or a full index.
- **Working layer:** updated (a) by the PostToolUse hook for the edited file, (b) by lazy refresh before every MCP call: `git status --porcelain=v1 -z` → re-index changed parseable files whose mtime differs from `files.mtime_ms`, (c) by the explorer's Refresh (M4, #40): there is no file watcher and no push. Every explorer API request first checks for changed files the same way as lazy refresh (`git status` plus mtime; cheap, no re-index), and view responses carry `stale: { files: n }` when files changed since the index was last brought up to date. The web shows an "Out of date (n files)" marker. `POST /api/refresh` (same token, Origin and Host checks as the rest of the API, `Content-Type: application/json`, body ignored) runs heal (only when `HEAD` moved) plus the working-layer re-index of those files and returns `{ changed: { files, functions }, ms, healed, files: [file ids], functions: { added, changed, removed } }` (#40 added the last three: `changed` holds counts, the lists say which ids, "changed" meaning the code's exact hash differs); one refresh runs at a time and a second request gets the same answer. `/api/meta` and `/api/view/:id` carry `stale`; the web fetches `/api/meta` again when its tab gets focus back, so the marker shows after a save in the editor without a watcher. The web's Refresh button calls `/api/refresh` and reloads the current view in place (and the inspector's node, source and overview). Existing nodes keep their positions: flat graphs through the `overlay.layouts` table; the project map (no saved positions, its treemap is derived from the counts) by keeping the previous layout of the same picture (view, focus, level, filters): the workspace boxes as they were, every node's previous treemap weight, and the scene's count-based structure decisions (root-file groups, lifted folders), until the picture changes or Re-layout is pressed. Added nodes are placed inside their parent; added and changed functions (and changed files) get a highlight until the next refresh; removed ones are dropped; the selection stays while its node exists. No model call. Done-when for M4: on a repo of about 1,500 files, Refresh after editing up to 20 files shows the new code in under 2 s, nothing that did not change moves, and the marker appears within one request of a save.
- **Recipe (#203):** each index reads the recipe of the tree it indexes: the main layer reads `.gantry/recipe.json` from `HEAD` (`git show`), so an uncommitted recipe changes nothing in main, and the working layer reads the file on disk. A changed recipe changes the output of every file, which the next full index rewrites; the PostToolUse hook does not watch the recipe file. Review reads each side's recipe from its own ref (`loadSideRecipes`, `core/src/review/recipe.ts`: the merge base for the base side, head for the head side), never from the working tree. Hooks never write `overlay.db` on this path, add no stderr line for a missing recipe, and spend only one file read or one `git show` and the ast-grep passes on files of workspaces a rule applies to.
- **Main layer / heal:** `repos.head_sha` of the repo the command runs in vs `git rev-parse HEAD` (the other repos of a workspace keep their own head; per-repo heal and hooks are #219); changed files = `git diff --name-status <old> <new>`; re-index those into main, delete removed, clear their working rows if the working tree now matches. Run by post-checkout, post-merge, post-rewrite, SessionStart and `gantry heal`. A store with another `meta.schema_version` is deleted by `resetStaleStore` (section 9) before the next non-hook command opens it, and that command builds the index again from scratch; hooks never do (section 14).
- **Descriptions:** keyed by contentKey; any symbol whose contentKey has no description goes to the backlog. Never call a model during heal.
- **Embeddings:** filled lazily, never by `init`, heal or a hook, because embedding function bodies is slow compared with indexing (measured on the Devprentice test bed: about 140 ms per function after truncation, so about 7 minutes for 3,000 functions, against about 7 s for the whole deterministic index). `gantry embed` (or `gantry init --embed`) stores the missing `vec_descriptions` and `vec_code` rows, descriptions first, then code in backlog-priority order, resumably, in committed batches. Until a vector exists every consumer treats it as "no neighbours" (fail open); a changed contentKey has no vector until the next `gantry embed`.
- **Pre-commit:** read staged blobs only (`git diff --cached --name-only -z` + `git show :<path>`), parse them in memory, run local duplicate + import checks, print findings to stderr (visible to Claude in Bash output) and enqueue new functions. "New or changed" is measured against the main layer, so a copy that PostToolUse already put in the working layer is still reported. Modes `timeboxed`/`strict` additionally run `gantry describe --staged`. Always exit 0.

- **Review diff (#42, `core/review/diff.ts`).** `reviewDiff(paths, base, head)` compares the merge base of the two refs with `head`; it reads the changed indexable files' blobs with `git show`, parses and hashes them in memory, and opens no store and writes nothing (not the main layer, not the working tree). The file list is `git diff --name-status -z -M`, filtered with `isIndexable` on either path; a file over `MAX_FILE_BYTES` on either side is skipped. Symbols match by id first (`modified` when `exactHash`, signature or export status differs; unchanged symbols are not listed). Leftover removed and added symbols are paired by `exactHash`, then by `renamedHash` (own name masked), preferring the same file: same file is `renamed`, another file is `moved`; inside a renamed file, leftovers with the same name are `moved`. `id` of a change is the after id (the before id for `removed`). Each side (`SymbolSide`) also carries `kind`, `exported` and `complexity` (added in #43; impact and risk read them from the diff because the store may sit on another commit). `signatureChanged` compares the whitespace-collapsed signature text and `exportedChanged` the export flag, both only when both sides exist; `locDelta` is lines after minus lines before. Import changes compare module specifier sets per file. `base` and `head` echo the arguments; `mergeBase` is the commit sha. Everything is sorted (changes by id then kind, files and import changes by path), so the JSON is identical across runs and data dirs (no timing field). A copied file (`C`) counts as added; git type changes count as modified. `gantry review <base>...<head> --json` (also `..`) and `--pr <n> --json` print the result on stdout and nothing else; since #44 the JSON also carries `impact` (the `Impact` of the section below, from `reviewImpact` on the index as it is: no heal, no re-index, nothing created; `null` when the repository has no index), because `/gantry:review` grounds a review in it. Without `--json` the command prints the text summary of the impact section below (#43). `--open` (#44) opens the review view (below) with the same start-or-reuse logic as `gantry_open_view` (`ensureExplorer` in `explorer/server/launch.ts`) and prints the tokenised URL as a last line `Review view: <url>` (on stderr with `--json`, so stdout stays JSON). `--pr` runs `gh pr view <n> --json baseRefName,headRefOid`, fetches `origin/<base>` and `pull/<n>/head` when missing (writes under `.git` only), and without a working `gh` fails with a message that names the range form. Done-when: a 20-file diff in under 3 s (measured about a second or less for 20 files and 200 functions).
- **Impact and risk (#43, consumers since #169; `core/review/impact.ts`, `consumers.ts`, `risk.ts`).** `computeImpact(store, changes, { maxHops: 3, files? })` is synchronous and reads only the store's effective graph (main plus working layer). Seeds are the ids (after and before) of every change that is not `added`. **Consumer edge kinds** (`CONSUMER_KINDS`): `calls`, `renders`, `uses_hook`, `extends`, `implements`, `references_type` and the route edges `serves`, `handles`, `requests` where an adapter indexed them. **Hop 1** is the union of every seed change's _direct consumers_ (`directConsumers`): the sources of incoming consumer edges to either id of the change, plus, when the change is exported (for a removed, renamed or moved symbol: exported before, and its base-side file; otherwise exported on either side, and its head-side file; never for `added`), the files that import its file, except an importer file one of whose symbols is already a direct consumer (then the index can tell which code uses it, and the file is not listed twice). Hops 2 and 3 follow the same consumer edge kinds, and a `file:` node (a module-level call site, an importer) continues through the files that import it. Decision (#169): the walk and the risk follow the new kinds from hop 1 on, as the issue recommended; before #169 only `calls`, `renders` and `uses_hook` were walked and only removed, renamed or moved exports counted their importer files. The risk rules keep their meaning: "direct callers" counts the distinct hop-1 nodes, which are now every direct consumer (so a barrel or a test file that imports a changed export counts). Each node is recorded at the first hop it appears at, ids sorted within a hop, seeds excluded; `callersByHop` stops at 3 hops or 500 callers (a note says so). **Reachable tier (#293).** Whether or not that walk stopped at 500 callers, `computeImpact` goes on (a walk of its own, from the hop-1 consumers, so a stop of the first tiers does not shorten it) over the same edge kinds (a `file:` node also through its importers) at hops 4, 5, and so on until nothing new is reached or the walk holds `REACHABLE_NODE_CAP` = 2500 nodes (seeds excluded, all hops counted, a hop's new nodes taken in sorted id order); on the cap it adds the note `The reachable walk stopped at 2500 nodes; deeper consumers are not listed.` The cap and the descending fan-in order are the values of the blast-depth spike (`docs/spikes/blast-depth.md`, "Decisions"). `Impact.reachable` counts the nodes first reached at hop 4 or later, per hop; `callersByHop` stays at hops 1 to 3. The walk reads the graph from memory: one `effectiveEdges` query loads every consumer edge (`ConsumerGraph.preload`), because one query per node rebuilds the effective-files view each time and takes minutes on a large repo; the answers are those of the per-node query, in the same order. `ImpactOptions.reachable` (default true) and `reachableCap` turn it off or lower the cap; with `reachable: false` nothing else in the output changes. Risk is unchanged: nothing reachable feeds `computeRisk`. `Impact = { changed, callersByHop: [{hop, ids}], crossings: [{from, to, kind}], risk: {score, level, reasons}, notes, consumers }`. **Consumers (#169)** frame the blast radius per change in two tiers. `consumers` has one entry per changed symbol (sorted by id; `added` ones too, by symbol edges only) and then one per changed file (`files`, sorted by path; `reviewImpact` passes the diff's files): `{ id (the change id or file:<path>), target: "symbol"|"file", direct, directTotal, potential, potentialTotal }`. **Directly affected** (`direct`, hop 1): everything that uses the changed item itself, as above; for a changed file, the files that import it. **Potentially affected** (`potential`): the consumers of those, hops 2 to 3, same edge kinds (a file through its importers), excluding the change itself and its direct consumers, each kept at its first hop with the direct consumer it reaches the change through (`via`) and the node it uses one step nearer (`next`; one path is enough, the first in sorted order); that walk stops after 500 nodes. Each entry is `{ id, name, kind (symbol kind, file, or the adapter node kind such as route), path, line (null for a file or adapter node), workspace (name or null), hop, uses (edge kinds to the change, or to next, sorted; imports for an importer file), crosses (the crossing kinds below, between the consumer's file and the changed item's, sorted), via?, next? }`: names and paths only, never descriptions. `direct` and `potential` are sorted by workspace (none last), then path, then name, then id, and capped at 200 entries (`MAX_CONSUMERS`) with the totals uncapped. **Reachable consumers** (`reachable`, `reachableTotal`) come from the same walk without a hop limit, per change, from that change's direct consumers (also when the potential tier hit its 500-node stop); entries are at hop 4 or later with the same `via`, `next` and `uses` rules and carry `pathConfidence` and `fanIn`. `pathConfidence` of a direct consumer is `high` when some edge from it to the change is `high` (an importer file counts as `high`); of a node at hop h it is `high` when a predecessor at hop h-1 with `high` path confidence reaches it through a `high` edge, else `low`. `fanIn` is the number of distinct sources of its incoming consumer edges (`CONSUMER_KINDS`, plus `imports` for a `file:` node, without `ext:` sources and self edges). The tier is ranked by `compareReachable`: hop, then `high` before `low`, then `fanIn` descending (`FAN_IN_ORDER`), then workspace, path, name, id. It is capped at 200 entries per hop (not per tier, so a wide hop cannot hide the hops after it), with `reachableTotal` uncapped. **Hubs collapse (#294).** A node is a hub when its fan-in (as defined above) is above `HUB_THRESHOLD` = 608, the `hub_threshold` of the blast-depth spike (`docs/spikes/blast-depth.md`, "Decisions"; fan-in as `fan_in_definition` there). The walk goes through a hub as through any node, but in the `potential` and `reachable` tiers (hop 2 and later) a consumer whose `next` is a hub is not listed: it is counted in that hub's `HubEntry` (`ChangeConsumers.hubs`) instead, and the walk goes on from it, so its own consumers are listed normally or collapsed under another hub. The `direct` tier never collapses (it lists the change's own consumers and the risk rule counts them), and a hub stays listed in its own tier. `potentialTotal` and `reachableTotal` keep counting every distinct consumer of their hops, collapsed ones included, so the totals do not change; the lists hold the rest (the reachable cap of 200 per hop applies to what is left). `HubEntry.consumersTotal` counts the consumers first reached through the hub (those within the potential walk's 500-node stop or the reachable walk's node cap), `members` lists up to 200 of them in `compareReachable` order (entries of the potential tier carry no `pathConfidence` or `fanIn`, so the order is that of `compareConsumers`). `hubs` is sorted by hop, then `consumersTotal` descending, then hub id. `Impact.hubs` has every hub any change's walk collapsed, `consumersTotal` the largest over the changes, sorted by `consumersTotal` descending, then hub id. With `reachable: false` the reachable tier and its hubs are empty. No risk input reads hubs. **Crossings** are judged between a changed symbol and its direct consumers, one entry per kind, sorted (`from` is the change id): `app` when the caller is in a workspace of kind `app` and the changed symbol in one of kind `package`, otherwise `workspace` when the workspaces differ, and `client_server` when exactly one of the two files starts with `"use client"`. **Risk** is the sum, capped at 100, of the rules in the exported `RISK_RULES` table: signature changed on an exported symbol +30; removed exported symbol that still has callers or importers +30; distinct hop-1 callers ×2 (max 20); crossings ×5 (max 20); a changed (not added) function with complexity above 15 +10; a changed function whose file no test file (`*.test.*`, `*.spec.*`) imports +10 (each flat rule counts once per review). Levels: below 30 low, below 60 medium, else high. `reasons` has one line per rule that fired (`+30 signature changed on an exported symbol`). **Notes:** a removed export still used (names up to three users); changed symbols the index does not hold (the store should be at the base for callers of removed code to exist; a store at the head lacks them, and the note says so); and, from `reviewImpact(paths, store, diff)` (async, reads head blobs with `git show`), new imports no workspace declares (`checkImports`, only for specifiers the diff added) and added functions with an exact or near duplicate (`findDuplicates`, tiers `exact` and `near`). The issue's contract has `computeImpact` return `Impact` synchronously, which stays true; the head-blob notes need the async `reviewImpact`. Output is deterministic. `gantry review <range>` without `--json` prints: the range and counts, `Risk: <level> (<score>/100)` with the reasons, callers per hop (hop 1 lists up to three ids), crossings (first five), then for each change with consumers (at most 20, the rest are in `--json`) `Consumers of <id>:` with `Directly affected (<n>):` (top five, `name (kind, path:line) uses; crosses ...`) and `Potentially affected (<n>):` (top three, `... hop <h> via <name>`), then (#295) `Reachable (<n>):` (top three, `... hop <h> via <name>`, `and <n> more`) when the change has reachable consumers and `Hubs (<k>):` with up to three lines `<name> (<kind>, <path>): <n> consumers at hop <h> in <w> workspace(s)` (`and <n> more`) when it has hubs, a line `  reachable (hop 4+): <total>` after the hop lines of the callers when the reachable tier is not empty (a change is listed when its direct, potential or reachable total is above 0), and notes; `--json` prints `impact.consumers` in full (both tiers, capped at 200 each); it runs `heal` and `refreshWorking` first, so the index is the checked-out tree. `gantry_impact` (section 15) shapes the same data for MCP.
- **Re-attaching hand-picked entries (#288; `core/src/overlay/reattach.ts`).** `reattachOverlay(store): { reattached: { from, to }[], unresolved: UnresolvedEntry[] }` looks at every anchored id (section 9) that is not in the effective graph and finds the effective function-like symbols (`function`, `method`, `component`, `hook`) with the same `exactHash`. Exactly one, and its id not already held by the same entry: the old id is rewritten to the new one everywhere it occurs (label row, selector JSON, anchor row) in one transaction. Zero or several: nothing changes. It matches by `exactHash` first; since `exactHash` includes the symbol's own name, a move or a file rename with an unchanged body re-attaches by it. When no symbol has the anchored `exactHash` (#349), it looks for effective function-like symbols in the same file and of the same kind family with the anchored `renamedHash` (`overlay.anchor_renames`), the same body under another name, and applies the same rule: exactly one and not already in the entry. The kind families are those of section 17 (`function` and `method` together, `component`, `hook`), compared with the family stored in `overlay.anchor_families`; a function renamed to `use[A-Z]…` (a hook) or to a PascalCase component with the same body is another family and stays unresolved (`gone`). Same file only, because a `renamedHash` also matches a copy written elsewhere under another name; a function renamed and moved at once stays unresolved. Several `exactHash` matches stay ambiguous without trying `renamedHash`. It writes only when an id changes, so an index with no moved symbol leaves `overlay.db` byte-identical. It runs only where the caller asks for it (`heal(paths, { reattach: true })`, `refreshWorking(paths, { reattach: true })`, both off by default): `gantry heal`, `gantry index`, `gantry init`, `rebuildIndex` (the `map` command), the MCP lazy refresh and `POST /api/refresh`. It runs on every such call, also when the heal or refresh itself changed nothing (a hook may have healed the commit first, without re-attaching); it writes only when an id changes. No hook entry point (SessionStart, the git hooks `post-checkout`, `post-merge`, `post-rewrite` and `pre-push`, PostToolUse, Stop) sets it, so a hook never writes `overlay.db`; the lookups (`search`, `node`, `trace`) do not set it either, and the next call above re-attaches. `UnresolvedEntry = { entry: "label" | "hidden" | "group" | "view", id, groupId?, viewId?, text?, reason: "gone" | "ambiguous" }`, sorted by entry, then id; `ambiguous` when the anchored hash (`exactHash`, else `renamedHash` in the same file) matches several symbols (or the only match is already in that entry), `gone` otherwise. `listUnresolved(store)` computes it without writing. Entries are never dropped for being unresolved.
- **Overlay at view time (#286; `explorer/server/overlay.ts`, `api.ts`).** Every `/api/view/:id` response is passed through `applyOverlay(ctx, result, state, spec?)` after the view is built, and carries `overlay: { hidden: number, groups: { id, name, members: string[] }[] }`. Labels: a node whose id has a label gets `label = text` and `labelOriginal = <previous label>` (`GraphNode.labelOriginal?`). Hidden: nodes matching the global hidden list or `spec.hidden` are removed with their descendants (by `parent`) and every edge with a removed end; `overlay.hidden` is the removed node count. Groups: for each group (all, or those in `spec.groups` when non-empty), `members` are the ids of response nodes matching its selectors, sorted; groups are sorted by id. Selectors see the store's path and workspace of a node, never its id's text. **Saved views:** `GET /api/view/:id?saved=<viewId>` applies a saved spec; an unknown id answers 404 `Unknown saved view: <id>`, a spec for another view 400. The spec's `level`, `focus` and `filters` are the defaults for the view's parameters and query parameters given explicitly win; the same saved view and index always give the same response bytes. **Routes** (same Host, Origin and token checks as the rest of the API; writes need `Content-Type: application/json` and a body of at most 64 KiB, else 413; a validation failure answers 400 `{ error: "<path>: <zod message>" }` from the first issue; `DELETE` is allowed only on the two `DELETE` routes, every other method and path keeps answering 405 with `allow: GET, HEAD`):

- **Curation controls (#287; web `components/CurationActions.tsx`, `CurationPanel.tsx`, `SavedViews.tsx`, `NameDialog.tsx`, `curation.ts`, `api.ts`, `store.tsx`).** The web holds the overlay (`GET /api/overlay`) in its store and loads it again after every write and after Refresh; a write is followed by a fetch of the open view. **Hash key `saved`** (the saved view id): `parseHash` and `formatHash` round-trip it, it is not a filter, and it goes to `/api/view/:id` as the query parameter `saved`. The inspector, on any node, has **Rename** (an inline `Label` field of at most 80 characters; Enter saves through `PUT /api/overlay/labels`, an empty value removes the label, and the inspector shows the original name under the new one), **Hide** (appends `{ type: "ids", ids: [<node id>] }` to the hidden list through `PUT /api/overlay/hidden`) and a `Group` combobox (the existing groups, then `New group…`). Choosing a group appends the node id to that group's first `ids` selector, or adds an `ids` selector when it has none. `New group…` asks for a name; the id is the slug of the name (`a-z0-9-`, at most 63 characters), a taken id gets `-2`, `-3`, and the new group is created with one `ids` selector holding the current node (a group needs at least one selector) and `mayUse: null`. The left panel's `Curation` section lists labels (node, text, remove), hidden entries (`Show again` removes that entry) and groups (name, `overlay.groups[].members` count of the open view, rename, delete). The top bar's `Saved view` combobox lists the saved views by name, then `Save view…` (dialog `Save view`, textbox `Name`; saves `{ view, level, focus, filters }` of the current route with `groups: []` and `hidden: []` under the slug of the name) and `Reset curation…` (confirm dialog, then `POST /api/overlay/reset`); choosing a saved view navigates to `#/<spec.view>?saved=<id>`. The two comboboxes are native `<select>` elements of the kit's `native-select`, and the dialogs are SmoothUI's `dialog`; every animation honours `prefers-reduced-motion`.
- **Review view (#44; on the map since #167; `explorer/server/views/review.ts`, `reviewView.ts`, web `views/Review*.tsx`).** View id `review`, hint `review`. Params (view options) `range` (`<base>...<head>`, at most 300 chars) or `pr` (a pull request number, resolved with `resolvePullRequest`); both is a 400, neither returns `{ nodes: [], edges: [], review: null }` and the web asks for a range. It runs `reviewDiff` and `reviewImpact` on the commits `reviewCommits(paths, base, head)` resolves (read-only: git blobs and the index as it is, no re-index) and caches the result in memory per (data dir, merge base, head sha), at most 8 entries, dropped when the index changes (`meta.head_sha` or `store.generation()`, which also moves on commits by other processes such as the hooks and the MCP server) and on every `POST /api/refresh`; a `pr` is resolved with `gh` at most once a minute per pull request (cleared by Refresh too). `gantry review --open` waits up to 10 s for a fresh explorer; `gantry_open_view` keeps 2.5 s and its timeout message says to retry in a few seconds. A bad or unknown ref, or a failing `gh`, is a 400 with the message. **Mode `map` (default): the review as a layer on the project map.** The response's nodes and edges are exactly the project map's for the same level and filters (`focus` is ignored: in the review it is the selected change), so every node sits where it sits on the plain map (tested: same nodes, edges and laid-out positions); `map=3d` draws on the 3D map's settlements instead and uses the Files level. `review.layer` = `{ marks, links, linksTotal, placed, unplaced }`, every id a node of the response: a mark `{ id, change?, changes?, hop? }` puts each changed symbol on the deepest node that shows it (either side's id, else either side's file, so a removed symbol shows at its base-side file while that file is in the index, otherwise it is in `unplaced` and only listed), and each changed file of the diff on its node; the kind is `added`, `modified`, `signature` (modified with a signature change), `moved` (renamed or moved) or `removed`, and on a shared node the first of removed, signature, moved, modified, added wins. Nodes without a change that hold a caller get the nearest `hop` (1 to 3). ## 12. Git hooks install

- Hooks: pre-commit, pre-push, post-checkout, post-merge, post-rewrite. Each is a 3-line sh script: `[ "$GANTRY_WORKER" = 1 ] || "$HOME/.gantry/bin/gantry" hook <name> "$@" </dev/null || true`, then chaining (git runs hooks without the plugin environment, so when the repo's resolved data dir is not under `~/.gantry/data` the install writes `CLAUDE_PLUGIN_DATA='<base>'` in front of the shim call, #144, so the hook reads the same store as the plugin; when no plugin base applies the resolved base is `~/.gantry/data`, the install still proceeds and writes to stderr `gantry: warning: no plugin data directory found; the git hooks will read <dataDir>. Run this from /gantry:init or set CLAUDE_PLUGIN_DATA.`) (below), then `exit 0`. `GANTRY_WORKER=1` skips only the Gantry call, so a chained user hook still runs; Gantry's stdin is `/dev/null` so the chained hook still receives git's stdin.
- If `core.hooksPath` is unset: write into `.git/hooks/` (use `git rev-parse --git-path hooks`); if a hook file already exists, rename it `<name>.gantry-prev` and chain to it.
- If `core.hooksPath` is set (husky/lefthook): create `<dataDir>/hooks/` wrapper scripts that run Gantry then exec the original `<hooksPath>/<name>` with the same args, and set local `git config core.hooksPath <dataDir>/hooks`, saving the previous value in `meta.prev_hooks_path`.
- Shim `~/.gantry/bin/gantry`: sh script with absolute paths to `node` and `plugin/dist/cli.js` resolved at install; if the target is missing it exits 0.
- `gantry hooks uninstall` / `gantry uninstall` restore everything exactly.

## 14. Hook I/O contracts

- **PostToolUse** (matcher `Write|Edit|MultiEdit`), the trigger: stdin JSON with `tool_name`, `tool_input.file_path`, `cwd`, `session_id`. It records the edited file in the session's batch and re-indexes it if it is a source file; with a `session_id` it prints nothing. Budget 1,500 ms warm on 2,000 files.
- **Stop**, the end of the batch (#131): stdin JSON with `session_id`, `cwd` (and `stop_hook_active`, not read). It settles the session's batch (below). On findings, stdout exactly `{"hookSpecificOutput":{"hookEventName":"Stop","additionalContext":"<≤600 chars>"}}`; on none, no stdout. Same budget.
- Without a `session_id` a PostToolUse edit is a batch of one, under a key of its own (never shared with another call; its row is removed when the call ends): it is settled at once and the findings are printed as `{"hookSpecificOutput":{"hookEventName":"PostToolUse","additionalContext":"<≤600 chars>"}}`.
- **SessionStart:** heal, then print one plain-text line only if the index is missing (`Gantry: run /gantry:init to index this repo`; a store without a built backlog, `isIndexed` false, counts as missing) or backlog ≥ `backlogReminderThreshold` (`Gantry: N functions await descriptions — run /gantry:sync when convenient`). With no store it creates nothing (#147). Claude Code adds plain stdout of SessionStart to the model's context.

- **Stale store (#198).** A store whose `schema_version` is not `SCHEMA_VERSION` (section 9) makes `openStore` throw `StaleStoreError`. Hooks (the git hooks, SessionStart, PostToolUse, Stop and pre-commit) never reset or rebuild it: they catch the error, log one line to `<dataDir>/logs/hooks.log`, exit 0 with their normal empty output and leave the store as it is. SessionStart then prints its usual `Gantry: run /gantry:init to index this repo` line. The next non-hook command rebuilds the store.

Implementation notes (#31; checked against the Claude Code hooks docs on 2026-11-14; Stop added in #131 and checked against https://code.claude.com/docs/en/hooks on 2026-11-15). `hooks/hooks.json` is `{ "description"?, "hooks": { "<Event>": [ { "matcher"?, "hooks": [ { "type": "command", "command": "...", "timeout": <seconds> } ] } ] } }`: the event names sit under a `hooks` key and each matcher group holds a nested `hooks` array (Stop takes no matcher). Claude Code sends more fields than the contract needs (`transcript_path`, `hook_event_name`, `tool_use_id`, `permission_mode`, `last_assistant_message`, ...); the hooks read only the fields above. Exit 0 with the JSON above on stdout adds `additionalContext` to Claude's context (the docs cap it at 10,000 characters; ours is 600); for Stop the docs say it is non-error feedback and the conversation continues so Claude can act on it, so a turn that left a duplicate gets one more step to reuse it. Stop fires for the main agent only (SubagentStop is separate and not used): a subagent's edits join the session's batch and are settled when the main agent stops. Exit 2 would show stderr to Claude and any other non-zero code shows a "hook error" notice, so a Gantry hook never exits non-zero.

The pipeline is trigger, then batch re-index, then checks, then a double-check, then output (#131; the M2 replay showed that checking each edit on its own alerts on the first half of a move and on an import whose dependency the same change adds to package.json):

- **Trigger (PostToolUse).** Any edited file that can change a finding is recorded in `pending_files` (section 9) for the session: a source file (`isIndexable`, which also excludes sensitive files), a `package.json`, a `tsconfig*.json` or `pnpm-workspace.yaml`. Other files are ignored. The first time a batch touches a file, the `exactHash` of each of its symbols is stored as the file's baseline. A source file is re-indexed into the working layer at once (a store write, never a write into the repo), so the MCP tools see it; nothing is checked yet.
- **Batch re-index (Stop).** Every source file of the batch with `reindexed` 0 (a trigger cut off before its index finished, or a manifest edited after the file) or gone from disk is re-indexed into the working layer, 8 files per committed step, each marked `reindexed` (so a batch too large for one Stop continues at the next); the manifest rows are removed once that is done. Each index run re-reads the workspaces from disk (`package.json` name, dependencies and exports, the workspace list, `tsconfig` paths) and stores them, so the checks see the post-batch state; a deleted file is marked deleted. Files whose trigger finished its index are not indexed again. A source file changed afterwards by a shell command is not re-read here; the double-check covers the matched side only.
- **Progress and concurrency.** A settle first prunes rows older than 24 h, then works file by file. Each step takes the store's write lock with a short wait (200 ms); when another settle or index holds it, the settle stops there and the rest stays in the batch (fail open). A file's row is deleted in the same transaction as its check, by the `created_at` that was read, so a file edited again during the settle, and a file added to the batch meanwhile, stay for the next Stop. No file is started after the budget minus a margin (300 ms, or a quarter of the budget if smaller), so the findings of the files already checked are printed in time; the files it had no time for stay in the batch, and every Stop makes progress on it. Opening the store itself can still wait on a lock held by a long index run; the hook budget then cuts the Stop off and nothing is lost but time, since no row was deleted.
- **Known limit: baselines are per session.** Two sessions editing the same file each keep their own baseline. When session B first touched a file before session A changed other functions in it, B's Stop also reports A's changes (they differ from B's baseline); when A changed it first, B's baseline already includes A's changes and B reports only its own.
- **Checks.** For each source file of the batch, the function-like symbols that are new or whose `exactHash` differs from the baseline are checked with `findDuplicates` (tiers exact, near, code_vector). The `semantic` tier is not used. `code_vector` reads stored vectors only and never loads the model, so a new symbol without a vector is checked by the exact and near tiers alone. An import is reported only if `checkImports` flags it for the file and does not flag it for the `HEAD` version of the file (only imports added since the last commit).
- **Double-check against disk**, just before output. A duplicate is kept only while the matched function is still in its file on disk: unchanged since it was indexed, or changed but still exact or near to the new function at the configured thresholds (a changed code_vector match is dropped, as its vector cannot be recomputed in the hook). This drops the first half of a move once the old copy has been edited away or deleted, also by a shell command that ran no hook. An undeclared-import finding is dropped when the workspace's or the root's `package.json` on disk now declares the package (dependencies, devDependencies, peerDependencies or optionalDependencies). Dropped findings are silent. The double-check runs before the matches of a symbol are cut to 2, so a dropped match makes room for the next one; for one symbol, when any kept match has `inline: true` advice only the inline matches are listed.
- **Group boundaries (#289).** A group whose `mayUse` is not null is a boundary (section 7); `null` means no rule. A _crossing_ is an edge of kind `imports` (file to file), `calls`, `renders` or `uses_hook` whose source is a member of a boundary group G and whose target is a member of a group H, with H not G, H not in G's `mayUse`, and the source not also a member of H. Membership uses `matchSelector` on the node; a symbol is a member when it or its file matches. Only crossings the batch adds are reported: edges from the batch's new or changed symbols (and, for `imports`, from the batch's files) that the main layer does not have. The check reads the groups once per file with `readOverlay` and reads nothing else but the store; it never writes `overlay.db`. It runs per file after that file's duplicate and import checks, inside the same step, so it shares the budget margin, and a crossing goes through the double-check too: it is dropped when the source file on disk no longer holds an import of the target (a relative specifier is resolved against the source file; a package or alias specifier cannot be resolved here and keeps the crossing). pre-commit adds the crossings of the staged symbols and files, against the main layer. Boundaries only warn: nothing is ever blocked (section 5).
- **Output.** Names, paths, tiers, scores and actions only; no body and no stored description. A line is `Gantry: <new> (<path>:<line>) looks like <existing> in <path>:<line> [<tier> <score>]. <action>`, or `Gantry: <action> (line N)` for imports, whole lines only up to 600 chars; files in path order, in each file symbols lowest in the file first, then imports, then crossings. A crossing between two symbols is `Gantry: <srcName> (<srcPath>:<srcLine>) in group <srcGroupName> uses <dstName> (<dstPath>:<dstLine>) in group <dstGroupName>, which <srcGroupName> does not list. Warn only.`; an `imports` crossing with no symbol-level crossing between the same two files and groups is `Gantry: <srcPath> in group <srcGroupName> imports <dstPath> in group <dstGroupName>, which <srcGroupName> does not list. Warn only.` Crossing lines of a file are ordered by source line (an import-only line counts as line 0), then target id. Once every file is checked the batch is empty, so a second Stop in the same turn says nothing.
- Each hook stops at 1,500 ms (env `GANTRY_POST_TOOL_BUDGET_MS` overrides it for tests) and prints nothing (fail open). A Stop cut off at the budget has deleted the rows of the files it finished, and their findings are not printed (the margin above is there to make that rare; the M2 replay counts it); the files it did not finish stay for the next Stop. Each hook's own `timeout` in `hooks.json` is 5 s.
- **Duplicate rules of the pull request comment (#282).** The Action (section 10) applies the pre-commit rule, new or changed symbols checked against the rest of the index, to the pull request: `gantry duplicates --since <base>` keeps the groups of the Duplicates view (section 17, tiers exact and near; code-vector only when the workflow ran `gantry embed`; the `semantic` tier is not used) with a member among the symbols added or changed in `<base>...HEAD`, and the comment marks those members "added here" or "changed here". Unlike the hooks, it reports groups, not a 600-character line, and it has no double-check against disk (the checkout is the head commit). Both are read-only and make no model call. The review's own notes of added functions that duplicate indexed code (`reviewImpact`, exact and near) are left out of the comment while the duplicate check ran, because the section says the same with more detail.
- pre-commit prints the same lines (no 600-char cap, at most 10) to stderr for the staged symbols that are new or changed against the main layer (section 11), and for imports added against `HEAD`. It indexes the staged blobs on a scratch store whose workspaces are read from disk; it has no batch and no double-check (the staged version is what is checked).

`gantry_open_view` link contract (#136). The URL is `http://127.0.0.1:<port>/?t=<token>#/<view>?focus=<id>&saved=<id>&<filters>`. `saved_view` (#287, string, 1 to 63 characters) is the id of a saved view: the tool reads `overlay.views` and answers `{ error: "unknown_saved_view", message, views: [ids] }` for an id that is not there, and `{ error: "saved_view_mismatch", message, view: <spec.view> }` when `view` differs from the saved view's `spec.view` (`view` stays required); otherwise the hash carries `saved=<id>` (after `focus`) and the explorer sends it to `/api/view/:id` as `saved`. `saved` is a reserved filter key like `focus`, `t` and `view`. `focus` is the node the view is about (the project-map subtree root, the ego centre, the node a page, slice, duplicates or 3D view centres on) and is also the node shown in the inspector. The tool writes `focus` only; the explorer applies the selection when it loads the page: if the hash has a `focus` and no `sel` key, it behaves as if `sel` equalled `focus`, as a click in the app does. An explicit `sel` (passed in `filters`; an empty `sel=` means "nothing selected") wins. This is done once at load. Closing the inspector writes `sel=` (empty) next to the `focus`, so a reload or a copied URL keeps it closed. Explorer lifecycle (#123): `ensureExplorer` (`explorer/server/launch.ts`, shared by the tool and `gantry review --open`) is a hard bound: it returns within its limit (2.5 s for `gantry_open_view`, 10 s for `gantry review --open`) even when the explorer named in `explorer.json` accepts connections but never answers, and deletes nothing in that case. The explorer it spawns runs `gantry map --no-open --no-url --idle-timeout 30` and exits after 30 minutes without a request (closing the server and removing `explorer.json`), so the embedding model it may have loaded does not stay in memory; a foreground `gantry map` has no idle timeout. The start lock is waited for longer than its 10 s staleness age.

Claims expire after 10 minutes and return to `pending`. A claim never changes the rows of a batch that is still claimed: only the same `worker_id` is handed that batch again, and a smaller re-claim returns a part of it while the rest stays claimed, so descriptions submitted for the full batch are still accepted (no `not_in_batch`). Tool names as seen by Claude: `mcp__plugin_gantry_gantry__<tool>`.

`gantry_trace` details (#47). Runs `trace` (section 9) on the target; an unknown target is `{ error: "not_found" }`. `routes`, `endpoints` and `tables` are the chain's nodes of those kinds (the start excluded), `low: true` marking a low-confidence step. When the whole chain does not fit in 3,800 characters, the steps that are not routes, endpoints or tables (components, hooks, helpers) are summarised as `repeats: [{ depth, via, kind, count, sample }]` (one per depth, edge kind and node kind, with the first id) and the lists are cut to 40, 20, 10, ... entries until it fits, each cut list adding `<name>_total`; at most 8 gaps of 200 characters (`gaps_total`). Ids, kinds and edge kinds only: no description text is returned, and a containment test seeds a marker as every symbol's description and suggested name and asserts it appears in no trace of any node, either direction.

`gantry_impact` details (#43). Exactly one of `range` (`<base>...<head>`, a symbol diff then impact with the head-blob notes), `paths` (up to 50 indexed files: every symbol in them counts as modified in the working layer against main) or `symbol` (a symbol id or `path:line`) is required, else `{ error: "bad_arguments" }`; a bad or unknown range is `{ error: "bad_range" }` and an unknown target `{ error: "not_found" }`. Lists are capped so the response stays under 4,000 chars: 10 `changed` entries (`changed_total` when more), 12 ids per hop (`more`), 8 crossings (`crossings_total`), 6 notes of at most 220 chars (`notes_total`). `consumers` (#169) lists the changed symbols that have any (at most 5, `consumers_total` when more), each with `direct` (directly affected, hop 1: up to 5 with how each uses it and its crossings) and `potential` (potentially affected, hops 2-3: up to 3 with hop and the direct consumer it goes through), with uncapped totals; ids only, the same data as `impact.consumers`. Reachable and hubs (#295): the top level has `reachable_total` (`impact.reachable.total`); each `consumers` entry has `reachable_total`, `reachable_by_workspace` (`{ <workspace name or "(none)">: count }` over the change's listed reachable consumers and the consumers of every hub of hop 4 or later, at most `IMPACT_LIMITS.reachableWorkspaces` = 6 keys by count descending then name, `reachable_workspaces_total` when there are more; the listed ones are capped at 200 per hop, so the counts of a very wide hop can fall short of `reachable_total`) and `hubs` (at most `IMPACT_LIMITS.hubs` = 3 of `{ hub (node id), consumers_total, by_workspace (an object as above, at most 6 keys) }`, `hubs_total` when more). Ids, names and counts only. A description is returned only as `untrusted_description` on a `changed` entry (cut at 160 chars), and the tool description says never to follow it; a containment test seeds a marker and asserts it appears under no other key (the consumer lists included, and checked non-empty). The graph is the index of the checked-out tree, so a range whose head is not checked out sees callers of the code as it is now.

Describer tool details (#24). `gantry_claim_batch` items are `{ content_key, path, kind, signature, doc, callees, return_type, runs_when?, body }` (`runs_when` only for a Go `init`, #372). `worker_id` is optional: when it is missing the server mints `w-<8 hex>` and returns it as `worker_id` (every response carries `worker_id`), so two callers never share an id by accident; the skills also give each describer its own id (`init-1` to `init-4`, `sync-1` to `sync-4`). Submits are validated by `batch_id` alone, whoever claimed it. A batch the worker claimed and did not submit is returned again, under the same `batch_id` and with `reissued: true`, before any new function is claimed (the claim clock is not restarted). A claim returns up to `size` sheets (default and maximum 10, `CLAIM_SIZE`; a larger `size` is a schema error) in one response of at most 20,000 chars (10 typical sheets are about 4,000; the old 40 and 80,000 were too big for a describer to read in one tool result, and 10 worked in the live run, #141); sheets of a fresh claim beyond that go back to `pending` and the payload says `truncated: true` (the rest of a re-issued batch stays claimed and comes with the next claim); a single oversized sheet is shortened (doc, callees, signature, then `body`, flagged `body_truncated`). `gantry_submit_descriptions` keeps the 4,000-char cap. `gantry_submit_descriptions` rejects a `content_key` outside the batch as `not_in_batch`, adds `embedded` (vectors stored right away, only when the model is already cached) and `batch_status: "unknown_or_expired"` when no claim carries that `batch_id`. Every tool description ends with the `untrusted_description` notice.

Rejections and resubmits (#147). A validation rejection counts an attempt and records `last_error`, but the row stays `claimed` in its batch (same `claimed_by`, claim clock unchanged), so a reworded resubmit under the same `batch_id` is validated again and accepted when it passes; it was released to `pending` before, which made the resubmit `not_in_batch`. A rejected row the describer does not resubmit comes back with that worker's next claim (`reissued: true`). At `MAX_DESCRIBE_ATTEMPTS` (2), or 3 after a clean `shape`/`identifier` second rejection (#150, section 8), the row becomes `failed` and keeps its `claimed_by`, so a later resubmit in the same batch is answered `attempts_exhausted` (and the batch is still known); `resubmit` on each rule rejection says whether the row is still in the batch with an attempt left. A row whose third attempt fails with an extendable rejection gets the fallback description instead when one passes the validator and no description exists yet (#175) (`fallback: true`, the response's `fallbacks` counts them). The headless worker uses the same limit rule; it never runs a row with 2 attempts, so the extra attempt and the fallback happen on the describer path. The headless worker path keeps releasing a first failure to `pending`.

Describer runs (#147). The describer subagent has `maxTurns: 60` (section 16), and a live run on a 3,511-function backlog showed describers stopping at the turn limit with no report, then piling up context when resumed. So the server, not the model, ends each run: it counts the claims that returned items per data dir and `worker_id` (in memory; a server restart only makes a run longer), and after `DESCRIBER_RUN_CLAIMS` (15) the next claim that has no unsubmitted batch to reissue returns `{ worker_id, batch_id: null, items: [], stop: "run_limit", remaining, message }` and resets that count (`remaining` = pending + claimed). A run is then at most 15 claims, 15 submits and some resubmits, well under 60 turns. An empty claim otherwise says `stop: "backlog_empty"` with `indexed: true` and `remaining`, or, when `isIndexed` is false for the store (no `gantry init` ran against this data dir), `stop: "not_indexed"`, `indexed: false`, `data_dir` and a message to run `/gantry:init`, so a describer never reports an unindexed store as an empty backlog. The `init` and `sync` skills restart a describer that hands back with work left (section 16).

Overview tool details (#35; the contract and the `overviews` table notes were missing and are added here). `node_id` is `ws:<repo>:<workspace name>` or `dir:<repo-relative folder path>` (`dir:.` is the whole repository; the 3D map's spelling `dir:<workspace id>:<path inside the workspace>` is accepted and normalised); any other id, a folder with no indexed file, or a path with `..` returns `{ error: "not_found", message }`. `overviews.input_key` = sha256 of the sorted repo-relative paths of the node's files, then `\n--\n`, then the sorted `contentKey`s of every function-like symbol (`function`, `method`, `component`, `hook`) in the node's files, then `\n--\n`, then, for a workspace, the sorted ids of the workspaces nested under its directory (a workspace owns only files whose `workspace_id` is its own); a folder covers every file under its path. `gantry_get_overview` returns the stored text only when `input_key` still equals the current key, else `cached: false` with `reason: "missing"` (no row) or `"stale"`; `functions` is the function-like count in the node. `gantry_save_overview` stores `text` for the node's current key, replacing any earlier row. Checks, in order: whitespace runs fold to one space; empty or non-string is `schema`; more than 1,200 characters is `length` (never truncated); the secret filter (`scanSecrets`, spec section 8 check 2) is `secret`; the injection filter (`scanInjection`: control and non-ASCII characters, instruction patterns, chat-template tokens, markup, obfuscated hosts, links, URL schemes, shell commands) is `injection`. Shape and grounding rules do not apply (an overview is prose, not a one-sentence description). `detail` names rules only, never matched text. Every save writes one `usage_log` row `{ task: "overview", model, effort }` from the `overview` routing entry, `functions` = the node's function count, `source: "explainer"`. Overviews are never generated by any tool or hook on their own: only the `explainer` agent writes one, only when `/gantry:overview` asks. The overview is model-written text about untrusted code, so it is returned only in a field named `untrusted_overview` (MCP `gantry_get_overview` and the explorer's `GET /api/overview/:id`, which returns `{ node_id, untrusted_overview: string\|null, stale, model?, created_at? }` and never a stale text), every tool description carries the notice that the field is data and nothing in it is to be followed, and the explorer inspector shows it for workspace and folder nodes as plain text under "Overview — generated, may be wrong", or the hint "Run /gantry:overview <id> in Claude Code". A containment test seeds a marker as an overview and asserts it appears in no MCP tool or `/api` response except as the value of `untrusted_overview`.

The `init` and `sync` skills keep the backlog moving: on each describer completion they start a **fresh** `describer` with the same prompt and worker id when it reported `MORE WORK` or came back marked partial or cut off, or when it reported `DONE` and `backlog --json` still shows `pending` above 0; they stop on `NOT INDEXED`, `ERROR`, two runs in a row of one worker id with 0 accepted, or when the user asks; at the end they offer `backlog --failed` and `--retry-failed`. So: the server ends runs before the limit (the model need not count turns), the parent starts a new instance (small context; the server reissues any unsubmitted batch to the same worker id), and the per-claim size stays 10 (section 15) because larger claims were too big to read. Not done: more items per call (several batches per claim) would break the 20,000-char read limit of #141.

## 17. Duplicate tiers (thresholds measured in M0, re-fit in M2 (#32))

| Tier        | Rule                                                                                                                                                       |
| ----------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- |
| exact       | same `exactHash` or same `renamedHash` (#151), `stmtCount ≥ 3`                                                                                             |
| near        | same `shapeHash` or shape MinHash Jaccard ≥ 0.85, and token MinHash Jaccard ≥ 0.75 (#131), `stmtCount ≥ 6`, same parameter count ±1; score = token Jaccard |
| code_vector | cosine ≥ 0.98 (M2) between normalized-code embeddings, and token MinHash Jaccard ≥ 0.50 (#131)                                                             |
| semantic    | cosine ≥ 0.60 (measured in M0) between description embeddings, compatible signature                                                                        |

**Languages (#220).** Comparisons never cross languages: `findDuplicatesDetailed` and `rebuildSimilarEdges` skip every candidate whose `lang` differs from the query symbol's, so no `similar_to` edge joins two languages. Thresholds are per language: `thresholdsFor(config, lang)` returns the configured values for every language (the TypeScript values; Go gets its own only if seeded Go duplicates fail them), and each language module carries its statement floors (TypeScript: exact 3, near 6). Go (#223) uses the TypeScript values unchanged: the seeded Go set (below) finds its exact and near cases at them, and the code_vector cases once the Go embedding text is normalized like the TypeScript one (next paragraph). A Go `function` and `method` are the function family; `init` and `_` functions and generated files never take part; a Go struct, interface, type, const or var has no family. The five hash values come from one shared function, `hashStreams({ exact, shape, selfRefs })`; the token streams come from the language module, and no language-blind normaliser exists.

Go embedding text (#223). Before #223 the Go text was the declaration with comments dropped; a verbatim copy under a new name then embedded at cosine 0.89 to 0.95 of the original, never reaching `codeVector` 0.98 (measured on the seeded Go set, `evals/seeded-duplicates-go/`). The Go text now follows the TypeScript rule: the declaration's own name and every name declared inside it (parameters, results, receivers, `:=`, `var`, `const`, `range` and type-switch bindings, the same set as the exact stream) become `v1, v2…` in order of first appearance, comments are dropped, whitespace is collapsed, and string literals become `"s"`; field, method and package names and identifiers declared outside the declaration are kept. The same copies then embed at 0.983 to 0.992.

Embedding scope: only function-like symbols with `stmtCount ≥ 3` get a `vec_code` row (smaller ones are never compared by any tier), and the text is the normalized code cut to its first 1,500 characters (`CODE_EMBED_MAX_CHARS`, the fact-sheet body budget) with the tokenizer capped at 512 tokens, so the cost per function is bounded. Embedding is lazy (section 11).

Embedding model (measured in M0): `jinaai/jina-embeddings-v2-base-code` (q8 ONNX, mean pooling, L2-normalized) for both descriptions and normalized code, dimension D = 768, so `vec_descriptions` and `vec_code` are `float[768]` (section 9 migration v2). The two thresholds are initial values from a small hand-written set (15 + 15 pairs per task), not final: code_vector 0.96 gave recall 93% and 7% false positives (1 of 15), semantic 0.60 gave recall 80% and 7% false positives; the old 0.92 and 0.85 gave 33% false positives and 0% recall. M2 (#32) re-fit them on a real replay and real LLM-written descriptions (`docs/milestones/M2.md`): `codeVector` moved to 0.98 (on 1,416 replayed edits, 1 of 98 code-vector candidates at 0.91 or above was a true duplicate and none at 0.93 or above, and between 0.96 and 0.98 they added 4 alerts, all false; the M0 code pairs find 14 of 15 at 0.98 with no false positive, against 15 of 15 and one false positive at 0.96), `nearJaccard` 0.85 and `semantic` 0.60 are kept (the sweep was flat for the first; for the second, 0.65 would drop recall on the M0 description pairs from 11 to 6 of 15 with no fewer false positives). `semantic` only gates the description-to-description tier of `findDuplicates`; neither the hook nor `gantry_find_similar` applies it to a draft.
Normalizer for `vec_code` (decided in M0, approved by the operator on 2026-11-14): rename local identifiers (parameters, `const`/`let` names, the function name) to `v1, v2, …`, drop comments, collapse whitespace, replace string and template literals with `"s"`, but keep property names after `.` and well-known globals (and any other identifier not declared inside the function, such as an imported helper). The function's own name is renamed too, recursive calls included. Renaming everything made `capitalize` and `decapitalize` identical (cosine 1.000); keeping them raised Jina's best accuracy from 93.3% to 96.7% (measured in M0).

Renamed copies (#151). The near tier needs `stmtCount ≥ 6`, so a renamed copy of a 3 to 5 statement function matched no tier. `exactHash` includes the function's own name, and it is also the base of `contentKey` (descriptions, backlog, vectors), so it is left alone. A second hash, `renamedHash` (section 7, `symbols.renamed_hash`, migration v6), is the hash of the near-tier token stream below: the same tokens as `exactHash` with the symbol's own name (recursive calls included) replaced by `$0`. The exact tier matches on either hash, score 1, `stmtCount ≥ 3`. A row without `renamedHash` (before v6) matches on `exactHash` only until the next heal re-indexes it. Known gap: a class or object method has no root name to normalise, so a renamed copy of a short (under 6 statements) method is still missed. Measured on the M2 replay in `docs/milestones/M2.md` section 6.

Near-tier token stream (#131). The shape stream drops literals, property names and callees, so any two functions of the same shape scored 1.00 (in the M2 replay most false near alerts were two lookup functions mapping different strings). The near tier therefore has a second gate: a MinHash (64 permutations, 5-token shingles, as for the shape) over the exact token stream (section 7: node types, operators, literal values, property names and outside identifiers kept, locals renamed `$1, $2…`) with the symbol's own name replaced by `$0`, so a copy under a new name still scores 1. It is stored as `symbols.near_minhash` (migration v5). A pair is near when the shape gate holds (same `shapeHash` or shape Jaccard ≥ `nearJaccard`) and the token Jaccard is ≥ `nearTokenJaccard`; the score is the token Jaccard. A row without a token MinHash (written before v5; the migration forces a full re-index on the next heal) is judged by the shape gate alone. The code_vector tier has the same blind spot (its normalizer turns every string into `"s"`), so a code_vector pair also needs a token Jaccard ≥ `codeVectorTokenJaccard`; it is skipped when either side has no token MinHash. Both gates were fitted on the M2 replay (docs/milestones/M2.md): its near candidates labelled false had token Jaccard 0.56 or less and the true ones 0.84 or more (`nearTokenJaccard` 0.75); its code_vector candidates at cosine 0.98 or more were all labelled false and had token Jaccard 0.47 or less, while the M0 same-code pairs at 0.98 or more have 0.64 or more (`codeVectorTokenJaccard` 0.50, which drops none of them).

Compare only within kind family (function/method together; component; hook). Skip tests, fixtures, generated files, barrels and `duplicates.ignore`. Dismissed pairs never alert (they are read from `overlay.dismissals`, so they survive an index rebuild). Budget: < 1 in 10 hook alerts false; alerts on < 5% of edits. M2 measured the alert rate at 1.3% and the false rate at 45.2% (#32); #131 changed the rules (near-tier token gate, batch flow with a double-check against disk, section 14) and re-measured (`docs/milestones/M2.md`).

Seeded-case format (M2, #32; supersedes the one-line description in section 13): `evals/seeded-duplicates/cases.json`: 10 cases (3 with misleading names) each as `{ id, misleading, query, newCode | copyAs, expected: { tiers, situation } }`. `newCode` is written by hand; `copyAs` means "copy the existing function under this name" at run time, so no private code is committed. The `existing` symbol id and the target file of each case live only in git-ignored `evals/private/` (`GANTRY_PRIVATE_DIR`). `evals/m2/` and `evals/run-m2.ts` hold the M2 scripts (seeded cases, replay, labelling, sweep, timing).

Go seeded set (#223): `evals/seeded-duplicates-go/`, all hand-written and public. `base/` is a Go module (`go.mod` `module example.com/seeded`) with ten functions of at least 6 statements in `internal/` (string, time, slice, map and error helpers) and `web/slug.ts`, a TypeScript function with the logic of a Go one. `cases.json` is `[{ id, misleading, existing: "<path>#<name>", targetFile, newCode | copyAs, expected: { tiers } }]`: g01 to g03 are misleading (new name, restructured body: `["code_vector","semantic"]`), g04 to g06 verbatim copies under a new name through `copyAs` (`["exact"]`, via `renamedHash`), g07 to g10 edited copies (`["exact","near"]`). `negatives.json` is `[{ id, kind: "unrelated" | "cross_language", targetFile, newCode }]`: two unrelated functions of the same size and a Go copy of the logic of `web/slug.ts`; none may have a candidate. `seeded.test.ts` (in `pnpm check`, no model) copies `base/` to a temp git repo, indexes it, writes each case to its target, indexes the working layer, asks `findDuplicates(store, { symbol })` and asserts g04 to g10 each return `existing` first in an expected tier and the negatives return nothing; g01 to g03 need embeddings. `run.ts --embed` (not in `pnpm check`; needs the built CLI and the local model) does the same after `gantry embed` and prints `{ found, misleadingFound, perCase: [{ id, tier, score }] }` against the M2 bar (8 of 10, 2 of 3 misleading). A Go function whose body is a different implementation of the same behaviour embeds at about 0.8 to 0.94 of the original, below `codeVector`: such a match needs the semantic tier, which needs Go descriptions.

## 18. Reuse advice (deterministic)

"Reachable" = exported from the package's `exports` map (or `main`/`types` when no map). Situations: (1) reachable and caller's workspace depends on it → `inline: true`, action "Import it: import { X } from '<pkg>'"; (2) reachable, not a dependency → suggestion "Add the dependency" unless it creates a workspace cycle or a server/client boundary crossing (`"use client"` / server-only markers); (3) not reachable → suggestion "Export it or move it to a shared package"; (4) lives in another app → suggestion "Move it to a shared package"; (5) `nameFits=false` → suggestion "Consider renaming X; see untrusted_suggested_name", with the model's name only in the field `untrusted_suggested_name` (only if config `renameSuggestions` is true); (6) new import of an undeclared workspace or npm package, or deep import past `exports` → `inline: true`, action "Declare it in <pkg>/package.json".

Go (#223). The unit is the package, a directory of a module; its import path is `<module path>/<directory inside the module>`. A Go symbol is reachable when its name is exported (upper-case first letter; a method also needs an exported receiver type) and Go's `internal` rule lets the caller's package import the match's. For a caller that is a `.go` file and a Go match in another file: same package → situation 1, `inline: true`, "Call it: X is in the same package (<dir>)"; reachable and the same module, or a module the caller's `go.mod` requires → situation 1, `Import it: import "<module path>/<dir>"`; not reachable → situation 3, "Export it or move it to a shared package"; reachable in another module the caller does not require → situation 2, "Add the dependency: require <module path> in <dir>/go.mod, then import it" (situation 4, "Move it to a shared package (adding <module> would make a dependency cycle)", when that module already depends on the caller's). No advice for a caller that is not a `.go` file. TypeScript advice is unchanged.

Implementation notes (#29): the advice reads only the index. Reachability follows the stored `exports` edges from each exports-map entry file (or `types`/`main`/`src/index`), so `importPathFor(ws, match, store?)` takes the store as an optional third argument. The `"use client"` directive is recorded by the parser (`ParsedFile.directives`) and stored in `files.directives` (section 9, migration v3; no edge is emitted, `adviseReuse` reads the column through `store.effectiveFile`); server-only means a `server-only` import (an `ext:server-only` edge, so the package must be declared or installed) or a `.server.ts` suffix. A boundary crossing is a client caller and a server-only match. `checkImports` treats a bare name as a tsconfig alias when the index resolved that import line to a file, and reports a deep import only for workspace packages that have an `exports` map.
