The raw results, labels and seeded bindings live in `evals/private/` (git-ignored; may be a symlink to a directory outside the repo) or in the directory named by `GANTRY_PRIVATE_DIR`. ## Setup

- Index: `gantry init` on the copy, 14.8 s wall on a loaded machine (load average above 20).
- Descriptions: 3,511 functions needed a model description (1,860 more are templated). The headless worker (`describe.sync`, Haiku, low effort, batches of 40, four at a time) described 3,291 in 19 minutes; 220 (6.3%) failed validation twice and stay in the backlog as `failed`. Two of the ten seeded targets were among them (see below).
- Vectors: `gantry embed`, local model, 5,151 description vectors and 2,985 code vectors in about 10 minutes. No model call.
- Model usage, from `gantry usage` on the copy: `describe.sync` on Haiku, 105 worker calls, 3,521,060 input and 1,063,066 output tokens (estimated list price 8.84 USD, a figure the plan is not billed by). ## 1. Seeded duplicates

Ten cases in `evals/seeded-duplicates/cases.json`. Six are generic, self-written utility jobs (date formatting, "time ago" text, URL protocol check, XML escaping, dedupe by id, time zone name), three of them with a misleading name: a different name that says nothing about the job, and a different implementation. Four are verbatim copies of an existing function under a new name, made at run time from the copy; their definitions, queries and names are private, and the public file holds only their ids and expected advice. Which function each case duplicates, and where the new file goes, are in the private bindings only.

Each case runs three ways, in the order an agent meets them: `gantry_find_similar` with the draft code, `gantry_find_similar` with a one-sentence query, then the new file is written to a target file and the real PostToolUse hook runs on it. A case is found when the existing function comes back from any of the three; its advice is correct when the reuse situation for the target file equals the expected one (spec section 18; the expected situations were written down from the workspace dependency facts before the run).

| Case | Misleading name | Found by          | Tier (hook / code / query) | Situation got / expected | Correct |
| ---- | --------------- | ----------------- | -------------------------- | ------------------------ | ------- |
| s01  | yes             | query             | - / - / semantic           | 1 / 1                    | yes     |
| s02  | yes             | none              | - / - / -                  | 1 / 1                    | no      |
| s03  | yes             | query             | - / - / semantic           | 2 / 2                    | yes     |
| s04  | no              | query             | - / - / semantic           | 4 / 4                    | yes     |
| s05  | no              | query             | - / - / semantic           | 3 / 3                    | yes     |
| s06  | no              | query             | - / - / semantic           | 3 / 3                    | yes     |
| s07  | no              | hook, code, query | near / near / semantic     | 1 / 1                    | yes     |
| s08  | no              | hook, code, query | near / near / semantic     | 3 / 3                    | yes     |
| s09  | no              | hook, code, query | near / near / semantic     | 3 / 3                    | yes     |
| s10  | no              | hook, code        | near / near / -            | 1 / 1                    | yes     |

Result: **9 of 10** found with correct advice (misleading-name cases: **2 of 3**). By form: the hook finds 4 (the verbatim copies), the code form 4, the query form 8. All situations (1, 2, 3 and 4 of spec section 18) came out as expected for every found case.

What the numbers say:

- The one miss, s02, is the description step, not the search: the existing function never got a description (it is one of the 220 that failed validation twice), so it has no description vector and the query form cannot reach it. s10 has no description either but was found by the hook and the code form, which need none. Where a description exists the query form found the target in 8 of 8 cases, at rank 1 in 7 and rank 2 in one.
- The misleading-name cases are found by description vectors only. Their draft-code cosines to the existing function are 0.91, 0.84 and 0.87, below every `codeVector` value in the sweep except 0.91, which would catch one.
- The code form of `gantry_find_similar` and the hook cannot use code vectors for a new draft: the engine only reads stored vectors and a draft has none, so for new code they are exact and near only. A draft embedded on the fly would add the code-vector tier to the code form; that is a new feature, not done here.

## 2. Replay of real edits

The last 200 non-merge commits that touch `.ts` or `.tsx` (2026-10-29 to 2026-11-11), oldest first. For each commit the clone is put at its parent, the index is healed to it, and each changed file is written back at the commit version, as an Edit would, and passed through the real PostToolUse code path; then the edit is undone. 1,416 edits (934 outside test and end-to-end paths; 185 new files; 2 more were not indexable). Slowest hook run 1,456 ms under load, against the 1,500 ms budget.

For the sweep, every duplicate candidate of the changed functions was also collected at loose thresholds (`nearJaccard` 0.75, `codeVector` 0.90) with a freshly computed code vector for each changed function, because the hook as shipped only reads stored vectors and a new function has none. 159 distinct alerts (duplicate pairs and import lines) were labelled once each by a Sonnet pass with a fixed rubric (true when a careful reviewer would say the new function does the same job as the existing one and should have been reused; false for different jobs, boilerplate or shape-only similarity, or a move in progress; an import alert is true when the package really is not declared). When unsure the rubric says false, so the labels lean strict.

| At the defaults                             | Edits | Edits with an alert | Alert rate | Alerts | False | False rate |
| ------------------------------------------- | ----- | ------------------- | ---------- | ------ | ----- | ---------- |
| Chosen (`codeVector` 0.98)                  | 1,416 | 18                  | 1.3%       | 31     | 14    | 45.2%      |
| M0 values (`codeVector` 0.96)               | 1,416 | 21                  | 1.5%       | 35     | 18    | 51.4%      |
| Hook as shipped, stored vectors only (0.96) | 1,416 | 19                  | 1.3%       |        |       |            |

Breakdown at the chosen defaults:

| Kind                        | Alerts | True | False |
| --------------------------- | ------ | ---- | ----- |
| Undeclared-import line      | 14     | 14   | 0     |
| Duplicate, exact tier       | 6      | 1    | 5     |
| Duplicate, near tier        | 10     | 2    | 8     |
| Duplicate, code-vector tier | 1      | 0    | 1     |

The false duplicate alerts have three causes, from the labeller's one-line reasons (the 14 count is exact, the grouping is approximate): about 6 are the first half of a move (the new file is written before the old one is edited, so for one edit the function exists twice); most of the rest are the near tier matching two small functions that differ only in their string literals (the shape stream ignores literals, so the Jaccard is 1.00 for any two functions of the same shape, for example two if-chains that map different statuses to different text); and code-vector pairs of similar scaffolding, 98 candidates at 0.91 or above of which 1 was a true duplicate, none at 0.93 or above. The import check was right every time (14 of 14).

**Operator spot-check (2026-11-15).** Of the 20 sampled alerts, the operator agreed with the label on 11 (all 10 labelled false and 1 of the 2 duplicate alerts labelled true), was unsure on 1 (a duplicate alert labelled true) and disagreed on 8. All 8 disagreements are undeclared-import alerts labelled true that are false: at the alert's commit the workspace's package.json declares each package, because the same commit adds it. The replay wrote only the .ts/.tsx files of a commit, so the index's workspace records were stale, and the labeller was shown package.json at the parent commit, so it made the same mistake. Section 5 re-labels the import alerts against package.json at the alert's commit: all 14 are false, so the false rate at the chosen defaults was 90.3% (28 of 31), not 45.2%.

Twenty of the 31 alerts raised at the chosen defaults for the operator to spot-check, by opaque id (the first 8 hex digits of a hash of the alert key; the key-to-id map is in the private directory; drawn by `evals/m2/spotcheck.ts`): 148ac408, 191ff878, 1faff441, 27272b0c, 29adabef, 2c2689a7, 315b3c6f, 360eed92, 47081381, 494a2778 (labelled true); 0ababc72, 328654cd, 3b031fe6, 48ca9fe6, 5589ae25, 5a97bfda, 604ba676, 6c9e6be5, 8e65fad0, 9f8f9532 (labelled false).

## 3. Threshold sweep

`nearJaccard` 0.80 to 0.90 and `codeVector` 0.91 to 1.00 in 0.01 steps (110 settings), each scored for alert rate, false rate and seeded recall; `semantic` 0.55 to 0.65 on its own. Full grid: `pnpm tsx evals/m2/sweep.ts`.

- **Neither budget-fitting rule can be satisfied.** Alert rate stays between 1.1% and 4.3% over the grid (always under 5%), but the false rate is between 41.4% and 83.8%; no setting is under 10%.
- Seeded recall is 9 of 10 at every setting (the hook and code form depend on `nearJaccard` only through scores of 1.0 for these copies; the query form does not use the thresholds).
- `nearJaccard`: flat. From 0.80 to 0.84 nothing changes; raising it to 0.86 or 0.87 removes one false alert, to 0.88 and above removes one true alert. Kept at **0.85** (one alert is not evidence).
- `codeVector`: false alerts fall as it rises (0.96: 18 false of 35; 0.98: 14 of 31; 0.99: 13 of 30) and no true duplicate sits above 0.93. The M0 hand-written code pairs (`docs/spikes/embed/pairs.jsonl`, 15 same and 15 different) give: 0.96 finds 15 of 15 with 1 of 15 false positives; **0.98 finds 14 of 15 with none**; 0.99 finds 12 of 15 with none. Chosen **0.98**: it removes 4 of the 4 false alerts that sit between 0.96 and 0.98 and keeps the M0 recall at 93%. Going to 0.99 removes one more false alert in 1,416 edits and costs two more M0 pairs.
- `semantic`: the real-description check is the cosine between each seeded query and the target's description. Of the 8 targets that have a description, all 8 are at or above 0.77, so recall is 8 of 8 from 0.55 to 0.65. The number of queries whose nearest other description is also at or above the threshold falls from 8 at 0.58 to 7 at 0.59 and 0.60, 6 at 0.61 to 0.63 and 4 at 0.64 and 0.65. The M0 description pairs say the opposite for raising it: 0.60 finds 11 of 15 with 1 of 15 false positives, 0.65 finds 6 of 15 with the same false positive. Kept at **0.60**. The threshold only gates the description-to-description tier of the duplicate engine; neither the hook nor `gantry_find_similar` applies it to a draft, so the seeded and replay numbers do not depend on it. It was calibrated on paraphrases and fitted only on 8 query-to-description cosines, so treat it as weakly supported.

Defaults after M2: `nearJaccard` 0.85, `codeVector` **0.98** (was 0.96), `semantic` 0.60. `packages/core/src/config/index.ts` and spec sections 5 and 17 are updated.

## 4. Pre-commit timing

A real `git commit` of 20 changed `.ts`/`.tsx` files (staged at the version before their latest change, so about 10 functions are not described yet), through a pre-commit script that runs `gantry hook pre-commit` as the installed hooks do. Each run starts from a fresh copy of the data dir. Three runs per mode.

| Mode                          | Wall time per run (ms)   | Max (ms) | Worker calls (3 runs) | Functions described |
| ----------------------------- | ------------------------ | -------- | --------------------- | ------------------- |
| `off` (the default)           | 1,520 / 1,269 / 1,267    | 1,520    | 0                     | 0                   |
| `timeboxed`, `budgetMs` 8000  | 7,815 / 8,148 / 8,138    | 8,148    | 3                     | 24                  |
| `timeboxed`, `budgetMs` 20000 | 12,796 / 13,261 / 11,143 | 13,261   | 6                     | 33                  |

- **"No commit waits more than 8 s" is met in the default `off` mode** (1.3 to 1.5 s for 20 files) **and only partly in `timeboxed` mode** (numbers below).
- **For the operator:** in `timeboxed` mode a commit waits up to the budget. With the budget at 8000 the wait is 7.8 to 8.15 s, so slightly over 8 s on two of three runs (the child is killed at the deadline and git adds its own time). With the budget at the new default of 20000 the 20-file commit waited 11.1 to 13.3 s, because the roughly 10 new functions took two worker calls; a larger commit would wait up to 20 s. The M0 estimate (3.3 s cold start plus 0.4 s per function) fits: 10 functions would be about 7 s for one call, and a second worker call (probably the retry of descriptions that failed validation) adds another cold start. Whether a 13 to 20 s wait is acceptable for an opt-in mode is the operator's call; `timeboxed` stays opt-in.

## 5. Re-run after the #131 rule changes

Issue #131. Same 200 commits, same throwaway copies (re-copied data dir, so the original index stays as it was), same seeded cases, same labelling rubric and labeller (one Sonnet pass at low effort, told to answer false when unsure). Raw results are in the private directory; reprint with `GANTRY_PRIVATE_DIR=<private dir> pnpm tsx evals/run-m2.ts <copy>`.

What changed in the product (spec sections 14 and 17):

1. **Batch flow in the hooks.** PostToolUse is now only the trigger: it records the edited file (sources, and also a package.json, a tsconfig or `pnpm-workspace.yaml`) in the session's batch and re-indexes a source file. The checks run once the batch settles, at the Claude Code `Stop` hook (end of the turn): every touched file is re-indexed together, which re-reads the workspaces, dependencies and tsconfig paths from disk; then the duplicate and import checks run.
2. **Double-check against disk** just before a finding is shown: a duplicate is dropped when the matched function is gone from its file or no longer matches, an undeclared-import finding when the workspace's or the root's package.json on disk now declares the package.
3. **Near tier keeps literals.** A second MinHash over the exact token stream (literals, property names and callees kept, the function's own name as `$0`); a near pair needs token Jaccard >= `nearTokenJaccard` 0.75 besides the shape gate, and the score is the token Jaccard.
4. **Code-vector tier keeps literals too.** A code-vector pair also needs token Jaccard >= `codeVectorTokenJaccard` 0.50 (the code normalizer turns every string into `"s"`).

What changed in the eval: the replay applies each commit as one batch, as an agent's turn would leave it: every changed file is written at its commit version (the same 1,416 .ts/.tsx edits, plus 400 other files such as package.json), the 16 deleted files are removed without a hook (as a shell `rm` would be), the checks run on the post-batch state with the double-check, and the real Stop hook settles the batch: the built CLI in its own process with the real 1,500 ms budget, as Claude Code runs it. A finding the Stop hook did not show (cut off at the budget, or its file left in the batch for a later Stop, which the replay does not run because it undoes the commit) counts as not shown. The labeller is shown the existing function and the nearest package.json as they are at the alert's commit. All 143 distinct candidates the double-check kept at the loose thresholds were labelled afresh (18 Sonnet calls, 326,313 input and 8,235 output tokens); the 14 import alerts of the first run were re-labelled the same way (2 calls).

| Replay, at the defaults                                   | Edits | Edits with an alert | Alert rate | Alerts | True | False | False rate |
| --------------------------------------------------------- | ----- | ------------------- | ---------- | ------ | ---- | ----- | ---------- |
| #32 run, #32 labels                                       | 1,416 | 18                  | 1.3%       | 31     | 17   | 14    | 45.2%      |
| #32 run, import alerts re-labelled at the alert's commit  | 1,416 | 18                  | 1.3%       | 31     | 3    | 28    | 90.3%      |
| #131: batch flow and double-check, no token gates         | 1,416 | 11                  | 0.8%       | 14     | 2    | 12    | 85.7%      |
| #131: plus the near-tier token gate                       | 1,416 | 6                   | 0.4%       | 8      | 2    | 6     | 75.0%      |
| #131: plus the code-vector token gate (the shipped rules) | 1,416 | 2                   | 0.1%       | 2      | 2    | 0     | 0.0%       |

True alerts go from 3 to 2 (all 3 are duplicate alerts; the 14 import alerts counted true in the first row are false). The numbers in the last three rows are what the Stop hook showed at the end of each batch; they are the same when the findings it did not show (below) are counted in, because none of those passes the default gates.

Seeded duplicates with the new hooks (the seeded runner now sends a session id and runs the Stop hook after the write): **9 of 10** found with correct advice, misleading-name **2 of 3**, the same cases as in section 1 (the miss is still s02, which has no description).

What the numbers say:

- The batch flow removes every import alert: in each of them the same commit declares the dependency, so after the batch re-index (and again in the double-check) the package is declared. It also removes the first half of a move: when a commit moves a function, the old copy is edited away or deleted in the same batch, so there is no candidate any more or the double-check drops it (1 candidate was dropped by the double-check; the others never became candidates). One alert labelled true in the #32 run is gone for that reason: the same commit changed the matched function's file and the match no longer exists, so it was a move.
- What is left without the token gates is 12 false alerts out of 14 (the code-vector gate alone leaves 10 of 12), all pairs of small functions that map different strings (status to label, step to text): the near tier at shape Jaccard 1.00 and the code-vector tier at cosine 0.98 to 0.99, both blind to literals. With literals kept the false near candidates have token Jaccard 0.19 to 0.56 and the true near one 0.84; the code-vector candidates at cosine 0.98 or more (all labelled false) have token Jaccard 0.11 to 0.47.
- The two alerts left are both true duplicates (one exact, one near). The one true alert of the #32 run that is gone was a move (above), so the true-alert count goes from 3 to 2 without a true duplicate being missed.
- Thresholds: `nearTokenJaccard` gives 0 false alerts anywhere from 0.60 to 0.80 (2 alerts) and loses one true alert at 0.85; 0.75 sits between the false (0.56 or less) and the true (0.84 or more) candidates. `codeVectorTokenJaccard` gives 0 false from 0.50 up; at 0.30 and 0.40 one false alert is left. Held-out check on the M0 hand-written code pairs (`evals/m2/pairs.ts`; not used to fit either gate): the token gate at 0.75 keeps 14 of the 15 same-code pairs and 0 of the 15 different ones; the whole near tier (shape gate, token gate, 6-statement floor) keeps 6 of the 6 same pairs that have 6 or more statements and 0 of the 3 such different pairs. At codeVector 0.98 the code-vector tier finds 14 of 15 same pairs with none flagged, with or without the 0.50 token gate (the same pairs at 0.98 or more have token Jaccard 0.64 or more). 66 of the 110 (nearJaccard, codeVector) settings now meet both budgets, against 0 before.
- **Caveat: the after numbers rest on 2 alerts.** 0 false out of 2 meets the budget as measured, but it is a small sample, and the token gates were fitted on the same labelled candidates they are scored on (as the codeVector threshold was in section 3). The replay found 3 candidates labelled true in all: the two shown, and one code-vector pair at cosine 0.92, below the 0.98 threshold before and after.
- **Stop hook time** (the built CLI, its own process, the real 1,500 ms budget, on a machine also running the replay): 205 ms at the median over the 200 batches, 491 ms at the 90th percentile, 1,224 ms at most; **none at or over the budget**. 8 of the 200 batches (of 8 to 108 edited files) did not finish in one Stop: the hook stopped starting steps before the budget and left 193 edits in the batch for the next Stop. The replay counts their findings as not shown. They hold 6 loose candidates, none of which passes the default gates, so no alert was lost; re-scored with them counted as lost, the numbers above do not change (2 alerts, 0 false, 0.1% of edits, true alerts 2 of 2; seeded recall 9 of 10, re-run with the final hooks). An earlier build of this fix, without the chunked re-index and the step-time guard, was cut off at the budget on 3 to 4 batches (1.55 to 2.8 s); that is what the two were added for.
- Trigger (PostToolUse) time, in process: the slowest trigger of a batch took 448 ms at the median and 651 ms at most, none over the budget. The trigger writes the batch row before it re-indexes and marks the row indexed only when its index finishes; a trigger cut off at the budget leaves the row unmarked and the Stop hook indexes the file (added after the replay above, which had no trigger over the budget, so its numbers are unchanged).

## Method limits

- The seeded queries were written after reading the existing code, so the query-form recall is optimistic for an agent that has not read it.
- The labelling rubric shows the labeller the tier and the score of each alert, and the labeller is one Sonnet pass at low effort, told to answer false when unsure. The labels lean strict and are not blind to the tool's own confidence.
- The sweep and the 159 labels cover the alerts found at the loose replay thresholds. The operator's spot-check sample is the 20 drawn from the 31 alerts at the defaults, not from the 159.
- "Correct advice" is the situation that `adviseReuse` gives for the existing function and the target file, compared with the expected situation. It is not read from the tools' output, although `gantry_find_similar` and the hook call the same function.
- The seeded cases cannot test `codeVector`: a draft is never embedded, so the hook and the code form only run the exact and near tiers on it. The code-vector tier is judged by the replay and the M0 pairs only.

## Deviations and caveats

- The replay writes each changed file at its commit version in diff order. A commit that moves code (new file first, old file edited second) shows the duplicate for one edit; that is how an agent working in that order would see it, and it is counted as false by the rubric.
- Vectors for the replay come from the HEAD index (they are keyed by function content); a function that no longer exists at HEAD has none, which understates the vector tiers for old commits. The fresh vector for each edited function was computed for the sweep.
- Labels come from one Sonnet pass per alert without a human check; the operator's 20-alert spot check above is the only human review.
- The describe spike's 9 of 200 descriptions graded 0 were not re-checked here, and the Linux x64 sqlite-vec result is not recorded (the operator has not run it).

## Follow-ups

- **False-alert budget**: missed in #32, met in #131 (section 5) on a small sample (2 alerts). Worth re-measuring on a longer replay or a second test bed once one is available.
- Optional: embed the draft in `gantry_find_similar`'s code form so the code-vector tier works for new code (the draft cosines for the misleading cases were 0.84 to 0.91, so it would not have found them at 0.98).
- Optional: retry the 6% of descriptions that fail validation twice (they are invisible to the semantic tier).
