# M2 evals: seeded duplicates, false-alert budget, threshold tuning

Issue #32. Test bed: the private TypeScript monorepo used for M1 (1,531 files, 9,042 symbols, 5,710 function-like), copied into a throwaway directory; the original clone was not touched. Per the public-repo rule this report holds aggregate numbers and opaque ids only: counts, rates, timings, thresholds.

Reprint every table from the stored results (the raw results, labels and seeded bindings live in a git-ignored directory outside the repo, named by `GANTRY_PRIVATE_DIR`):

```sh
pnpm build
GANTRY_PRIVATE_DIR=<private dir> pnpm tsx evals/run-m2.ts <copy>
GANTRY_PRIVATE_DIR=<private dir> CLAUDE_PLUGIN_DATA=<data dir> pnpm tsx evals/run-m2.ts <copy> --rerun seeded|replay|label|timing
```

`evals/m2/describe-copy.ts` describes the copy's backlog with the headless worker (four calls at a time) and `gantry embed` fills the vectors; both must have run before the steps above. `evals/m2/sweep.ts` and `evals/m2/pairs.ts` print the threshold sweep and the M0 pair check.

## Setup

- Index: `gantry init` on the copy, 14.8 s wall on a loaded machine (load average above 20).
- Descriptions: 3,511 functions needed a model description (1,860 more are templated). The headless worker (`describe.sync`, Haiku, low effort, batches of 40, four at a time) described 3,291 in 19 minutes; 220 (6.3%) failed validation twice and stay in the backlog as `failed`. Two of the ten seeded targets were among them (see below).
- Vectors: `gantry embed`, local model, 5,151 description vectors and 2,985 code vectors in about 10 minutes. No model call.
- Model usage, from `gantry usage` on the copy: `describe.sync` on Haiku, 105 worker calls, 3,521,060 input and 1,063,066 output tokens (estimated list price 8.84 USD, a figure the plan is not billed by). Alert labelling on Sonnet (low effort; counted by the labelling script, not in `gantry usage`): 20 calls, 300,275 input and 8,880 output tokens. Pre-commit timing runs on `timeboxed`: 9 worker calls, 45,461 input and 5,364 output tokens (two runs were cut off at the 8,000 ms deadline before the call reported usage).

## 1. Seeded duplicates

Ten cases in `evals/seeded-duplicates/cases.json`. Six are hand-written code (three with misleading names: a different name that says nothing about the job, and a different implementation), four are verbatim copies of the existing function under a new name, made at run time from the copy (no private code is committed). Which function each case duplicates, and where the new file goes, are in the private bindings only.

Each case runs three ways, in the order an agent meets them: `gantry_find_similar` with the draft code, `gantry_find_similar` with a one-sentence query, then the new file is written to a target file and the real PostToolUse hook runs on it. A case is found when the existing function comes back from any of the three; its advice is correct when the reuse situation for the target file equals the expected one (spec section 18; the expected situations were written down from the workspace dependency facts before the run).

| Case | Misleading name | Found by          | Tier (hook / code / query) | Situation got / expected | Correct |
| ---- | --------------- | ----------------- | -------------------------- | ------------------------ | ------- |
| s01  | yes             | query             | - / - / semantic           | 1 / 1                    | yes     |
| s02  | yes             | none              | - / - / -                  | 1 / 1                    | no      |
| s03  | yes             | query             | - / - / semantic           | 2 / 2                    | yes     |
| s04  | no              | query             | - / - / semantic           | 4 / 4                    | yes     |
| s05  | no              | query             | - / - / semantic           | 3 / 3                    | yes     |
| s06  | no              | query             | - / - / semantic           | 3 / 3                    | yes     |
| s07  | no              | hook, code, query | near / near / semantic     | 1 / 1                    | yes     |
| s08  | no              | hook, code, query | near / near / semantic     | 3 / 3                    | yes     |
| s09  | no              | hook, code, query | near / near / semantic     | 3 / 3                    | yes     |
| s10  | no              | hook, code        | near / near / -            | 1 / 1                    | yes     |

Result: **9 of 10** found with correct advice (misleading-name cases: **2 of 3**). By form: the hook finds 4 (the verbatim copies), the code form 4, the query form 8. All situations (1, 2, 3 and 4 of spec section 18) came out as expected for every found case.

What the numbers say:

- Both misses are the description step, not the search. In s02 and s10 the existing function never got a description (it was one of the 220 that failed validation twice), so it has no description vector and the query form cannot reach it. Where a description exists the query form found the target in 8 of 8 cases, at rank 1 in 7 and rank 2 in one.
- The misleading-name cases are found by description vectors only. Their draft-code cosines to the existing function are 0.93, 0.82 and 0.87, below every `codeVector` value in the sweep except 0.91 and 0.92, which would catch one.
- The code form of `gantry_find_similar` and the hook cannot use code vectors for a new draft: the engine only reads stored vectors and a draft has none, so for new code they are exact and near only. A draft embedded on the fly would add the code-vector tier to the code form; that is a new feature, not done here.
- The queries were written by the author of the cases, who had read the existing code, so the query-form recall is optimistic for an agent that has not.

## 2. Replay of real edits

The last 200 non-merge commits that touch `.ts` or `.tsx` (2026-10-29 to 2026-11-11), oldest first. For each commit the clone is put at its parent, the index is healed to it, and each changed file is written back at the commit version, as an Edit would, and passed through the real PostToolUse code path; then the edit is undone. 1,416 edits (934 outside test and end-to-end paths; 185 new files; 2 more were not indexable). Slowest hook run 1,456 ms under load, against the 1,500 ms budget.

For the sweep, every duplicate candidate of the changed functions was also collected at loose thresholds (`nearJaccard` 0.75, `codeVector` 0.90) with a freshly computed code vector for each changed function, because the hook as shipped only reads stored vectors and a new function has none. 159 distinct alerts (duplicate pairs and import lines) were labelled once each by a Sonnet pass with a fixed rubric (true when a careful reviewer would say the new function does the same job as the existing one and should have been reused; false for different jobs, boilerplate or shape-only similarity, or a move in progress; an import alert is true when the package really is not declared). When unsure the rubric says false, so the labels lean strict.

| At the defaults                             | Edits | Edits with an alert | Alert rate | Alerts | False | False rate |
| ------------------------------------------- | ----- | ------------------- | ---------- | ------ | ----- | ---------- |
| Chosen (`codeVector` 0.98)                  | 1,416 | 18                  | 1.3%       | 31     | 14    | 45.2%      |
| M0 values (`codeVector` 0.96)               | 1,416 | 21                  | 1.5%       | 35     | 18    | 51.4%      |
| Hook as shipped, stored vectors only (0.96) | 1,416 | 19                  | 1.3%       |        |       |            |

Breakdown at the chosen defaults:

| Kind                        | Alerts | True | False |
| --------------------------- | ------ | ---- | ----- |
| Undeclared-import line      | 14     | 14   | 0     |
| Duplicate, exact tier       | 6      | 1    | 5     |
| Duplicate, near tier        | 10     | 2    | 8     |
| Duplicate, code-vector tier | 1      | 0    | 1     |

The false duplicate alerts have three causes, from the labeller's one-line reasons (the 14 count is exact, the grouping is approximate): about 6 are the first half of a move (the new file is written before the old one is edited, so for one edit the function exists twice); most of the rest are the near tier matching two small functions that differ only in their string literals (the shape stream ignores literals, so the Jaccard is 1.00 for any two functions of the same shape, for example two if-chains that map different statuses to different text); and code-vector pairs of similar scaffolding, 98 candidates at 0.91 or above of which 1 was a true duplicate, none at 0.93 or above. The import check was right every time (14 of 14).

Twenty alerts for the operator to spot-check, by opaque id (the id is the first 8 hex digits of a hash of the alert key; the key-to-id map is in the private directory): 148ac408, 191ff878, 1faff441, 27272b0c, 29adabef, 2c2689a7, 315b3c6f, 360eed92, 433aa72c, 47081381 (labelled true); 043af0c7, 07070e93, 072c196a, 0747d481, 08db9fff, 098b68d0, 0ababc72, 0fa1ca1e, 109d85de, 139afa6a (labelled false).

## 3. Threshold sweep

`nearJaccard` 0.80 to 0.90 and `codeVector` 0.91 to 1.00 in 0.01 steps (110 settings), each scored for alert rate, false rate and seeded recall; `semantic` 0.55 to 0.65 on its own. Full grid: `pnpm tsx evals/m2/sweep.ts`.

- **Neither budget-fitting rule can be satisfied.** Alert rate stays between 1.1% and 4.3% over the grid (always under 5%), but the false rate is between 41.4% and 83.2%; no setting is under 10%.
- Seeded recall is 9 of 10 at every setting (the hook and code form depend on `nearJaccard` only through scores of 1.0 for these copies; the query form does not use the thresholds).
- `nearJaccard`: flat. From 0.80 to 0.84 nothing changes; raising it to 0.86 or 0.87 removes one false alert, to 0.88 and above removes one true alert. Kept at **0.85** (one alert is not evidence).
- `codeVector`: false alerts fall as it rises (0.96: 18 false of 35; 0.98: 14 of 31; 0.99: 13 of 30) and no true duplicate sits above 0.93. The M0 hand-written code pairs (`docs/spikes/embed/pairs.jsonl`, 15 same and 15 different) give: 0.96 finds 15 of 15 with 1 of 15 false positives; **0.98 finds 14 of 15 with none**; 0.99 finds 12 of 15 with none. Chosen **0.98**: it removes 4 of the 4 false alerts that sit between 0.96 and 0.98 and keeps the M0 recall at 93%. Going to 0.99 removes one more false alert in 1,416 edits and costs two more M0 pairs.
- `semantic`: the real-description check is the cosine between each seeded query and the target's description. Of the 8 targets that have a description, all 8 are at or above 0.68, so recall is 8 of 8 from 0.55 to 0.65. The number of queries whose nearest other description is also at or above the threshold falls from 8 at 0.58 to 5 at 0.59 and stays at 5 to 0.65. The M0 description pairs say the opposite for raising it: 0.60 finds 11 of 15 with 1 of 15 false positives, 0.65 finds 6 of 15 with the same false positive. Kept at **0.60**. The threshold only gates the description-to-description tier of the duplicate engine; neither the hook nor `gantry_find_similar` applies it to a draft, so the seeded and replay numbers do not depend on it. It was calibrated on paraphrases and fitted only on 8 query-to-description cosines, so treat it as weakly supported.

Defaults after M2: `nearJaccard` 0.85, `codeVector` **0.98** (was 0.96), `semantic` 0.60. `packages/core/src/config/index.ts` and spec sections 5 and 17 are updated.

## 4. Pre-commit timing

A real `git commit` of 20 changed `.ts`/`.tsx` files (staged at the version before their latest change, so about 10 functions are not described yet), through a pre-commit script that runs `gantry hook pre-commit` as the installed hooks do. Each run starts from a fresh copy of the data dir. Three runs per mode.

| Mode                          | Wall time per run (ms)   | Max (ms) | Worker calls (3 runs) | Functions described |
| ----------------------------- | ------------------------ | -------- | --------------------- | ------------------- |
| `off` (the default)           | 1,520 / 1,269 / 1,267    | 1,520    | 0                     | 0                   |
| `timeboxed`, `budgetMs` 8000  | 7,815 / 8,148 / 8,138    | 8,148    | 3                     | 24                  |
| `timeboxed`, `budgetMs` 20000 | 12,796 / 13,261 / 11,143 | 13,261   | 6                     | 33                  |

- **"No commit waits more than 8 s" is met in the default `off` mode**: 1.3 to 1.5 s for 20 files.
- **For the operator:** in `timeboxed` mode a commit waits up to the budget. With the budget at 8000 the wait is 7.8 to 8.15 s, so slightly over 8 s on two of three runs (the child is killed at the deadline and git adds its own time). With the budget at the new default of 20000 the 20-file commit waited 11.1 to 13.3 s, because the roughly 10 new functions took two worker calls; a larger commit would wait up to 20 s. The M0 estimate (3.3 s cold start plus 0.4 s per function) fits: 10 functions would be about 7 s for one call, and a second worker call (probably the retry of descriptions that failed validation) adds another cold start. Whether a 13 to 20 s wait is acceptable for an opt-in mode is the operator's call; `timeboxed` stays opt-in.

## Deviations and caveats

- The replay writes each changed file at its commit version in diff order. A commit that moves code (new file first, old file edited second) shows the duplicate for one edit; that is how an agent working in that order would see it, and it is counted as false by the rubric.
- Vectors for the replay come from the HEAD index (they are keyed by function content); a function that no longer exists at HEAD has none, which understates the vector tiers for old commits. The fresh vector for each edited function was computed for the sweep.
- Labels come from one Sonnet pass per alert without a human check; the operator's 20-alert spot check above is the only human review.
- The describe spike's 9 of 200 descriptions graded 0 were not re-checked here, and the Linux x64 sqlite-vec result is not recorded (the operator has not run it).

## Follow-ups

- **False-alert budget (missed).** Needs a rule change, not a threshold change, so it is outside this issue: (1) make the near tier compare more than the shape stream (literals or identifiers) so that same-shaped functions with different strings stop matching at score 1.00; (2) do not alert on the first half of a move, for example by checking whether the existing copy is edited or removed in the same turn; (3) re-run `evals/run-m2.ts` and aim at under 10% false. Suggested title: "Duplicate alerts: cut the near-tier false positives and re-measure against the M2 replay".
- Optional: embed the draft in `gantry_find_similar`'s code form so the code-vector tier works for new code (the draft cosines for the misleading cases were 0.82 to 0.93, so it would not have found them at 0.98).
- Optional: retry the 6% of descriptions that fail validation twice (they are invisible to the semantic tier).
