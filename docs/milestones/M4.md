# M4 regression: Refresh on request

Issue #40. The explorer is not live (spec section 11 (c)): there is no file watcher and no push. Every explorer API request runs a cheap check for files changed since the index was last brought up to date, the status bar then says "Out of date (n files)", and the Refresh button in the top bar re-indexes those files and reloads the view in place. Everything here comes from one script, `evals/bench/m4.ts`, run against the built explorer (`pnpm build` first). Per the public-repo rule this report holds aggregate numbers only: counts, timings, yes/no. The real-repo run used the private TypeScript monorepo from the M3 report (1,541 files, 9,042 symbols, 11 workspaces); its names, paths and layouts stay outside this repository. The same script also ran on the public `fixtures/pnpm-turbo`, which anyone can re-check.

```sh
pnpm build
pnpm tsx evals/bench/m4.ts <repo> --out <private dir>   # a git clone of <repo> is edited, never <repo> itself
pnpm tsx evals/bench/m4.ts fixture                      # public data only
```

The script clones `<repo>` into a scratch directory (set `TMPDIR` to choose where), puts the data directory (`CLAUDE_PLUGIN_DATA`) there too, runs `gantry init` and `gantry map --no-open`, and opens the project map at the Functions level in Chromium. For each edit count (1, 5 and 20 files, three runs each) it appends one new exported function to that many source files of the clone, then:

1. **marker**: one `GET /api/meta`; `stale.files` must equal the number of edited files. The browser then gets a `focus` event (the explorer fetches `/api/meta` again when its tab comes back), and the status bar must read "Out of date (n files)".
2. **refresh**: clicks Refresh and records the server's own `ms` from `POST /api/refresh`, the time from the click to the response, and the time from the click until the canvas has drawn the new layout with every new function outlined ("shows the new code").
3. **moved**: compares the layout position of every node outside the edited files before and after (the canvas's `gantry:probe` hook with `{ positions: true }`). The done-when is zero.

`git status` of the source repository is compared before and after (unchanged in every run below).

## How it works

- **Stale check** (`staleFiles` in `core/heal`): the same test as lazy refresh, without writing anything: `git status --porcelain=v1 -z` plus each dirty file's mtime against the stored row, working rows for files that git no longer lists, and the `git diff` of a pending heal when `HEAD` moved. `/api/meta` and `/api/view/:id` answer with `stale: { files }`.
- **Refresh** (`POST /api/refresh`, same token, Origin and Host checks, JSON only): heal when `HEAD` moved, then `refreshWorking`; one at a time per server, a second request gets the same answer. It returns the counts the spec names plus the ids of the changed files and of the added, changed and removed functions, which the web outlines until the next refresh.
- **Keeping positions** on the project map, whose treemap has no saved positions (it follows from the function counts): after a refresh the same picture (view, focus, level, filters) reuses the previous workspace boxes as they were, gives every node that was there its previous treemap weight, and keeps the count-based structure decisions (root-file groups, lifted folders). So a changed file keeps its cell and only its own functions are laid out again; added nodes appear inside their parent. The camera stays where the user left it. Re-layout, or any change of view, level, focus or filters, lays out from scratch. Flat graphs keep their positions through the `layouts` table, as before.

## Found and fixed while measuring

- **Re-indexing spent most of its time deleting search rows.** A targeted re-index removed each symbol's `fts_symbols` row with a delete by the unindexed `symbol_id` column, a full scan of the table per symbol. The indexer now reads the rowids once per write batch and deletes by rowid. A CPU profile of 20-file refreshes on the private repo put about 290 ms per refresh in those deletes; after the change they no longer show up. The PostToolUse hook and lazy refresh use the same code and gain the same way.
- **`/api/meta` loaded every symbol and edge to count them.** It now counts in SQL (4 ms instead of 80 ms or more on the private repo), which matters because the explorer fetches it again whenever its tab gets focus back.
- **A grouping flip moved 188 cells.** One added function in a loose file next to a big folder changed whether those files were gathered in a "(root files)" cell, which reflowed the folder. The structure decisions are now kept across a refresh (above); after the fix, 0 cells moved.

- **Review fixes.** The stale check's git calls now pass `--no-optional-locks`, so the `git status` that runs on every request never takes `.git/index.lock` while the user commits or rebases. A test that re-indexes more than one write batch of files (edits, renames, removals, additions, a hook-style single-file re-index in between, then a revert) found search rows left behind for working-layer symbols that were renamed away or reverted; those are now removed with their working rows, and the test checks for duplicates, orphans and untouched rows.

## Caveats

- "Nothing moved" is measured outside the edited files. Inside an edited file the cell keeps its place, but its functions (the unchanged ones too) are laid out again around the new one; the bench does not compare those, and it did not measure a run that adds or deletes a whole file (an added file is placed inside its folder, which reflows that folder's cells).
- The refresh highlight comes from what the refresh itself changed. If something else brought the index up to date first (the PostToolUse hook after an edit by Claude, or an MCP call's lazy refresh), the refresh finds nothing to do and outlines nothing, although the view still shows the new code.
- A kept layout stays kept for the same picture: a later re-layout of that picture that the canvas starts itself (after a large resize) reuses it too. Only the Re-layout button, or a change of view, level, focus or filters, lays out from the current counts.

- The kept layout drifts from the true function counts as refreshes pile up (a file that gained ten functions keeps its old cell size). Re-layout, or changing the level, view or filters, starts from the current counts again.
- The ego (bow-tie) view and the 3D map are laid out from their data every time; a refresh reloads them in place but does not pin their positions. The list renderer marks added and changed functions; the bow-tie does not outline them.
- Most of the remaining server time is the importer check of a targeted re-index: it resolves the edges of every file to find importers whose edges changed (inherent to how lazy refresh works since M1, not new here).
