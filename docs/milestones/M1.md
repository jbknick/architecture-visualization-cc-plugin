# M1 regression report: structural graph

Issue #20. Test bed: a private TypeScript monorepo (Devprentice), cloned read-only into a throwaway directory with dependencies installed. Per the public-repo rule this report holds aggregate numbers only: counts, percentages and timings.

Reproduce on any clean throwaway clone (the script edits one file and stashes it, then restores and cleans the clone):

```sh
pnpm build
pnpm tsx evals/bench/m1.ts <path-to-clone> [--runs 3] [--calcom <path>] [--skip-tests]
```

The script runs the built CLI with a fresh `CLAUDE_PLUGIN_DATA` per cold run, prints the table below and exits non-zero if a done-when line is missed. Its threshold and table logic is unit-tested in `evals/bench/m1-report.test.ts`.

## Deviations from the issue text

- The test bed has 1,531 indexable files, not 2,000. The "2,000 files in under 2 minutes" line is judged by the time for the whole repo, which is far under the limit. A 5,000-file repo (Cal.com, no install) also finished in about 11 s, which supports the claim at the stated size.
- "Unresolved %" is computed over distinct (file, specifier) pairs that are either resolved to a repo file or unresolved. Specifiers classed as generated (for example router codegen output) or excluded by config are counted apart, so they do not inflate the miss rate. Bare specifiers with no declared dependency also count as unresolved, which makes the figure conservative.
- To report that split, `IndexResult` gained a `specifierCounts` field (resolution class counts), a small change in `packages/core/src/indexer.ts`. No other module changed.
- The git-flow check in the bench uses an edit plus `git stash push -u` and compares an in-process graph dump (same formatting as `gantry index --dump`, checked equal to the CLI dump on the clean store) before and after. It does not call `index --dump` after the stash, because that would rebuild the graph and hide a healing bug.

## Known limits

- The refresh after one edit took about 2.3 s on a loaded machine, against 110 ms for a search on a clean tree. The cost was not profiled; it includes process start, the HEAD check, and re-indexing the edited file together with its importers. It is within the M1 intent but not instant. A profile belongs with the M3 hook work, where the PostToolUse path needs it. No done-when line sets a refresh budget.
- Call-site mapping is bounded by the lack of type information (see `docs/spikes/oxc.md`): about half of call sites map to a binding, the rest are locals or globals. Unchanged by this report.
- Timings are from one machine under load, not a controlled benchmark. Medians of 3 cold runs, spread under 7%.
- Cal.com was timed without installing packages, so its edge count and unresolved count are not representative of a resolved tree.
