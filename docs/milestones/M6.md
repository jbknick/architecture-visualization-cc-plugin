# M6 regression: page → API → table chains and the cross-stack views

Issue #48. Every number here comes from one script, `evals/bench/m6.ts`, run against the built CLI and explorer (`pnpm build` first). Per the public-repo rule this report holds aggregate numbers only: counts, timings, yes/no. The real-repo run used the private TypeScript monorepo of the test bed (TanStack Start, oRPC, Hono, Drizzle); its route, endpoint and table ids, the expected chains and every screenshot stay outside this repository. The expected chains were drafted in #47 and signed off by the operator; they live in the git-ignored `evals/private/m6-expected.json`.

```sh
pnpm build
pnpm tsx evals/bench/m6.ts <repo> [evals/private/m6-expected.json] --data <dir outside the repo> --out <private dir>
```

`<repo>` is only read. The script builds a fresh index into `--data` (refused inside the repo), compares `git status --porcelain` before and after, and prints no id, path or name of `<repo>`. Raw per-feature diffs go to `--out` only.

## Setup

- Machine: the operator's Apple M3 Pro Mac; Chromium from the playwright install in `packages/explorer`, headless, viewport 1440 x 900.
- Index: one fresh `indexRepo` into a new data dir, 11.3 s. The repo's `git status` was the same before and after.
- Chains: for each of the 3 features, `trace(route, down)`, `trace(endpoint, down)` for its endpoints and `trace(table, up)` for its tables, over the store. Then the same through the views' API: `page-api` must hold an edge route → endpoint, `api-tables`' `endpointTables` must list exactly the expected tables, `feature-path` focused on the route must contain the endpoints and tables, `table-usage` focused on each table must contain the pages.
- API times: `handleApi` in process. "Cold" opens a new store connection first, so the snapshot of the store and every trace are built for that request; "warm" is the same request again. Median of 5.
- Page loads: each view opened through the `gantry_open_view` tool's own code (token URL, `gantry map` started on the same data dir, the production build), then a full page load to the drawn canvas (`data-ready`). Median of 5.

## Notes

- Every view answers from an in-memory snapshot of the store (`snapshotOf`, keyed on the store's generation), so tracing all 54 routes for the page → API view costs one load of the edges rather than a query per visited node. A test checks that `trace` over the snapshot equals `trace` over the store for every route, endpoint and table of `fixtures/adapters`, in both directions.
- The page → API view counts a request only from the page's own code (what the route reaches before any endpoint); a handler that calls another endpoint is server code and is left out. The API → tables view follows an endpoint's own handler only (no other endpoint's tables), which is the per-endpoint comparison the expected file asks for.
- Operator hand-check: open each view with the production build (`node plugin/dist/cli.js map --no-open` in the repo) and compare with the expected chains; the command lines and focus values are with the operator, not in this repository.
