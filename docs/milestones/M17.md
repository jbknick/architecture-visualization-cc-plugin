## Hook time with boundary checks (row 9 and 10)

What was run. A copy of `formbricks@b52ebf8` was indexed cold with `gantry index` (6,033 files, 24,923 symbols, 107,604 edges, 12,996 unresolved, 0 parse errors, 26.1 s). Groups were then written to its overlay, one per top-level directory under `apps/*` and `packages/*`, with `mayUse` set to the workspaces that directory's `package.json` depends on. That rule gives **23 groups, not the 20 the issue states** (3 under `apps/`, 20 under `packages/`; 80 `mayUse` entries in all). The rule was kept and the count recorded.

For each batch size and run the indexed data directory (with the groups) was copied afresh and the repo copy reset with `git checkout -- .`. How to read the bar. Spec section 14 gives the per-edit hook and the end-of-batch check a budget of 1,500 ms each. Read that way (one PostToolUse call, one Stop call), Stop passes with a wide margin (212 and 336 ms) and PostToolUse fails (about 2.4 s). Read as the issue's wording, "PostToolUse plus Stop for a batch, under 1,500 ms each", both batches fail (2,580 and 23,981 ms). Either way the rows are recorded as failed.

Why PostToolUse is slow, as far as measured. The hook logged `budget of 1500 ms exceeded` on every one of the 33 PostToolUse calls (the hook's own timer gives up and prints nothing, which it does anyway when a session id is given; the process stays alive until its re-index of the file ends, which is why the wall clock is 2.4 s). PostToolUse does not read `overlay.db`. As a control the same three runs were repeated with `overlay.db` deleted from every data copy, so there were no groups at all:

| ------- | ------------------- | ------------ | ----------- |
| 1 file  | 2,376 ms            | 207 ms       | nothing     |
| 10 file | 2,368 ms            | 307 ms       | nothing     |

The load averages at the start of these six runs were between 2.08 and 2.36 (1 min). So the boundary checks cost about 5 ms (1 file) and 29 ms (10 files) in Stop and nothing in PostToolUse; the 2.4 s of PostToolUse is the cost of re-indexing one file of a 6,033-file repo into the working layer, not of M17. Which part of that re-index takes the time was not investigated when this report was first written; #360 did (next section).

## Hook time after the fix (#360, rows 9 and 10)

Where the time went. A V8 CPU profile of one PostToolUse call (one edited file, `formbricks@b52ebf8` indexed, 2,129 ms of profile; about 270 ms of that is Node start-up and loading the CLI):

| Phase of the working-layer re-index                                                                                                                                                      | ms   |
| ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---- |
| Re-resolving the edges of every file to find importers whose edges changed (`indexRepo`)                                                                                                 | 822  |
| Framework adapters over the whole read set: the Drizzle adapter parsing every file that has a `.update(` or `.from(` call (255), the client-call matcher resolving every bare call (260) | 623  |
| File discovery (`git ls-files`, include and exclude matching, workspace detection)                                                                                                       | 258  |
| Everything else (reading and hashing files, parse cache, the one file written, store open)                                                                                               | rest |

The first two grow with the repository; store open and the write of the edited file are in the "rest" and are a few milliseconds. What was changed (no schema change, no change to what a full index writes):

- A targeted run (`files` given) re-resolves only the files that can have changed: the importers of the files it wrote or deleted, walked on through every importer whose edges did change (which is how a barrel passes a change on), the files that carry adapter output, and the files whose text ends an import specifier with the name of a file it wrote (an import that was waiting for it). It used to resolve all 6,033.
- The Drizzle adapter now applies only to workspaces that depend on `drizzle-orm` or on a workspace that does. Its `link` already dropped tables and usage everywhere else, so the output is the same.
- The client-call matcher skips resolving bare calls when the repository has no TanStack Start server function, since such a call could not name one. The output is the same.

A cold full index with the changed code on `formbricks@b52ebf8` gave the same SHA-256 for the main-layer `edges` rows, the `adapter_nodes` rows and the `files` ids and content hashes as the build before (`5df5851a2f6a`, `dfbda4c3f6d2`, `28cb97bfba1d`, first 12 characters), so the store schema version stays at 12.

The same procedure as above, with a harness outside the repo: a copy of the pinned repo indexed cold, 23 groups written to its overlay (one per directory under `apps/*` and `packages/*`, `mayUse` from each `package.json`; 81 entries here, 80 above), each run on a fresh copy of the data directory with the repo copy reset. The edit appends an import of an exported function from a group the file's group does not list, plus a function that uses it (22 files planned, the first 1 or 10 used). ## Boundary noise on a real repo (row 11)

What was run. A private copy of the repo's history (fetched at the pinned SHA by the #284 script), the same 23 groups as above. The base state is the parent of the oldest replayed commit (`5381fc5`), indexed cold (23.1 s). The 100 replayed commits are the 100 first-parent commits before the pinned SHA, `19e87ea` (oldest) to `9c9bf6a` (newest); the pinned commit itself is not replayed. For each commit, the files it changed were checked out into the working tree on top of its parent (deleted files removed), each source file and manifest was recorded as an edit with `recordEdit`, and the batch was settled with `settle` (the Stop pipeline of `packages/cli/src/hooks/postToolUse.ts`) with no deadline, so every file is checked. Crossing findings were counted before the 600-character cap. Between commits the checkout moved to the commit and `heal` brought the index up to it.

A positive control, to show the replay can see a crossing: in a separate three-commit run of the same script, one name-based import of `@formbricks/database` was appended to a changed file of `packages/types` (which does not list `packages/database`) at the second commit. That commit gave 2 crossing lines, both `packages/types -> packages/database` (the import and the call); the other two commits gave none.

What this says and does not say. With groups built from each package's declared dependencies, 100 real commits added no import or call into a group that the group's `package.json` does not already depend on. That is a lower bound on noise for this kind of group, not a general rate: groups drawn along the dependencies a repo already declares are close to the repo's own rules, and the hand-drawn groups of a person (a feature slice, a layer) would cross far more often. Edges the main layer already had are not reported, so only new edges count. The bar is none; the number recorded is zero.

## Overlay survival on a real repo (row 12)

#284 (`docs/spikes/overlay-ids.md`) measured, on `formbricks@b52ebf8` over 500 first-parent commits, 1,000 sampled function-like entries, 967 of which still exist at the end: 960 (99.28%) survive by id, 966 (99.90%) with re-attaching by `exactHash`, 0 wrong re-attaches. On trpc the same figure is 97.14% (577 of 594), against a bar of 90%.

Rerun on this branch's code, once:

```
pnpm tsx docs/spikes/overlay-ids/run.ts --repo formbricks --commits 500
```

It finished in 2,520 s (load averages 2.25, 7.11, 9.75 about two minutes in and 12.71, 16.61, 12.52 at 275 of 500 commits; the machine was shared). Its stdout has sha256 `c6a42c30679fee9cebd0cf6588e2fd075ee6faf41b73554d141f48b56bcd34a9`, the same as the hash #284 recorded for the formbricks section of `results.json`, and the section is identical to it: 1,000 entries, 33 deleted, 967 still exist, 960 survive by id, 966 with `exactHash`, 966 with `renamedHash`, 0 wrong re-attaches. The share with `exactHash` is 99.90%, equal to #284's within 0.5 percentage points (difference 0.00).

Update (#361): the script now stores each sampled entry as a real label in `overlay.db`, heals with `reattach` at every replayed commit and counts the labels that point at the truth symbol, so the share below comes from the shipped `reattachOverlay`. The re-run (`pnpm tsx docs/spikes/overlay-ids/run.ts --repo formbricks --commits 500`, 2,143 s) gave 1,000 entries, 33 deleted, 967 still exist, 960 survive by id, **966 (99.90%) with the shipped re-attachment**, 0 wrong re-attaches, 0 ambiguous; the one miss is the `modified_and_moved` `createToolServer` entry. That is equal to #284's 99.90% (difference 0.00 percentage points, inside the 0.5 bar). `renamedHash` is no longer scored (the shipped code has none). The in-place rename gap (#349) is untouched: 9 in-place renames in these 500 commits, none among the sampled entries that missed.

What the script was before #361. `docs/spikes/overlay-ids/run.ts` replayed commits with the shipped `heal` and `reviewDiff`, but scores the entries with its own `attach()` function (re-attach to the one symbol whose `exactHash` equals the stored one). It does not call the shipped `reattachOverlay` (#288), and `heal` is called without `reattach`. So the identical result confirms the spike's figure still reproduces on the current `reviewDiff` and indexer, and that the rule #288 implements (one unique `exactHash` match, otherwise unresolved) gives 99.90% on this repo; it does not run #288's code on 500 commits. #288's own code is covered by `reattach.test.ts` (5 cases, in row 3) and the Verify of row 6.

## Known gaps recorded by the build reviews

- Re-attachment (#288) uses `exactHash` only, so a function renamed in place does not re-attach: it is listed as unresolved with reason `gone`. A file move or file rename does re-attach. Follow-up: #349. The #284 spike had 9 in-place renames on formbricks and none on trpc in 500 commits, so a rename-heavy repo is untested; the 99.90% above does not speak for one.
- Re-attachment runs only from explicit callers (`gantry heal`, `index`, `init`, the map rebuild, the MCP refresh, the explorer Refresh), never from a hook, and also when a hook already healed the commit.
- Hovering a group on the map marks only its first file member (the README says so). The Curation section is not shown in the 3D map's left panel. The pickers use the kit's select.
- Boundary crossings are warn only; there is no `block` mode, and the PR comment carries no crossings (groups live in the data dir). Hooks read `overlay.db` and never write it.

## Deviations from the issue text

- 23 boundary groups were created, not 20: one per directory under `apps/*` (3) and `packages/*` (20) is 23 at `b52ebf8`. The rule was followed; the count of the issue was not.
- The Verify script of #290 was run with the base worktree at `d0556074` instead of `git merge-base HEAD origin/main`, which is the commit under test when the branch holds no commits. The worktree was in the session's scratch folder, not `/tmp`.
- Two Verify scripts (#285, #289) got `echo` lines that print the hashes and exit codes; no command of the issue was changed or dropped. The scripts were run with `bash`.
- Row 2: `pnpm build` was run on its own first, then the Playwright command.
- Hook timings are the wall clock of the whole Node process, start-up included, measured by a harness outside the repo that spawns the built CLI; the issue does not say how to time a hook.
- The 10-file batch ran 10 PostToolUse processes and one Stop; Stop printed 2 crossing lines because of the 600-character cap, not 10.
- Row 12: the first version of the script did not exercise the shipped `reattachOverlay`; #361 fixed that (see above).
- README: the Status table had no M17 row; one was added. The Quick start, "What you can see" and the Commands table were checked against `main`; "What you can see" gained one sentence on what re-attachment does and does not follow (see the README diff).

Body: In the M17 report (`docs/milestones/M17.md`), `gantry hook post-tool-use` took a median of 2,371 ms (1 file, 3 runs) and 2,366 ms (10 files, 30 calls) on `formbricks@b52ebf8` (6,033 files) on an Apple M3 Pro at load 1.7 to 2.6, against the 1,500 ms budget of spec section 14. Every call logged `budget of 1500 ms exceeded`. It is not caused by M17: the same median (2,376 ms) was measured with no overlay at all, and PostToolUse does not read `overlay.db`. Stop was 212 ms (1 file) and 336 ms (10 files). Find where the time goes when one file is re-indexed into the working layer of a large repo (workspace and tsconfig resolution, opening the store, resolving imports), and bring a single call under 1,500 ms on that repo, or change the budget through the spec. Re-measure with the same method: median of 3 runs, load averages beside every timing.
