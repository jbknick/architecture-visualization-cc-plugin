# M3 regression: 30k-function performance, determinism, deep links

Issue #39. Everything here comes from one script, `evals/bench/m3.ts`, run against the built explorer (`pnpm build` first). Per the public-repo rule this report holds aggregate numbers only: counts, timings, frame rates, yes/no. The real-repo runs used a private TypeScript monorepo (1,541 files, 9,042 symbols, 5,710 function-like, 11 workspaces); its screenshots, layout dumps and names stay outside this repository. The same script also ran on the public `fixtures/pnpm-turbo`, which is where the deep-link, determinism and cross-origin results can be re-checked by anyone.

```sh
pnpm build
pnpm tsx evals/bench/m3.ts <repo> --out <private dir>    # views 1-5, 30k, determinism, deep links, 403
pnpm tsx evals/bench/m3.ts fixture --steps determinism,deeplinks,security   # public data only
pnpm tsx evals/bench/m3.ts fixture --steps perf30k [--headed] [--gl swiftshader]
```

`<repo>` is only read: its data directory goes under `--out` (or a temp dir) through `CLAUDE_PLUGIN_DATA`, and the script compares `git status` before and after (unchanged in every run below). The script takes the repo path as an argument and writes no path, file name or symbol name of it into its output.

## Setup

- Machine: Apple M3 Pro Mac (the operator's), macOS, Chromium 1254 from the playwright install in `packages/explorer`, viewport 1440 x 900, light scheme. Views 1 to 5, determinism, deep links and the cross-origin check ran **headless** (`chrome-headless-shell`). The 30k step ran **headless twice and headed once** (a visible window on the built-in 120 Hz screen); both are shown below.
- GL: the machine's GPU through ANGLE/Metal (`--use-angle=metal`); the renderer string reported by the page was `ANGLE (Apple, ANGLE Metal Renderer: Apple M3 Pro)`. Software GL (`--gl swiftshader`) is available and far slower; it was not used for any number here.
- Frame rate is counted with `requestAnimationFrame` over a scripted 10 s drag (and, in the 30k run, a second 10 s of drag plus wheel zoom). Headless Chromium paces `requestAnimationFrame` at 60 Hz, so 60 is the ceiling there and "60.0" means no dropped frames, not "more headroom exists"; the headed run follows the screen's 120 Hz.
- The index is `gantry init` into a fresh data dir (about 9.6 s for the private repo); the explorer is started through the `gantry_open_view` tool's own code (`openViewTool.run`), so the token URL, the spawn and the 2.5 s start limit are the real path (start: 142 to 220 ms).

### Is headless fps representative?

For pan, yes; for the worst cell, it is pessimistic. The GPU path is real in both modes (Metal through ANGLE, the same renderer; sigma draws the same WebGL frames). Headless has no window compositor and paces frames at 60 Hz, so it cannot show more than 60. The headed run on the same graph, same machine, measured 117.8 to 119.9 fps panning (the screen's 120 Hz) and 72.3 fps for far-zoom drag plus wheel zoom, where headless measured 45.0 and 47.4. So the headed number is the one to quote for the operator's Mac, and the headless number is a safe lower bound. To re-run the fps step headed (a window opens and plays the scripted drag for about 2.5 minutes; leave the mouse alone and keep other apps idle):

```sh
pnpm build
pnpm tsx evals/bench/m3.ts fixture --steps perf30k --headed
```

The line to read is `minPanFps` in the JSON on stdout (the lowest of the three "pan" rows); the done-when is at least 50. For a real repo, `pnpm tsx evals/bench/m3.ts <repo> --steps views --headed` does the same for views 1 to 5.

## 4. Deep links

`gantry_open_view` is called for each view with a `focus` (a node id found through the API: a workspace for the project map and the 3D map, a function with callers for the ego view, a function in the duplicates data, a route for pages, a slice for slices). The returned URL is opened in a fresh browser and the script waits up to 10 s for the inspector (`aside[aria-label=Inspector]`) to show a heading whose `title` is the focus id. The second column adds `filters: { sel: <focus> }` to the call.

| ----------- | ----------- | ------------------------------------- | -------------------------------------------------- | -------------------------------- |
| project-map | yes         | no                                    | yes                                                | yes                              |
| ego         | yes         | no                                    | yes                                                | yes                              |

| pages       | yes         | no                                    | yes                                                | yes                              |

Same result on the private repo and on the fixture. The link opens the right view and the view uses the focus (the project map shows that subtree, the ego view centers on that function), but the explorer opens the inspector only for the hash key `sel`, and `gantry_open_view` writes `focus`. `sel` can be passed today as a filter, because the route treats that key as the selection, but that is a workaround, not the documented contract. **Missed in the first run; fixed in #136** (the explorer now selects the focus node on load when the link has no `sel`; re-run on the fixture: 6 of 6 with focus only). No code was changed in #39 itself.

## 5. Cross-origin check

A second server on another port serves a page on `http://127.0.0.1:<port>` and, separately, on `http://localhost:<port>`. In a browser that holds a valid session for the explorer, that page calls `fetch` on `/api/view/project-map`. The status is taken from the browser's own network events (Chrome DevTools Protocol), matched to that request by its request id. For a request that CORS blocks, the browser still receives the response; the page just cannot read it, and the raw status is reported in `Network.responseReceivedExtraInfo`. The run is on the public fixture (`--steps security`).

| Request                                                                                           | Browser received | Origin header sent by the browser | Cookie sent | The page's own view of it                                        |
| ------------------------------------------------------------------------------------------------- | ---------------- | --------------------------------- | ----------- | ---------------------------------------------------------------- |
| Same origin, with the session cookie (control)                                                    | 200              | n/a                               | yes         | readable                                                         |
| **Page on `127.0.0.1:<other port>`, CORS-mode `fetch`, `credentials: include`**                   | **403**          | `http://127.0.0.1:<other port>`   | yes         | blocked (`MissingAllowOriginHeader`); no status or body readable |
| Page on `localhost:<port>` (a different site), CORS-mode `fetch`                                  | **403**          | `http://localhost:<port>`         | no          | blocked (`MissingAllowOriginHeader`)                             |
| Page on `127.0.0.1:<other port>`, `no-cors` `fetch` (a simple GET: the browser sends no `Origin`) | 200              | none                              | yes         | opaque response; the page cannot read anything                   |

The 403 in rows 2 and 3 is the status the browser got from the server for the page's own request, so the server refuses a foreign `Origin` and the page sees only a CORS failure (which a 200 would also produce; the 403 is what shows the server refused). Supplementary check, not the evidence: a request sent from Node (not a page) with the second origin's `Origin` header and the same cookie jar also gets 403, and the same request with the explorer's own origin gets 200.

The last row is a limit of the check, not a leak of data: an opaque response gives the other page nothing. It does mean the server relies on the `Origin` header and on the browser's opacity rule, not on the cookie being withheld for same-site requests. A hardening idea (send the token only in a header the page sets, not by cookie) is outside this issue.

## Method limits and caveats

- Frame rate is measured with a `requestAnimationFrame` counter during scripted mouse input. It does not see GPU time spent after the frame is submitted, and headless pacing caps it at 60 (see "Is headless fps representative?").
- **Far zoom with wheel zoom is the weakest cell.** Dragging at far zoom holds 59.6 fps headless and 117.8 headed, but 10 s of drag plus wheel zoom at far zoom measured 45.0 and 47.4 fps headless (33 to 67 ms frames) and 72.3 fps headed (worst frame 108 ms), because at far zoom every wheel step recomputes what is shown of the aggregated 30k graph. The done-when and the acceptance line are about panning, so the line is marked met; the headless wheel-zoom figure is under 50 and is listed as an optional follow-up. At mid and near zoom wheel zoom holds the ceiling. No code was changed in this issue. Fixed in #135: profiling showed the cost was not the aggregated graph but the search that places each workspace link's count pill (a segment-to-rectangle distance, run for every candidate spot against every routed line, allocating on each call). The rewrite allocates nothing and skips lines whose bounding box is out of reach; the pills land on the same spots. Far-zoom drag plus wheel zoom now measures 60 fps headless (95th percentile and worst frame 17 ms), against 38.3 fps on the same machine before.
- The synthetic graph has workspaces, files and functions with random-looking but seeded imports; a real 30k-function repo has a different edge distribution. Cal.com, named in the issue as the preferred 30k test, was not tried and was not cloned.
- The 30k step is served by the mock API, so it measures the browser side only (layout, drawing, panning), not the server's time to build a 30k-function view from SQLite. The private repo run (5,710 function-like symbols) exercises the real server.
- The private repo has no embedding vectors, so the duplicates view there shows the exact and near tiers only.
- The project map was timed at its default level only.
