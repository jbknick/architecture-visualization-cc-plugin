# M5 regression: review data and the review view without a re-index

Issue #44. Every number here comes from one script, `evals/bench/m5.ts`, run against the built CLI and explorer (`pnpm build` first). Per the public-repo rule this report holds aggregate numbers only: counts, timings, yes/no. The real-repo run used a throwaway clone of a private TypeScript monorepo (1,541 files, 9,042 symbols, 11 workspaces); its symbol ids, the hand-check list and its screenshots stay outside this repository. The same script runs on the public `fixtures/pnpm-turbo`, where anyone can re-check it.

```sh
pnpm build
pnpm tsx evals/bench/m5.ts <repo> --out <private dir>      # three ranges of about 5, 20 and 40 files
pnpm tsx evals/bench/m5.ts fixture --targets 1,2,3         # public data only
```

`<repo>` is only read. Its data directory goes under `--out` through `CLAUDE_PLUGIN_DATA`, and the script compares `git status` and a content hash of the index (files, symbols, indexed head) before and after every range. It prints no path, file name, symbol name or commit of `<repo>`: ranges are printed as `HEAD~k...HEAD`.

## Setup

- Machine: the operator's Apple M3 Pro Mac, Chromium from the playwright install in `packages/explorer`, headless, viewport 1440 x 900.
- The index is one `gantry init` at the clone's HEAD (15.2 s for the private repo), so every range below is `HEAD~k...HEAD` with the head checked out, as when a branch under review is checked out. Nothing is indexed again: `gantry review --json` reads git blobs and the index as it is, and the explorer's review view does the same.
- Ranges: for each target (5, 20, 40 changed indexable files) the first-parent range `HEAD~k...HEAD`, k up to 300, whose file count is closest. The private history gave 3, 17 and 45 files.
- The explorer is started through the `gantry_open_view` tool's own code (`openViewTool.run` with `view: "review"` and `filters: { range }`), so the token URL, the spawn and the start limit are the real path.
- Times: `gantry review --json` is the wall time of the CLI process (diff plus impact; run twice). "API cold" is the first `/api/view/review` request for that range in the explorer (nothing cached for it yet); "API cached" the second. "Page" is a full page load of the tokenised URL to the first drawn ring (`data-ready`), after the API calls.

## Hand-check

The blast radius of the 17-file range (22 changed symbol ids; 18, 34 and 52 callers at hops 1 to 3; 7 crossings) is in `handcheck.json` in the private output directory, by symbol id only. The operator confirms it in a comment on the PR; until then this line stays "Pending". As a check that needs no graph, the script reads the file of each hop-1 caller and looks for the old or new name of a changed (not added) symbol: 18 of 18 name one. On the fixture, 3 of 3 do (the third is the barrel file that re-exports the renamed function under its old name; the first version of the check looked for the new name only and counted 2 of 3).

## Notes

- The cached API answer still rebuilds the rings from the store (edge queries per ring node), which is why it is 0.2 to 0.6 s rather than near zero; the diff and impact are what the cache saves.
- In one earlier run of the same script on the private repo, `gantry_open_view` returned `explorer_unavailable`: the freshly spawned explorer did not answer within the 2.5 s start limit (the machine was busy; the next run started it in 222 ms). Worth watching on large repos; no issue filed yet.
- With the index at the head, callers of code the range removed are not in the graph; the impact notes say so (spec section 11). An index at the merge base would list them.
